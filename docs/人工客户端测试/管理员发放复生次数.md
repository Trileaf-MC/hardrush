# 管理员发放复生次数

日期：2026-10-21。状态：待人工测试。使用本次 26.3 构建，在独立极限模式测试实例进行；无需客户端模组。自动检查覆盖规则、快照升级、SQLite 与原生命令权限，不代替客户端画面和游玩验证。

准备一名 OP 3 管理员、至少两名本轮已参赛玩家；其中一名死亡成为怪物，另一名保留人类身份。

- [ ] 管理员输入 `/hardrush admin grant-revival <怪物玩家名> 3 测试补偿`，无需 confirm，提交成功的回执显示目标 UUID、增加 3 次、剩余 3 次和成绩待核验提示。
- [ ] 目标收到次数增加提示，重新打开怪物菜单和复生祭坛显示 3 次，靠近祭坛的行动栏也显示余额。
- [ ] 提交中再次执行发放被拒绝；完成后再发 2 次，余额为 5；无 OP 或 OP 2 不能发放，控制台可直接发放。
- [ ] 怪物在冷却中通过祭坛确认或 `/hardrush revive` 空装复生，余额只减一次；连续点确认、交替输入命令不重复扣除。再次死亡回怪物大厅，剩余次数保持。
- [ ] 向仍为人类的本轮玩家提前发放 2 次，身份和背包不变；人类死亡回大厅后显示并可使用这 2 次。
- [ ] 目标离线后按完整 UUID 发放，再重连显示正确余额；正常停服重启后余额保持。
- [ ] 持有多次的怪物击杀在赛人类，余额不额外增加也不缩减；余额为零时击杀仍获得一次。
- [ ] 目标使用过复生次数后，再次发放按当前余额累加；每条发放命令独立提交，不出现确认票据或要求执行 confirm 的提示。
- [ ] 本轮救场期间发放不延长剩余时间；普通模式、救场到期、结算或恢复隔离时不能发放，纯大厅访客不能领取。轮次结束并进入下一轮后旧余额不能使用。
- [ ] `/hardrush admin audit current` 显示 `GRANT_REVIVAL`、管理员、原因、目标 UUID 和前后余额；仅发放次数不增加实际复生统计，成绩显示待核验。

每项填写实际结果，画面和交互异常附截图或录像。本清单未执行真实客户端测试。
