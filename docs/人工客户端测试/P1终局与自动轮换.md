# P1 第三批人工检查：终局与自动轮换

日期：2026-10-14。由用户在独立开发实例、干净原版 Minecraft 26.3 客户端执行；本批没有运行真实客户端、截图或 computer use。实现说明见 [P1 第三批记录](../p1-terminal-rotation.md)，当前阶段未验收。

## 准备实例与记录

保留日常服务器数据库和世界。请在用户自行准备的独立 Fabric 26.3 测试实例安装本批 HardRush JAR 与对应 Fabric API，使用 Java 25，从该实例目录启动。首次全新 P1 库需明确普通模式：

```bash
java -Dhardrush.p1.enabled=true -Dhardrush.p1.initialMode=normal --enable-native-access=ALL-UNNAMED -jar fabric-server-launch.jar nogui
```

`fabric-server-launch.jar` 是启动文件名示例，按该实例实际名称替换。仓库的 `scripts/p0-gradle.sh :platforms:mc263:runServer -PhardrushP1=true -PhardrushP1InitialMode=normal` 固定使用已有 `.local/server-p0` 开发目录，**不会自动创建隔离实例**；仅在明确使用这个开发目录时运行，不能把它当成新测试实例入口。

P1 默认关闭；省略 normal 时首次库默认极限，当前极限模式拒绝就绪开赛，这是预期。已有库的当前模式不会被 `initialMode` 改写；`/hardrush config next-mode normal` 仅改下轮，也不会把当前极限轮立刻变成普通轮。不要删除或修改日常库来制造可开赛条件。

准备玩家 A、B 两个 UUID，分别记录昵称、JAR SHA-256、当前 `/hardrush status`、轮次 ID 与规则指纹；种子和三维度键可从本轮 `hardrush/p1-worlds/<roundId>.json` 只读记录。保留服务端日志。以下聊天提示、背包／容器画面和原版交互由用户判断，状态核对使用 `/hardrush status`；当前没有 TAB 倒计时、排行榜或历史书界面。

## 普通首龙、庆祝与下一轮

| 操作步骤 | 预期与记录 |
| --- | --- |
| 1. 等待世界准备完成；A、B 各执行 `/hardrush join`、`/hardrush ready`，等待默认 30 秒开局 | 持久化回执后才参与；当前轮次普通，安全进入同轮主世界，保存开局状态 |
| 2. A、B 以普通生存流程进入本轮原生末地；在箱子／末影箱存放可辨物品，保留一处普通建筑 | 不串到大厅或 P0 世界；记录本轮 END 键、物品和建筑位置；有效挑战时间推进 |
| 3. 两人分别攻击首龙，最后由 B 完成致死的一击；检查旧菜单时，让 A 在致死前已打开容器 | 只公布一次结果，胜者为真实 B 的攻击来源；保存致死前后状态与视频／操作时间。数据库写入完成可能晚于致死，成绩停在捕获点，不持续增加 |
| 4. 首龙致死后尝试近战／射箭、再次引爆竞技伤害；点击已经打开的旧容器，再主动关闭菜单；尝试打开新容器、丢弃／拾取物品或经验、搬动物资 | 新竞技伤害、容器点击和物资／经验转移被冻结；主动关闭菜单正常，轮换时系统关闭也正常，不复制物品、不产生第二结果。原参与者仍可观察庆祝；记录客户端回弹或不同步 |
| 5. 庆祝中让 B 下线并重连，随后重复一次 | 未返回者恢复庆祝位置和临时物资余量；已返回者留在大厅。原物资封存，不从旧 vanilla 文件回滚或重复发物品；胜者和成绩不变，庆祝不重新开始 |
| 6. 从真实致死观察点实际等待约 90 秒现实时间；期间每隔一段时间记录 `/hardrush status` | 成绩冻结，庆祝从捕获点起算；公布结果延迟不会重新起算 90 秒。不要更改当轮规则／数据库，假时钟或改短配置不作为此项人工通过证据 |
| 7. 到期时保持两人在线，观察轮换；容器／载具退出另用致死前已经打开菜单或已经乘坐的条件复测 | 全员退容器／载具并回长期大厅，系统关闭旧菜单正常；庆祝中不能靠新打开容器制造条件。旧代数档案核验完成，录制停止门槛和旧三维度真关闭完成后才出现下轮。准备未完成时不能提前入场 |
| 8. 核对下轮 status／清单；再次 join／ready，检查物品、经验、床／锚和进度 | 轮次 ID 更新、顺序号递增、使用新种子及下轮规则；新轮空装重置，不携带旧轮物资／绑定／进度；原版累计统计保留。旧轮清单和世界文件保留，无递归删除 |

第 3 项可以先用低血量首龙检查链路：管理员只在本次独立 P1 测试轮中降低原生首龙血量，玩家仍用普通攻击致死，并完整记录修改命令、原血量／目标血量、龙 UUID 和位置。该结果必须标为**低血量夹具**；不算满血生存击龙通过，也不能用 P0 探针世界或 `/kill` 冒充合法尾刀。

## 同批死亡与重复终局边界

| 操作步骤 | 预期与记录 |
| --- | --- |
| 在另一独立普通测试轮，A 创建能同时伤到自己和首龙的床／锚或其他原生爆炸；使同一次原生爆炸中 A 与首龙都死亡 | 已创建的人类来源归属 A，同批普通死亡先记录、唯一通关随后提交；仍只公布一次结果，不因死亡画面撤销合法尾刀。同一 tick 的两个独立攻击不能自动当成同 batch 证据 |
| 庆祝中让另一个玩家攻击尸体／剩余原生实体；另行核对原生已首杀标记或后续复召场景 | 既有胜者／成绩不变，不能建立第二个首龙终局。没有可安全复现的后续复召条件时记“未测试”，不强行编辑数据库凑通过 |
| 若需要降低 A／龙生命、预设站位或搭建爆炸装置才能复现同批条件 | 写明夹具条件、命令和参与 UUID；保留致死原生批次日志。低血量／固定站位夹具结果与普通生存场景分别记录 |

未知来源及旧轮攻击的待核验终局、数据库碰撞／失败回滚主要由自动服务端与 SQLite 夹具覆盖。人工不应篡改日常库或伪造攻击来源；没有专用测试条件时保留“自动夹具覆盖，人工未测”。本批普通模式同批检查不代表 P2 极限死亡→怪物→资格→救场／团灭的验收。

## 正常停止与回放状态

| 操作步骤 | 预期与记录 |
| --- | --- |
| 在一次庆祝剩余约数十秒时记录 status，正常输入 `stop`；等待保存完成，离线一段时间，再用相同实例／制品启动 | 保持原轮 ID、胜者／待核验、停表成绩；重新验证世界／档案后继续保存的剩余庆祝，停服墙钟时长不扣剩余量，不重新起算 90 秒 |
| 在致死后刚公布前或数据库尚在提交时正常 `stop`，保留日志后重启 | 已受理的终局与因果排空，无部分成绩／重复结果；停止时刻先捕获，保存等待不增加挑战时间。需要提交延迟夹具才能稳定复现时如实标夹具 |
| 默认未安装真实 ReplayPort 录制器时完成一轮 | 日志明确 replay disabled；可以按未安装分支继续轮换，但不能声称已经生成或保存录像 |
| 后续由管理员在独立实例安装实际录制器并核验适配；按录制器提供的故障方式测试保存延迟／失败 | 此项当前“未安装，未测试”。已安装分支必须同轮 VERIFIED 保存成功后才释放世界；失败保留旧世界和片段，不自动跳过。没有真实集成和可播放文件不能勾选回放验收 |

正常停止使用 `stop`，不要用强制杀进程替代；强制终止后的完整恢复属于 P3。已有 dirty／RECOVERY_REQUIRED、档案或回放故障时保留文件和诊断，`retry-world` 不能绕过这些门槛。
