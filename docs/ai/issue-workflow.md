# AI 的 Issue 工作流

本文供 AI 在处理 GitHub Issue 相关任务时查阅。面向贡献者的说明见 [CONTRIBUTING.md](../../CONTRIBUTING.md)，新建 Issue 的结构见 [Issue 模板](../../.github/ISSUE_TEMPLATE/)。通过 API 或 CLI 操作时同样遵守这些约定。

## 文档的读者

Issue、贡献指南和模板面向普通玩家/仓库开发者和未来完成这个 issue 落地的 AI Agent，读者不应需要了解当前聊天、AI 工作流或代理工具才能理解内容。

对外文档直接说明需求或参与方式以及你的执行建议和你觉得需要注意的点即可。AI 的执行边界、工具使用及防止误写的详细指令留在本文或相关专项文档中。

## 创建或改写 Issue

发布前搜索已打开和已关闭的 Issue，避免重复。一个 Issue 聚焦一个可以独立讨论和实现的变化；相关项用链接连接，前置依赖需说明具体依赖的能力。

标题直接描述期望的行为。正文先说明场景、期望和价值，再按需补充参考资料、边界、待定问题及可能的验收。简单想法可以只写几句话，不为填满模板而编造细节，也不要求先完成实施设计。

- 写成给开发者的功能建议，避免“本期不实施”“先记录后续事项”等依赖当前任务的措辞。
- 保留确定程度：用户已确认的约束直接写明；实现建议用“可以考虑”；尚未决定的玩法列为待定问题。不要把建议升级为需求，也不要把已确认的要求弱化成可选项。
- 将必要的设计决定和证据整理成独立可读的说明。工具调用、调试经过、子代理分工和执行日志不放进提案。
- 发布前删除模板提示和空章节，以首次阅读者的角度检查标题、背景和链接。

例如，可以写“期望让玩家化身僵尸时，有机会获得幼年形态。复杂度可能在于真实体型、视角和命中判定”，无需先交代这个想法来自哪次开发任务或为什么延期。
