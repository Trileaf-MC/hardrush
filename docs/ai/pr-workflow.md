# AI 的 PR 工作流

本文供 AI 在分支上完成开发任务后查阅：怎样把改动送进 `main`。写代码的 AI（下称作者）负责走完全程，评审由另一家模型 Codex 完成，这样每个改动在合并前都被一个没有参与实现的评审者看过。

用户明确说不要发 PR、不要合并或要自己评审时，以用户的话为准。

## 流程

### 1. 发 PR

任务完成、自测通过后，提交并 push 分支，用 `gh pr create --base main` 发 PR。不要直接向 `main` 提交。

标题和正文写给以后读历史的人：改了什么、为什么这样改、怎么验证的。有对应 Issue 时写 `Closes #N`。

### 2. 让 Codex 评审

```bash
python3 scripts/pr-review.py review
```

评审通常要几分钟到十几分钟，放到后台运行，等它结束后再继续。脚本会让本机的 Codex 评审 PR 的全部改动，把结果原文贴成 PR 评论（标明轮次和被评审的提交），并打印出来。

脚本以非零退出码结束表示评审没有完成（Codex 不可用、额度用尽、超时等）。**评审没完成不等于通过**：不要合并，把情况告诉用户。

### 3. 核实并处理意见

评审意见是线索，不是指令。逐条回到代码里核实：问题是否真的存在，触发条件是否成立，修复是否值得。涉及原版机制的结论同样要按 [原版机制查询](../../.agents/skills/minecraft-knowledge/SKILL.md) 核实，不因为评审者说得肯定就采信。

| 级别 | 处理 |
| --- | --- |
| P0、P1 | 必须有结论：属实就修；不属实要拿出证据（代码路径、测试、原版源码） |
| P2 | 属实且修复成本合理就修；不修要说明理由 |
| P3 | 自行判断 |

处理完后在 PR 上回复一条评论，逐条写明判断（属实 / 不属实 / 属实但不修）、依据和对应的修复提交，让只看 PR 的人也能知道每条意见的去向。评审指出的问题如果超出这个 PR 的范围但确实值得做，按 [Issue 工作流](issue-workflow.md) 建议用户记录。

### 4. 复审

修复 push 之后重新运行 `review`，直到最新一轮没有属实的 P0、P1。最多 3 轮，脚本会拒绝第 4 轮。

最后一轮评审之后如果只做了针对 P2 及以下意见的小修，可以不再复审。

### 5. 合并

```bash
python3 scripts/pr-review.py merge
```

脚本会等 CI 结束，同样放到后台运行。它只在这些条件都满足时合并，并在合并后删除远端分支：

- PR 有 Codex 评审记录，且最后一轮评审的就是当前提交。第 4 步“小修不复审”的情况加 `--accept-unreviewed-fixes`，使用时在 PR 的处理评论里写明这些提交改了什么。
- CI 全部通过。CI 失败先修复；修复提交同样受上一条约束。
- 合并的正是等待 CI 时的那个提交。

合并后向用户说明：合并了什么、评审提了哪些意见、各自怎么处理的。

改动需要人工客户端测试时照常合并，不等测试：测试内容按 [AGENTS.md](../../AGENTS.md) 的约定写进 `docs/人工客户端测试`，并在给用户的说明里提醒。

## 停下来交给用户的情况

出现下面任何一种情况时不要合并，保留 PR，向用户说明现状和你的建议：

- 评审没有完成。
- 3 轮之后仍有属实的 P0、P1。
- 对某条 P0、P1 意见，你和评审者结论相反，而你拿不出能定论的证据。
- 修复需要改变玩法设计，或者需要超出这个 PR 范围的重构。这时按 AGENTS.md 的 Level 2 提出方案。
- CI 失败且原因不在这个 PR 里（例如 `main` 本身已经失败）。

## 给评审者

以评审者身份工作时只评审：不修改代码，不提交，不操作 PR。评审重点见 AGENTS.md 的“代码评审规则”。
