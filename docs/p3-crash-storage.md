## 已实现的保护

玩家跨轮档案转换在重连或新进程遇到既存 PREPARED／APPLIED 时，不再重新执行新轮重置。只有匹配轮次、代数及悬停标记的持久目标快照才能重用；加载已封存的新轮空档案后补齐 APPLIED／VERIFIED。VERIFIED 但原版玩家代数落后时同样重用目标快照，保留原有重置结果。缺目标快照、代数倒退、UUID 不一致、隔离状态缺代数或旧轮悬停档案缺失，均保留隔离并报告故障。不能以大厅的原版数据替代丢失的旧轮档案，也不能把“当前背包为空”当作转换已经完成。

世界准备前检查存储卷可用空间、只读状态及实际创建／写入／fsync 能力；检查在世界 IO 线程执行。默认最低可用储备为 512 MiB，可通过服务端 JVM 参数 `-Dhardrush.p1.minimumFreeBytes=536870912` 调整。只接受非负整数字节数；设为 0 只关闭容量储备要求，仍检查只读和实际写入。非法值停止准备，不静默回退。

准备期间每秒在 IO 线程重新检查容量，检查等待期间暂停后续准备工作，最终清单写入前再次检查。失败保留同一轮次、种子、清单和半完成世界，不自动删档或更换轮次。只清理本次检查独占创建的临时探针。准备之前的 SQLite 操作及已经受理的原版区块 IO 仍可能遇到实际写入失败；储备检查不预留磁盘，也不替代事务回滚或原版 IO 错误处理。

SQLite 失败诊断区分写锁、只读、空间不足及 IO／损坏，并给出具体处理方向。数据库或档案失败继续关闭比赛入口；修复存储不会自动将 FAILED 清为 OPEN。非正常停止恢复为 RECOVERY_REQUIRED，状态明确提示全员留大厅、已提交身份与资格保留、当前没有解除隔离的管理入口。

正常停止除了排空世界 IO executor，还会检查清单、容量及关闭核验任务的结果；worker 已失败但主线程尚未来得及 tick 接收时，不能仅因 executor 退出就误写 clean。该窗口在独立容量故障 GameTest 中验证。

第一条检查 core、persistence、26.3 适配及生产 JAR，并运行无图形服务端回归。第二条必须单独运行：在新随机隔离存档中把最低储备设为不可能满足的数值，验证在清单／维度创建之前拒绝准备、仅修复设置不自动清故障、显式重试仍使用原 UUID／种子，最后实际保存并关闭三维度。它不填满主机磁盘，也不与正式运行时矩阵共享实例。第三条复核正式极限大厅的 20 次死亡／资格／复生闭环和档案接口。

全套 143 core＋94 persistence＋92 platform＝329 项 JUnit、99 项必需无图形 GameTest（含4个未启用专场门禁）通过。独立容量故障／同轮重试、正式大厅20次复生闭环、普通模式十轮各1项通过；另补 RUNNING 的整服正常退出／新 JVM 恢复，两台服务端 JVM 均正常退出，原轮身份／档案／计时及 SQLite 核验通过。这仍不是整服强杀恢复。新增故障矩阵包括：

- 9 项真实 SQLite 故障组合：资格发放、消费、首龙终局分别遇到原生 SQLITE_READONLY、SQLITE_FULL 和索引中途 ABORT。FULL 使用 SQLite `max_page_count`，不耗尽主机磁盘。失败后快照、索引、终局与事件原子回滚，同一事件修复后可重试。
- 12 项独立 JVM 存储强终止：每个场景分别在快照写入后、索引写入后、提交返回后 halt，以及索引写入后由父进程强杀。事务内通过测试触发器和小缓存让实际未提交 WAL 帧落盘；新 reader JVM 检查完整性和幂等结果。所有 halt／阻塞钩子只存在于测试源码。
- 3 项真实 Session 强杀：资格发放、消费和终局在 SQLite 已提交但主线程回调尚未应用时终止 writer，独立 reader 两次隔离重开。恢复不重放死亡／消费／首龙／轮换，计时冻结，保留原始因果和历史记录。
- 4 项档案 journal 强杀：PREPARED、目标悬停快照、APPLIED、VERIFIED 各边界终止 writer，再由独立 reader 检查旧档案、目标快照及转换阶段。4 项原生玩家 GameTest 另验证目标快照重用与缺快照时不能解锁。

SQLite 存储夹具中消费附带的 HUMAN_PROFILE operation 是测试构造的事务能力验证；生产 Session 的资格消费尚未与该任务合并提交，不能据此声称消费和原生档案转换已经跨系统原子化。Session 强杀覆盖的是数据库提交／回调之间，journal 强杀覆盖的是档案存储边界；两者不等于整台 dedicated server 同时承载世界、玩家和数据库时的强杀整链，也不覆盖断电导致的介质缓存丢失。

已完成并冻结的可信首龙终局保留原始证据与历史榜单资格；它不会仅因结算后的进程退出被篡改。没有终局的脏活动轮次计时不确定，保持大厅隔离；未来恢复后产生的成绩必须继续待核验，不能补算未知时段。

整服正常重启复验发现旧 Python runner 只认快照编码1，服务端已正常保存的编码4被脚本误拒绝。本批修复共享前缀的1～4兼容读取，保留未知版本、截断、文本长度、布尔标记及4MiB总长度拒绝，6项Python回归通过；随后使用新隔离存档的整服复验通过。初次脚本失败记录保留在证据中，未修改原失败存档以制造通过。

## 当前可执行的处理流程

1. 查询 `/hardrush admin status`，保留具体轮次、阶段、原始错误和日志，停止受影响玩家继续比赛。不要删除数据库、`-wal`、`-shm`、世界清单、档案 journal、世界或录像。
2. 若仅世界 PREPARING 失败，检查可用空间、挂载和写权限，修复后由 OP 3 执行 `/hardrush admin retry-world <原因>`，核对本轮与影响，再执行显示的 `/hardrush admin confirm <票据>`。请求先写审计；数据库也不可写时不会假报重试成功。完成后仍核验同轮世界和玩家档案才开放加入。
3. 若 Session 为 FAILED 或档案核验失败，先修复写锁、目录写权限、只读挂载或存储容量；正常停止服务端并保留退出错误，确认进程已退出后重新启动。不要同时启动两个进程占用同一存档。无法正常退出时保留强制退出事实，按脏恢复处理。
4. 重启进入 RECOVERY_REQUIRED 是预期隔离结果，不表示比赛恢复完成。本批没有支持解除该隔离、继续原轮或安全中止恢复轮的命令；继续保留资料等待后续恢复入口。重复重启、换规则、手改 cleanShutdown、直接编辑 SQLite 或重新建库不能替代恢复决策。
5. 若涉及损坏或 IO 故障，保留原始资料，在独立副本检查；不要用正在运行的单个 SQLite 主文件复制品当作一致性备份。正式一致性备份与恢复入口仍由 P3-09 实现。
