# 模组自带多个大厅包

2026-11-27 需求方确定方向：除默认营地外，模组再自带 3 个风格不同的大厅包，服主可以在游戏里选用。状态：待实现。

前置阅读：[大厅包与工坊](大厅包与工坊.md) 第 10、12 节，[建筑清单与大厅包构建](建筑清单与大厅包构建.md) 第 2 节。实现时如与本文不一致，在对应小节末尾用“实现偏差：”写明原因。

## 现状

- jar 里只有一个大厅包 `platforms/mc263/src/main/resources/hardrush/lobby/default.hrlobby`，由 `LobbyInstall.Source.builtIn()` 读取，只在没有 `current.json` 的首次启动时安装（`LobbyWorld` 约 134 行）。
- 包库（`LobbyAdmin.library`）只扫描世界目录下的 `hardrush/lobby/packs/*.hrlobby`。`PackSummary` 以 `Path file` 标识一个包，`LobbyAdmin.install(server, file, requester)` 要求文件就在包库目录里。
- 工坊“新建草稿”里的“从包库文件”（`Workshop.Seed.Pack(fileName)`）同样只认包库目录。
- 示例包的源文件在仓库 `lobby-packs/<id>/`，`scripts/lobby-pack.py build <id>` 产出 `out/<id>-v<version>.hrlobby`。

所以现在要让服主用上自带的包，只能让他们自己把文件拷进包库目录。

## 1. 需求

| 项 | 结论 |
| --- | --- |
| 自带的包放哪 | jar 内 `hardrush/lobby/bundled/<id>.hrlobby`，默认营地也搬进去（`bundled/default.hrlobby`） |
| 服主怎么选 | 包库菜单里，自带的包和服主自己放的包列在同一页，自带的排在前面并标明“模组自带”。安装、确认、回滚流程不变 |
| 首次启动装哪个 | 仍然是默认营地。不加配置项：换大厅就是进菜单点一下，没必要再多一个要解释的开关 |
| 能不能改 | 可以。工坊“新建草稿”里能以任一自带包为起点 |
| 版本更新 | 自带包随模组升级而更新。已经安装的大厅不会自动替换（正式大厅是包的一次性实例）；包库菜单里，当前大厅来自某个自带包且 jar 里的版本号更高时，在“当前大厅”按钮上提示“模组自带的这个大厅有新版本”，由服主决定是否重装 |
| 清洗 | 自带包和别的包走同一条读包、清洗、验收路径，不开后门 |

不做：大厅轮换、按人数自动选择大厅、从网络下载大厅包。

## 2. 包的来源抽象

把“包从哪来”做成一个值，替换现在散落的 `Path`：

```java
/** 包库里的一个条目：服主放进 packs/ 的文件，或 jar 里自带的包。 */
sealed interface PackRef {
    record Library(String fileName) implements PackRef {}   // hardrush/lobby/packs/<fileName>
    record Bundled(String id) implements PackRef {}          // jar: hardrush/lobby/bundled/<id>.hrlobby
    String key();   // 菜单按钮回传用的稳定字符串："file:<fileName>" 或 "bundled:<id>"
}
```

- 放在 `lobby/pack`。`LobbyInstall.Source` 增加 `bundled(String id)`，`builtIn()` 改为 `bundled("default")`。
- `PackSummary` 的 `Path file`、`fileName` 换成 `PackRef ref`，另加 `String label`（文件名或“模组自带”）。
- `LobbyAdmin.install(server, PackRef, requester)`：`Library` 分支保留现有的“文件必须在包库目录里”的检查；`Bundled` 分支检查 id 在自带清单里。
- `Workshop.Seed.Pack` 改为持有 `PackRef`。
- 菜单按钮的 `value` 现在是文件名，改为 `PackRef.key()`，点击时重新解析并核对条目仍然存在（沿用现在“按名字重新查找”的做法）。

## 3. 自带清单

jar 里没法可靠地列目录，所以写一份索引：`hardrush/lobby/bundled/index.json`

```json
{"packs": ["default", "end-islands"]}
```

顺序就是菜单里的顺序。`BundledPacks`（`lobby/pack`）启动时读一次索引并缓存；每个包的 `PackSummary` 和包库文件用同一个 `scan` 逻辑得到（读 `pack.json`、算临时设施与警告），放在同一个后台任务里，结果不随时间变化所以只算一次。

索引里列了但资源不存在、或读不出来的条目：记日志，菜单里显示为不可安装并写明原因，不让整个包库打不开。

## 4. 当前大厅的来源与更新提示

`current.json`（`LobbyInstallation`）已经记了包的 id、版本和 sha256。新增一个字段 `origin`：`"bundled"` 或 `"library"`，安装时由 `PackRef` 的类型决定；旧文件没有这个字段时按 `"library"` 处理（目前没有真实用户，不做迁移）。

包库菜单顶层“当前大厅”按钮：`origin` 为 `bundled`、jar 里同 id 的包版本号大于已安装版本时，说明里加一行“模组自带的这个大厅有新版本（v3 → v5），在大厅包库里重新安装即可更新”。只是提示，不自动安装。

## 5. 从源目录到 jar

构建大厅包要启动无头服务端，不适合放进每次 Gradle 构建。做法与现在的默认营地一样：**把构建产物提交进资源目录**，由脚本保证它和源目录一致。

- `python3 scripts/lobby-pack.py bundle <id>`：先 `build`，`ok` 为真才继续；把 `out/<id>-v<version>.hrlobby` 复制为 `platforms/mc263/src/main/resources/hardrush/lobby/bundled/<id>.hrlobby`；把 id 加进 `index.json`（已在则不动顺序）。
- 大厅包的字节是确定的（工坊文档第 7 节：同内容同字节），前提是 `lobby.json` 里提供 `created`。给 `lobby.json` 加一个必填的 `created`（ISO 时间），无头构建用它而不是当前时间。这样重复 `bundle` 不会产生无意义的二进制 diff，也能用来核对。
- `python3 scripts/lobby-pack.py bundle --check`：对索引里每个有源目录的包重新构建并比较字节，不一致时退出码 1。发版前手动跑，不进默认回归（太慢）。默认营地没有源目录，跳过。
- 示例包升级时改 `lobby.json` 的 `version` 和 `created`，再 `bundle`。

默认营地的搬迁：`default.hrlobby` 移到 `bundled/default.hrlobby`，内容不变。`docs/大厅工坊.md`“默认大厅”一节同步改路径。

## 6. 测试

- 平台单元测试：`index.json` 解析；`PackRef.key()` 往返；索引里每个条目的资源都存在、能通过 `PackFile.readHeader`、`pack.json` 的 `id` 与文件名一致。
- gametest：现有“默认大厅包安装成功、验收无错误、包含全部必需功能”的测试改为**遍历索引里的每一个包**。以后每加一个自带包，自动被覆盖。
- gametest（`LobbyAdminGameTest`）：包库列表里自带的包排在前面；安装一个自带包成功并可回滚；工坊里以自带包为起点新建草稿。
- 人工客户端测试：包库菜单里能分清哪些是自带的；每个自带包安装后走一遍主线动线。追加到最新一篇待测试文档。

## 7. 里程碑

- **M1 来源抽象与多包**：第 2、3、4、6 节，默认营地搬迁。此时索引里只有 `default`，行为与现在一致。完成标准：现有 gametest 全过，新增测试全过。
- **M2 打包命令**：第 5 节。完成标准：对一个示例包 `bundle` 后，它出现在包库菜单里并能安装；`bundle --check` 通过。

M1 不依赖任何示例包，可以和示例包的建造并行。
