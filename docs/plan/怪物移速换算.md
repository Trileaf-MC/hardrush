# 怪物移速换算：药水和附魔按原版怪物生效

2026-11-27 起草。状态：方案待需求方确认，未实现。

## 背景

### 现在的换算

原版怪物和玩家走的是同一个移动函数 `Entity.moveRelative(speed, input)`，每 tick 的位移约为“输入 × 速度”（已用 minecraft-knowledge 核对 26.3 源码）：

- 玩家按住 W 时输入为 1.0，速度为移速属性，所以位移 = 1.0 × 属性。
- 原版怪物由 `MoveControl.tick` 驱动：`mob.setSpeed(speedModifier × 移速属性)`，而 `Mob.setSpeed` 同时调用 `setZza(speed)`，把向前的输入也设成同一个数。追击时 `speedModifier` 为 1.0，所以位移 = 属性 × 属性。

因此 `MonsterRoles.ensureBound`（`MonsterRoles.java` 约 1050 行）把怪物玩家的移速**基础值**设成原版怪物基础值的平方：僵尸 0.23² ≈ 0.0529，骷髅、苦力怕 0.25² = 0.0625。没有任何修正时，怪物玩家和原版怪物走得一样快（僵尸约 2.28 格/秒）。

### 问题

平方只作用在基础值上。药水、细雪、附魔等修正直接加在怪物玩家已经平方过的属性上，相当于只算了一次，而原版怪物身上这些修正会随属性一起被乘两次：

| 修正（26.3 原版数据） | 运算 | 原版僵尸 | 怪物玩家（现状） |
| --- | --- | --- | --- |
| 迅捷 I（`MobEffects.SPEED`，每级 +0.2） | `ADD_MULTIPLIED_TOTAL` | ×1.44 | ×1.2 |
| 迅捷 II | 同上 | ×1.96 | ×1.4 |
| 缓慢 I（每级 −0.15） | 同上 | ×0.72 | ×0.85 |
| 神龟药水的缓慢 IV | 同上 | ×0.16 | ×0.4 |
| 细雪冻结（`LivingEntity.tryAddFrost`，最多 −0.05） | `ADD_VALUE` | (0.23 − 0.05)² ≈ 0.0324 | 0.0529 − 0.05 ≈ 0.0029 |
| 灵魂疾行 I（`enchantment/soul_speed`，+0.0405） | `ADD_VALUE` | (0.23 + 0.0405)² ≈ 0.0732 | 0.0529 + 0.0405 ≈ 0.0934 |

可以看出两种偏差：

- **乘法修正（药水）偏弱**：迅捷 II 的原版僵尸约 4.48 格/秒，略快于人类步行的 4.32；怪物玩家现在只有 3.20。缓慢、神龟药水同理，减速也偏轻。
- **加法修正方向不定**：细雪把怪物玩家几乎冻在原地（原版只是变慢）；灵魂疾行反而比原版快很多。

## 目标

怪物玩家身上任何移速修正的效果，都和同样修正作用在对应原版怪物身上时一致。用一句话说：**怪物玩家最终的移速属性 = 原版怪物在同样修正下的移速属性的平方**。

不改变的部分：

- 没有任何修正时速度不变，现有平衡不受影响。
- 怪物照旧不能疾跑（`MonsterRoles.tick` 每 tick `setSprinting(false)`，饱食度固定 6）。
- 不新增配置项。

## 方案

### 核心：一个补偿修正

保留现在的基础值 n²（n 为原版怪物基础移速），另外给怪物玩家的 `MOVEMENT_SPEED` 加一个由本模组维护的修正：

- id：`hardrush:native_gait`
- 运算：`ADD_MULTIPLIED_TOTAL`
- 以 `addTransientModifier` 添加：不写进玩家存档，下线、重启后由下一次 tick 重新计算。

每 tick 计算：

1. **v（原版怪物等效值）**：以 n 为基础，套用玩家 `MOVEMENT_SPEED` 上除 `hardrush:native_gait` 和原版疾跑修正（`LivingEntity` 的 `SPRINTING_MODIFIER_ID`，怪物不会疾跑，排除只是为了保险）以外的**全部修正**，按原版 `AttributeInstance` 的公式计算：
   - `x = base + Σ ADD_VALUE`
   - `x = x × (1 + Σ ADD_MULTIPLIED_BASE)`（以加完 ADD_VALUE 后的 x 为底，与原版一致）
   - `x = x × Π(1 + ADD_MULTIPLIED_TOTAL)`
   - 最后按属性的取值范围截断（`RangedAttribute.sanitizeValue`，移速下限 0）。
2. **w（现状值）**：同样的修正以 n² 为基础计算出的值，即去掉补偿修正后玩家的实际属性。
3. **目标值**：v²。
4. **补偿量**：w > 1e-6 时为 `v² / w − 1`；否则为 0（被冻到 0 时没有可补偿的量，原版怪物这时也几乎不动）。
5. 补偿量和当前修正相差小于 1e-6 时什么也不做；否则先移除再添加，避免每 tick 都触发属性同步包。

建议把第 1、2 步写成一个纯函数，例如 `MonsterGait.equivalent(double base, Collection<AttributeModifier> modifiers)`，返回截断后的值。这样同一个函数既算 v 又算 w，不会出现两处公式不一致。

不直接调用 `role.model` 的属性实例来算 v：`role.model` 还承担装备镜像、伤害和音效，往它身上挂修正，容易和别处的逻辑互相干扰。

### 接入点

- **计算时机**：`MonsterRoles.tick` 中 `ensureBound(player, role)` 之后，每个在线、存活的怪物玩家每 tick 算一次。药水添加和计算之间最多差 1 tick，可以忽略。
- **基础值**：`ensureBound` 里平方的那段保持不变，但要在那里加注释，说明为什么要平方（引用本文“背景”一节）。现在这段代码没有任何注释。
- **恢复人类**：`MonsterRoles.restoreOriginal` 恢复基础值的同时移除 `hardrush:native_gait`。`clear`、角色解除（约 750 行）和死亡转人类都走 `restoreOriginal`，实现时逐一确认没有漏掉的路径，例如直接 `setBaseValue` 而绕过 `restoreOriginal` 的地方。
- **换角色**：`ensureBound` 换形态后基础值 n 会变化，下一 tick 自然按新的 n 重算，不需要单独处理。

### 需要核实的原版事实

实现前用 minecraft-knowledge 核对以下几点，并把结论写进代码注释：

- `ClientboundUpdateAttributesPacket` 是否包含临时修正（transient modifier）。如果不包含，客户端预测的移速会和服务端不一致，造成回拉，那就要改用 `setBaseValue` 动态调整基础值（但仍需排除补偿本身）。
- `AttributeInstance.calculateValue` 的计算顺序是否与上面三步一致。
- 26.3 的 `RangedAttribute` 中移速的上下限。

### 其他影响

- **伪装显示**：`MonsterDisguise` 会把玩家的同步属性转发给观察者，用于原版怪物模型的显示。补偿修正会一起发出去，只影响显示用的数值，不影响位置，因为位置由服务端同步。确认 `MonsterAppearanceGameTest` 中“Mob display uses authoritative player speed”断言的仍是基础值。
- **玩法变化**（需求方确认）：
  - 商店迅捷药水（迅捷 I）：僵尸 2.28 → 3.29 格/秒，骷髅、苦力怕 2.70 → 3.89。
  - 盲盒开出迅捷 II 时，僵尸 4.48、骷髅 5.29，**快于人类步行（4.32）、慢于疾跑（5.61）**。
  - 神龟药水（商店 12 币）的减速变得很重：僵尸约 0.37 格/秒（现状 0.91），持续 20 秒。它换来的抗性提升 III 不变，药水说明可能需要提示“会变得非常慢”。
  - 盲盒的负面缓慢 I 从 −15% 变成 −28%。
  - 细雪不再几乎冻住怪物；穿灵魂疾行靴子的怪物不再异常地快（宝库奖池里有没有这种靴子，实现时顺带确认）。

## 测试

GameTest（放在 `MonsterRoleGameTest` 或新建 `MonsterGaitGameTest`，进默认套件）：

1. 僵尸和骷髅各一遍：无修正时属性 = n²（原有断言保留）。
2. 添加迅捷 I、迅捷 II、缓慢 I，属性分别 = (n × 1.2)²、(n × 1.4)²、(n × 0.85)²，误差 < 1e-5。
3. 同时有迅捷 II 和缓慢 I 时，属性 = (n × 1.4 × 0.85)²。
4. 手动加一个 `ADD_VALUE` +0.0405 的修正（模拟灵魂疾行），属性 = (n + 0.0405)²。
5. 效果移除后，属性回到 n²。
6. `MonsterRoles.clear` 之后，玩家身上没有 `hardrush:native_gait`，移速恢复人类原值（现有“Human movement restored”断言扩展为检查最终值和修正列表）。
7. 补偿量不变时连续 tick 不重新添加修正：两次 tick 之间修正对象是同一个实例，或用计数器断言。

如果把纯函数放在可单测的位置，再补一组单元测试，对照原版公式覆盖三种运算的组合，以及截断到 0 的情况。

人工客户端测试（追加到最新一篇待测试文档，约 5 分钟）：怪物喝迅捷 II 后在平地上走，看客户端有没有回拉或抖动，手感是不是“明显快了”。
