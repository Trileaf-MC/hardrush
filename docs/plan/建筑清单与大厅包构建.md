# 建筑清单与大厅包构建

2026-11-27 与需求方确认方向。状态：已实现（2026-11-27），待人工客户端测试（2026-11-27 场次）。

前置阅读：[大厅包与工坊](大厅包与工坊.md)（下文“工坊文档”）。实现时如与本文不一致，在对应小节末尾用“实现偏差：”写明原因。

## 背景

我们要用 AI 给模组做几个示例大厅包。建筑部分由 AI 在 [genMC](https://genmc.app)（浏览器里的方块建筑工作室，通过 MCP 让 AI 放方块、渲染自查）里完成，再导入工坊。实测（2026-11-27）发现三个缺口：

1. **功能绑定带不进来**。大厅功能靠标记盔甲架绑定（工坊文档第 4 节），而建筑文件导入只导方块和方块实体，不导实体（19.2）。一个合格大厅有 20 多个必需绑定，现在只能人进工坊一个个放。
2. **外部工具导出的方块缺连接状态**。genMC 导出的栅栏、玻璃板、墙、红石线不带 `east=true` 这类连接属性（楼梯、门是带的）。`PackPlacer` 为了不弄坏跨瓦片的门和床，用 `setKnownShape(true)` 放置且不做邻接更新，所以导入后栅栏是一根根孤立的柱子。
3. **AI 没有验收闭环**。验收只在游戏里的工坊跑，AI 不知道“还缺什么、哪个落点站不住”。

这三件事对社区同样有用：任何用外部工具建图的人，都可以随建筑附一份清单，导入即带绑定。

## 1. 建筑清单

建筑文件旁边放一个同名清单：`<去掉扩展名的文件名>.hardrush.json`。例如 `camp.schem` 配 `camp.hardrush.json`。没有清单时行为与现在完全一样。

```json
{
  "format": 1,
  "origin": [4, 2, 7],
  "update_shapes": true,
  "markers": [
    {"function": "assembly", "as": "zone", "shape": "flood", "at": [20, 2, 30], "materials": ["minecraft:lime_wool"]},
    {"function": "courtyard", "as": "zone", "shape": "box", "at": [40, 3, 12], "box": [5, 4, 5]},
    {"function": "landing_central", "as": "point", "at": [24, 3, 24], "yaw": 180},
    {"function": "role_zombie", "as": "model", "at": [30, 3, 10], "yaw": 90},
    {"function": "rules", "as": "click", "at": [22, 3, 20]},
    {"function": "ominous_vault", "as": "block", "at": [35, 3, 8]},
    {"function": "status", "as": "text", "at": [23, 4, 19]}
  ],
  "signs": [
    {"at": [31, 4, 10], "front": ["右键模型", "选择僵尸"], "back": []}
  ]
}
```

### 1.1 坐标

- 清单里所有坐标是**作者自己的坐标系**里的整数方块格。`origin` 是建筑文件最小角（建筑文件内的 `(0, 0, 0)`）在作者坐标系里的位置，缺省 `[0, 0, 0]`。
- 这样作者（或 AI）始终用建造时的坐标写清单，不必在裁剪后重算。
- 导入时建筑最小角放在世界的 `at0`（新建草稿是 `DraftImport.centredOnOrigin`，贴入是建设者脚下那套算法），清单坐标 `p` 对应世界 `at0 + (p - origin)`。
- 朝向 `yaw` 是 Minecraft 的 yaw 角度（0 南、90 西、180 北、-90 东），缺省 0。只对 `point`、`model` 有意义，其他形态忽略。

### 1.2 `at` 的含义（与工坊文档 4.2 一致）

| `as` | `at` 指的是 | 标记盔甲架生成在 |
| --- | --- | --- |
| `point`、`model` | 脚所在的格（空气格） | 该格底面中心，朝向 `yaw` |
| `zone` + `box` | 方框底面中心格 | 该格底面中心 |
| `zone` + `flood` | 一块地板方块 | 它上方一格的底面中心 |
| `block`、`click`、`text` | 被绑定的方块 | 上方一格是空气时在上方一格，否则在该方块格内（与绑定杖相同，复用 `Toolkit` 里“绑定后生成”的选位逻辑，抽成可共用的方法，不要复制） |

- `shape`、`materials`、`box` 的取值规则就是 `MarkerSpec` 的构造规则（`materials` 只给 `flood`，`box` 三个数 0–64 只给 `box`）。`materials` 可省略，省略时材质就是起点方块（与手放标记相同）。
- 标记一律走 `MarkerStands.spawn`，所以和手放的标记逐项相同，后续解析、粒子、验收、发布不需要任何改动。
- 清单不支持点击范围（`interaction`）和 `text_display`；需要的话导入后在工坊里手动加。

实现偏差：
- `yaw` 对所有形态都写到盔甲架朝向上，不只是 `point`、`model`：方块类绑定的提示朝向本来就取标记 yaw（工坊文档 4.2 的实现偏差），写上不影响解析和验收。
- `box` 形状必须给 `box`（不默认 0×0×0，免得漏写变成 1×1 的框）；`materials` 除了 `MarkerSpec` 的写法检查，还要求是方块注册表里有的方块，拼错的材质在导入时就报出来。
- 选位逻辑抽成 `MarkerStands.spawnOn(level, spec, target, yaw)`，绑定杖（`Toolkit.bindBlock`）和清单共用。

### 1.3 告示牌文字

`signs` 给已有的告示牌方块写字：`front`、`back` 各 0–4 行纯文本，每行最多 64 个字符。`at` 处不是告示牌时记一条提醒并跳过，不让导入失败。文字作为纯文本组件写入（不解析 JSON、不带点击事件），不上蜡。实现时按 minecraft-knowledge 核实 26.3 写告示牌文字的 API（`SignBlockEntity`、`SignText`）。

已核实：26.3 的 `SignBlockEntity.setText(SignText, SignTextSlot)` 换掉一面并调用 `markUpdated()`（`setChanged()` 加 `sendBlockUpdated(…, 3)`）；`new SignText(messages, filteredMessages, color, glowing)` 构造时不校验行数，按 `SignText.LINES`（4）补足空行；挂式告示牌的 `HangingSignBlockEntity` 也是 `SignBlockEntity`。

实现偏差：省略 `front` 或 `back` 时那一面保持建筑文件里的文字；写成 `[]` 才清空。写入时保留该面原有的颜色和发光，不改上蜡状态。“不是告示牌”的提醒写进完成通知。

评审修正：“不是告示牌”是一条结构化的导入问题（`ImportIssue`，种类 `NOT_A_SIGN`，带清单坐标和世界坐标，见 1.6）。工坊里它照旧是完成通知里的一句提醒；无头构建把它写成报告里的一条 warning（2.4），不让构建失败。

### 1.4 `update_shapes`

为真时，全部瓦片放完之后对本次放置的每个方块做一遍邻接形状更新，让栅栏、玻璃板、墙、红石线按原版规则连上。缺省 `false`，因为地图作者有时会故意用调试棒做出“不合规”的状态，默认不能替他们改。

做法：对本次导入实际放下的每个非空气方块（各瓦片 `blocks` 列表里的格子）调用原版 `Block.updateFromNeighbourShapes(state, level, pos)`，结果不同就用 `PackPlacer.FLAGS` 写回。这是 `StructureTemplate.placeInWorld` 在 `knownShape == false` 时自己做的事；放到全部瓦片之后做，就没有跨瓦片的问题。

注意：

- **实现前按 minecraft-knowledge 核实** `Block.updateFromNeighbourShapes` 在 26.3 的签名，以及 `StructureTemplate.placeInWorld` 在非 knownShape 分支的做法，照它的顺序和标志来。
- 这一步可能把失去支撑的方块变成空气（例如悬空的火把）。统计变成空气的数量（只算本次放下的格子），大于 0 时在 `notes` 里提示“形状更新移除了 N 个失去支撑的方块”。
- 分摊到多个 tick：按瓦片一步一块，与放置的步进方式一致。

已核实：26.3 的签名是 `static BlockState Block.updateFromNeighbourShapes(BlockState, LevelAccessor, BlockPos)`，按 `UPDATE_SHAPE_ORDER` 逐面调用 `BlockState.updateShape`。`StructureTemplate.placeInWorld` 在 `knownShape == false` 时，先 `updateShapeAtEdge` 更新放置范围外紧贴的邻居，再对每个放下的方块算 `updateFromNeighbourShapes`，不同才用 `updateMode & -2 | 16` 写回，随后 `level.updateNeighborsAt`。`PackPlacer.FLAGS`（2|16）代入正好得到同一标志。

实现偏差：只做上面“逐块形状更新 + 用 `FLAGS` 写回”这一步，不做 `updateShapeAtEdge` 和 `updateNeighborsAt`。所以贴入时，建筑范围外紧贴着的已有方块不会改形状（例如范围外的旧栅栏不会和新栅栏连上）；红石保持文件里的充能，沙子之类也不会因此开始下落。没有方块的瓦片不单独占一步。

评审修正：最初的实现把整个建筑包围盒交给形状更新，贴入时会改写草稿里原有的方块（建设者故意摆的不合规栅栏被“修正”、原有的悬空火把被移除），违背了上面“默认不能替他们改”的初衷。现在只更新本次放下的格子（`BuildManifestPlacer.updateShapes(level, 瓦片键, 瓦片, 建筑范围)`），新建草稿与贴入都一样。所以贴入的栅栏会连上旁边原有的栅栏，原有的那根却保持原状，不会反过来连上新栅栏；建筑里空气位置上原有的方块也一律不动。

### 1.5 限制与错误

清单和建筑文件一样视为不可信：

- 文件 ≤ 1 MB，UTF-8；`format` 只认 1；`markers` ≤ 512，`signs` ≤ 256。
- 未知字段忽略；未知 `function`、`as` 与功能不符、`shape`／`materials`／`box` 不合规（即 `MarkerSpec` 构造会抛的情况）、坐标缺失或不是整数：**整个导入失败**，错误信息写明是第几条、哪个功能、什么问题。
- 标记和告示牌的水平位置必须落在建筑的水平范围内（竖直方向不限，只要在世界高度内）。这样它们所在的区块一定已经被本次导入加载。超出则导入失败。
- 清单不做数量验收（缺集结区之类）；那是草稿验收的事，导入后工坊照常提示。

实现偏差：
- 水平范围在读取阶段检查；世界高度在第一步放置之前用实际维度的 `getMinY()`／`getMaxY()` 检查，失败时一块方块也不放。错误信息形如“建筑清单 camp.hardrush.json 有误：第 3 条标记（【中央落点】）：at 应当是 [x, y, z] 三个整数”。
- 清单是目录或符号链接时导入失败（import 目录本身也忽略符号链接）。允许 UTF-8 BOM。

评审修正：
- **未知方块不再静默变成空气。** 26.3 的 `NbtUtils.readBlockState` 遇到注册表里没有的方块 id 返回空气，遇到方块没有的属性名或不合法的属性值直接跳过（只记一条日志）。建筑文件转换并经过 `PackTiles.upgrade` 之后、进入世界之前，`PaletteCheck` 在 IO 线程上检查瓦片调色板的每个被用到的条目：id 不在 `BuiltInRegistries.BLOCK`（用 `containsKey`，方块注册表是带默认值的，`getValue` 会答空气）、`StateDefinition.getProperty` 找不到属性名、`Property.getValue` 读不出属性值。按种类汇总格数（如“未知方块 minecraft:foo（123 格），导入后是空气”“minecraft:oak_fence 没有属性 bar（2 格），导入时忽略这个属性”），格数多的在前，最多列 20 种，其余合成一条“还有 N 种无法识别的方块状态没有列出”。每种是一条 `ImportIssue`（种类 `UNKNOWN_BLOCK`）：工坊导入（新建草稿、贴入）照常进行，写进完成通知；无头构建记为 error，不写出包（2.4）。
- 世界高度检查失败现在抛 `PackException`（经 `DraftImport.Rejected` 传出，见 1.6），与读取阶段的清单错误同一类型，无头构建据类型而不是消息文字把它归为包的问题。

### 1.6 代码结构

- 核心 `dev.hardrush.core.lobby.plan`：新增 `BuildManifest`（不可变记录：`origin`、`updateShapes`、`List<Marker>`、`List<Sign>`；`Marker(MarkerSpec spec, Cell at, float yaw)`；`Sign(Cell at, List<String> front, List<String> back)`）和限制校验。核心没有 JSON 库，所以解析放平台模块。
- 平台 `lobby/pack/imports/BuildManifestJson`：用 Minecraft 自带的 Gson 把文件读成 `BuildManifest`，仿照 `LobbyPlanJson` 的写法；`StructureImports` 或 `DraftImport.structure` 负责找同名清单。
- `DraftImport.structure`：有清单时，`Content.steps()` 在瓦片之后追加步骤——先是形状更新（每块瓦片一步，仅 `update_shapes`），最后一步生成标记并写告示牌。`Content.entry()` 取清单里第一个 `landing_central` 的世界位置，新草稿的进入点就对了。新建草稿和“贴进当前草稿”两条路径都生效。
- `ImportFolder` 现在只列出三种建筑扩展名，`.hardrush.json` 不会出现在菜单里，不用改。菜单里有清单的建筑文件，在按钮说明里加一行“带建筑清单”。
- 完成通知里说明“已按清单放置 N 个标记、写了 M 块告示牌”。

实现偏差：清单的读取放在 `DraftImport.structure` 里，先于建筑文件（清单出错时不用等大建筑读完）；放置部分在 `lobby/pack/imports/BuildManifestPlacer`（`updateShapes`、`apply`），M2 的构建套件经 `DraftImport.structure` 也走这里。`ImportFolder.Entry.hasManifest()` 给新建菜单和工具箱的贴入菜单加“带建筑清单”一行。

评审修正：
- `DraftImport.Content` 分开“说明”和“问题”：`remarks()` 是给人看的说明（转换时忽略了几个实体、形状更新移除了几个方块、按清单放了几个标记）；`issues()` 是结构化的导入问题 `ImportIssue(kind, message, world, manifest)`，`kind.failsBuild()` 决定无头构建里是 error 还是 warning（`UNKNOWN_BLOCK` 是，`NOT_A_SIGN` 不是）；`notes()` 是完成通知用的合并文字（说明在前，问题的消息在后）。无头构建只读 `remarks()` 和 `issues()`，不靠匹配 `notes()` 的文字分类。
- `Content.place` 可以抛 `PackException`。内容本身有误（读取阶段的 `PackException`：建筑文件损坏或超限、清单有误；放置时的世界高度检查）时，`DraftImport.tick` 抛 `DraftImport.Rejected`（`IllegalStateException` 的子类，工坊照旧把消息告诉导入的人）；导入超时、维度没打开之类仍是普通的 `IllegalStateException`。

### 1.7 测试

- 核心单元测试：`BuildManifest` 的限制校验、坐标换算（含非零 `origin`）。
- 平台单元测试：`BuildManifestJson` 的合法样例与每一种拒绝情况。
- gametest（加进现有的工坊套件，`TestProperties.WORKSHOP`）：用 `SampleFiles` 生成一个带栅栏和告示牌的小 `.schem` 和一份清单，导入为草稿后断言：每种 `as` 的标记都在预期位置且 `MarkerTags.parseMarker` 解析结果与清单一致；`flood` 区域解析出预期的地板格；栅栏的连接属性已更新（`update_shapes` 为假时未更新）；告示牌文字正确；清单有错时草稿被删除并给出原因。

评审修正：
- 工坊套件加一次开着 `update_shapes` 的贴入：贴入位置事先放一根故意不合规（`north=true`）的栅栏，紧挨着建筑的栅栏行，再放一支悬空的火把，两者都在建筑包围盒内、建筑的空气格上。断言原有的栅栏状态不变、原有的火把还在，贴入的栅栏连上了（最西那根也连上了原有栅栏），完成通知里只移除了建筑自己的 1 支悬空火把。
- 平台单元测试：`PaletteCheck`（未知 id、未知属性、不合法属性值按种类计格数，跨瓦片汇总，最多列 20 种）；`PackTiles.upgrade` 对旧写法调色板在改名版本前后、当前版本都能读回同一个方块状态，且从改名版本起在 DataFixer 之前就已改名。

## 2. 大厅包构建（无头）

目标：一条命令把“建筑文件 + 清单”变成 `.hrlobby`，并给出机器可读的验收报告。AI 据此改建筑或清单再跑，直到零错误。

### 2.1 源目录

仓库根新增 `lobby-packs/`，一个子目录一个示例包，目录名就是包 id：

```
lobby-packs/<id>/lobby.json            {"name": "…", "authors": ["…"], "version": 1}
lobby-packs/<id>/build.schem           或 build.litematic／build.nbt，只能有一个
lobby-packs/<id>/build.hardrush.json   建筑清单
lobby-packs/<id>/out/                  构建产物，不进版本库
```

`.gitignore` 加 `/lobby-packs/*/out/`。`<id>` 须满足 `[a-z0-9_-]{1,32}`。

### 2.2 命令

```
python3 scripts/lobby-pack.py build <id>
```

脚本负责：检查源目录；在看门狗下启动 Gradle（总时长上限 15 分钟、日志大小上限 300 MB，超限只结束本工作区启动的那个 java 进程）；结束后把报告摘要打印出来；有错误时退出码非零。实际工作由一个独立的 GameTest 套件完成：

```
./gradlew :platforms:mc263:runGameTest -PhardrushLobbyPack=<源目录绝对路径> --offline --console=plain
```

按 `build.gradle` 里其他独立套件的写法接入：自己的全新运行目录（`.local/lobby-pack/<uuid>`）、`-Dhardrush.test.lobbyPack=<路径>`、`-Dfabric-api.gametest.filter` 只跑这一个测试类；与其他 `-Phardrush*` 套件互斥。`TestProperties` 加 `LOBBY_PACK`。不带这个属性时该测试类不运行，默认回归不受影响。

实现偏差：
- 参数既可以是 id（`lobby-packs/<id>`），也可以是源目录路径（目录名仍须是合法 id），方便在版本库外试建。
- 套件不需要比赛运行时，带 `-PhardrushCompetition=true`、任何其他独立套件开关或 `-PhardrushGameTestFilter` 时 Gradle 配置阶段直接报错；`-PhardrushLobbyPack` 必须是已存在目录的绝对路径。
- 套件互斥用的开关列表与 `isolatedSuites` 写在一处：`build.gradle` 里 `isolatedSuites`（互斥的生产运行时套件）加 `otherSuites`（默认存储里按过滤器跑的套件和不参与互斥检查的独立套件）合成 `allSuites`，大厅包构建拒绝其中任何一个和 `-PhardrushCompetition=true`。新增套件只改这两个列表之一。（评审修正：原来大厅包构建这里手写了一份列表，漏了 `hardrushCombatDeparture`。）
- 脚本用 `--no-daemon` 启动 Gradle，并放进自己的进程组（`start_new_session`）：这样 Gradle、它的一次性守护进程和游戏服务端都在这个组里，超限时只对这个组发 SIGTERM（20 秒后 SIGKILL），不按名字找 java 进程。用了常驻守护进程的话，游戏服务端是守护进程的子进程，不在本次启动的组里。
- 看门狗同时看 Gradle 输出文件和运行目录下的 `logs/latest.log`（运行目录从 Gradle 打印的 “Isolated GameTest storage: …” 一行得知），各 300 MB。Gradle 完整输出写到 `.local/lobby-pack/gradle-<id>-<时间>.log`，终端只打印报告摘要。
- 开跑前删掉 `out/report.json` 和 `out/*.hrlobby`，失败的构建不会留下看起来像是新的旧报告。退出码：0 通过，1 包有错误，2 源目录有误（脚本自己的检查），3 构建工具出错（超时、超限、没写出报告、Gradle 非零退出）。

评审修正：
- 开跑前检查 `.local/server/eula.txt` 里有没有 `eula=true` 一行（`runGameTest` 只复用这份已有的接受，从不替用户接受）。没有时退出码 3，并提示先阅读 https://aka.ms/MinecraftEULA ，同意后在该文件里接受；脚本不会创建这个文件。这样新克隆的仓库不会跑到 Gradle 里才报一句看不懂的错误。
- `python3 scripts/lobby-pack.py sample <目标目录>` 现场生成一个功能齐全的最小样例源目录（`lobby.json`、`build.schem`、`build.hardrush.json`）：21×2×21 的石头场地，三块羊毛给三个 flood 区域，一排只靠 `update_shapes` 才连上的栅栏，讲台、石砖、两种宝库和一块告示牌给点击和方块类绑定，10 个展位，数据版本 5023。构建结果 `ok` 为真，没有任何问题（包括容量提醒）。目标目录名须是合法 id；目录已存在且非空时拒绝（退出码 2）。人工测试用它准备带清单的建筑文件，自测也可以复制后改坏。

### 2.3 过程

在一个临时的 Fantasy 虚空维度里（配置与草稿维度相同，见 `world/LobbyDimension`）：

1. 用 `DraftImport.structure(…, DraftImport::centredOnOrigin)` 导入建筑和清单。
2. 走发布流程：区块与实体区段预热 → `MarkerScan` 完整扫描与验收 → 逐瓦片 `PackCapture` → 安装清洗预演（得到“安装时将被移除”的提醒）→ 写包。
3. 把写出的包再走一遍 `PreparedPack.read(…, SanitizeMode.INSTALL)`，确认它能被读回（格式、限制都通过）。
4. 写 `out/report.json`，成功时写 `out/<id>-v<version>.hrlobby`。

**不要复制发布逻辑。** `PublishJob` 现在把“扫描 → 捕获 → 清洗预演 → 组装 `PackManifest` → 写文件”和“草稿、发布者、Boss 栏、作者确认”绑在一起。把前一半抽成不依赖草稿和玩家的部分（输入：维度、范围、底部高度、最大尺寸、包的 id／名字／版本／作者、输出路径；输出：问题列表、提醒、写出的文件），`PublishJob` 和构建套件都调用它。`PublishJob` 对外行为不变，现有 gametest 必须全过。

实现偏差预留：如果导入需要 `Workshop` 的草稿机制才能跑，允许构建套件直接用 `Workshop` 建一份临时草稿再发布，但同样不能复制发布逻辑。

实现偏差：
- 抽出的部分是 `lobby/pack/PackBuild`：构造时给维度、范围、底部高度、最大尺寸，逐 tick 走“区块与实体区段预热 → 分摊扫描与验收 → 逐瓦片捕获 → 安装清洗预演 → `checkTotals`”，结果是 `problems()`（扫描的全部问题，加上清洗预演的 `SANITIZED` 提醒）、`limit()`（总量超限）和 `captured()`；`Captured.manifest(id, 名字, 作者, 版本, 创建时间)` 组装 `PackManifest`，`Captured.write(路径, manifest)` 写文件。超时不归它管：`PublishJob` 保留“加载草稿区块超时 5 分钟”“等待确认 10 分钟”、作者确认和“版本号遇到同名文件就往上加”，构建套件用同样的 5 分钟加载超时。`PublishJob` 的阶段名、进度文案、提醒与错误的文字和顺序都不变。
- 导入不需要 `Workshop`：构建套件在 `lobby.workshop` 包里（gametest 源码集），直接用包内可见的 `DraftImport` 和 `Draft`。维度是 `LobbyDimension.openTemporary`，与草稿维度同一份配置，只是 Fantasy 的临时维度。
- 临时维度从不保存区块，卸载了再加载就是空的；所以套件在导入之前先把整个范围的区块（连同实体区段）加载并一直持有到捕获结束，导入和打包之间不会掉区块。
- 范围与新建建筑文件草稿完全相同（`Draft.create(…).range`：以原点为中心、边长为服务端的大厅水平上限、全部高度），没有底部高度，所以构建接受的东西和“导入这个文件再在工坊发布”一样。
- 写出的包直接覆盖 `out/` 里的同名文件（构建产物，不是包库）；读回在 IO 线程上做，读不回来时删掉文件并报错。

### 2.4 报告

```json
{
  "ok": false,
  "pack": null,
  "placement": {"structure_min": [-32, 64, -28], "manifest_origin": [4, 2, 7]},
  "bounds": {"min": [-32, 64, -28], "max": [31, 90, 27]},
  "notes": ["已按清单放置 27 个标记、写了 6 块告示牌"],
  "problems": [
    {"severity": "error", "kind": "COUNT", "function": "display_slot",
     "message": "…", "world": [3, 65, 4], "manifest": [39, 3, 39]}
  ]
}
```

- `problems` 是发布验收的全部问题（错误和警告），加上清洗预演的提醒（`severity: "warning"`）。每条同时给世界坐标和换算回清单坐标系的位置（`manifest = world - structure_min + manifest_origin`），没有位置的问题两者都省略。
- 导入阶段就失败（清单有错、文件超限）时，`ok` 为假，`problems` 里只有那一条错误。
- `ok` 为真当且仅当没有错误并且包已写出；此时 `pack` 是产物的相对路径。
- 测试方法本身只在基础设施出问题时失败（维度打不开、超时）；包有验收错误不算测试失败，由 `scripts/lobby-pack.py` 读报告决定退出码。这样 Gradle 输出里不会把“包还没建好”混同于“工具坏了”。

实现偏差：
- `kind` 除了 `ProblemKind` 的名字，还有四个只出现在报告里的值：`SOURCE`（源目录或 `lobby.json` 有误，在导入前就停下）、`IMPORT`（导入失败，包括清单有误、文件超限和导入自己的超时）、`LIMIT`（方块实体或实体总数超限）、`PACK`（写文件失败或写出的包读不回来）。前两种出现时 `problems` 只有那一条，`placement` 和 `bounds` 为 `null`。清洗预演的提醒是 `kind: "SANITIZED"`，没有 `function`。

评审修正：
- `IMPORT` 只用于包本身的问题：`DraftImport.Rejected`，即 `PackException`（建筑文件损坏或超限、清单的读取和校验错误、清单的世界高度检查）。导入超时、维度没打开等其他异常是构建工具的故障：测试失败，`scripts/lobby-pack.py` 退出码 3。原来的写法把导入阶段的所有异常都记成 `IMPORT`。
- 导入问题（1.6 的 `ImportIssue`）按种类名写进 `problems`，排在发布验收的问题之前：`UNKNOWN_BLOCK`（未知方块 id、属性名或属性值，每种一条，error：`ok` 为假、不写出包，但扫描和验收照常做完，其他问题和 `bounds` 一并给出）；`NOT_A_SIGN`（清单的告示牌条目处不是告示牌，warning，同时给 `world` 和 `manifest`）。`notes` 只放说明（`remarks()`），不重复这些问题。
- `lobby.json` 的 `authors` 可以省略（视为空）；`version` 必须是整数。id、名字、作者数、版本号用 `PackManifest.problems` 的同一套规则在导入前检查。
- `bounds` 是扫描得到的包范围，扫描找到内容时就有（即使有验收错误）。报告用 Gson 带 `null` 字段输出，原子写入。
- 测试失败的情况：临时维度打不开、5 分钟内区块加载不完或区块加载出错、报告写不出来。

## 实现中发现并修掉的既有问题

- **26.3 的调色板字段改名**。结构瓦片的调色板条目在 26.3（数据版本 5006 起）从 `{Name, Properties}` 改成了 `{id, properties}`，游戏只认新名字。两处受影响：
  - `TileSanitizer` 的方块黑名单读的是 `Name`，对 26.3 发布的大厅包完全不生效（命令方块、刷怪笼等不会被去掉）；单元测试用的也是旧字段，所以一直是绿的。
  - `imports.StateEntry` 写旧字段，建筑文件的数据版本已经是当前版本时不会经过 DataFixer，导入后整栋建筑是空气。
- 修法：`PackTiles.upgrade` 在 DataFixer 之后把调色板统一成新字段（`canonicalPalettes`），黑名单经 `PackTiles.blockName` 读取并兼容两种写法；测试夹具改用 26.3 的真实写法，并加了旧写法的回归测试。
- 评审修正：数据版本在改名版本（5006，原版 `NbtUtils.BLOCK_STATE_ID_PROPERTIES_RENAME_VERSION`，private，所以 `PackTiles.PALETTE_RENAME_VERSION` 自己定义并注明出处）与当前版本之间、却仍写旧字段名的瓦片（`imports.StateEntry` 转换出来的就是这样），DataFixer 不会再替它改名，改名之后的修正又只认新字段名。所以 `PackTiles.upgrade` 在调用 DataFixer 之前，`fromDataVersion` ≥ 5006 时先做一次 `canonicalPalettes`（之后那次保留，兜住 5006 之前的文件）。26.3 里 5006 之后暂时没有改调色板的修正，所以这是潜伏问题，不是现有 bug。
- 宝库方块实体被清掉 `config` 等字段时不再计入“清空容器”，否则每个合格大厅发布时都会有一条无意义的提醒。
