# 大厅包与工坊

2026-11-13 与需求方讨论定稿。状态：已实现（2026-11-15），待人工客户端测试（见 `docs/人工客户端测试/2026-11-03-营地改版与怪物新玩法.md` 第七段）。

实现时如与本文不一致，在对应小节末尾用“实现偏差：”写明原因，不要悄悄改方案。

## 背景

粉丝愿意帮忙建设准备大厅，但现在大厅的建筑和功能都写在代码里：

- `core/.../lobby/LobbyLayout.java`：设施、落点、集结圈、怪物庭院全是相对出生点的 2D 常量，没有 Y，做不了多层。
- `platforms/mc263/.../world/CampBlueprint.java`：逐块生成建筑。
- `platforms/mc263/.../world/LobbyWorld.java`：超平坦维度 + “只认自己铺的方块”的清单校验 + 旧版迁移。
- `ProtectionRuntime` 把大厅维度整体封死，没有“建设者”身份。
- `LobbyInteractions.registerBlock` 只接受讲台、告示牌、宝库三种方块。

目标：把“建设 → 绑定功能 → 打包 → 分发 → 安装”做成 HardRush 正式提供的服务端能力，其他服主装上模组就能用，全程原版客户端。

参考过的同类做法：

- 起床战争插件（Screaming BedWars、BedWars1058）：管理员站到位置上敲命令设点，坐标存配置，地图另存。学它“人在哪设在哪”和“保存时检查最低要求”；不学它“配置和地图分离”。
- Nucleoid Creator Tools（与本项目使用的 Fantasy 同一团队）：独立工作区维度里建，导出为单个文件，方块和区域都在里面。本方案结构与它一致。

## 1. 需求定稿

| 项 | 结论 |
| --- | --- |
| 建设地点 | 正式服上的工坊维度，与正式大厅隔离 |
| 何时能建 | 本轮处于 `PREPARING`／`WAITING`／`COUNTDOWN` 时。进入 `RUNNING` 等其他阶段时，工坊里的人被送回大厅，草稿保留 |
| 权限 | 2 级 OP：新建草稿、进入工坊、搭建、绑定。4 级 OP：发布、安装、回滚、删除草稿 |
| 客户端 | 只要求原版客户端。工具全部是原版物品和箱子菜单 |
| 自由度 | 同一功能可放多个；点击类功能可绑到任意方块或实体；只有宝库和祭坛光柱限定方块类型 |
| 初始草稿 | 没有任何草稿时，自动从当前已安装的大厅生成一份 |
| 互动装饰 | 开放门、活板门、栅栏门、按钮、拉杆、压力板、音符盒、钟及红石信号传递；活塞、容器、破坏保持封锁 |
| 版本兼容 | 大厅包缺少新版模组的必需功能时，自动在中央落点旁放“临时设施” |
| 分发 | 面向陌生服主公开分享，导入时必须清洗 |
| 切换 | 只在 `PREPARING`／`WAITING` 时安装；大厅里的人传送到新大厅中央落点；可回滚到上一个 |
| 默认大厅 | 现有代码生成的营地原样转成大厅包，打进 jar |
| 新功能 | 本期做署名牌；名人堂、排行榜另记 Issue |
| 大小 | 水平上限 256×256（`hardrush.lobby.maxSize`，64–512），高度不限 |
| 已有建筑 | 可以把已有存档、`.nbt`／`.schem`／`.litematic` 建筑文件导入为草稿，见第 19 节 |

本期不做：多个大厅轮换、大厅包自带时间天气、工坊内完整试玩设施逻辑（只提供步行预览）、建设者背包跨会话保存。

## 2. 总体模型

三个概念，一条单向流：

```
草稿（工坊维度，可编辑） ──发布──▶ 大厅包（文件，唯一真相） ──安装──▶ 正式大厅（维度，只读的一次性实例）
        ▲                                   │
        └──────────── 导入为草稿 ◀───────────┘
```

- **大厅包是唯一真相**。正式大厅不允许就地修改，所有改动都走“草稿 → 发布 → 安装”。因此不再需要“方块所有权清单”这类机制。
- **所有坐标都是世界绝对坐标**，工坊、大厅包、正式大厅三者一一对应，没有任何平移或旋转。
- 模组自带的默认大厅是 jar 里的一个大厅包，与服主自己的包走同一条安装路径。

## 3. 功能目录

核心新增枚举 `core/.../lobby/LobbyFunction`，取代 `LobbyLayout.Facility`、`Landing` 和各区域常量。

| id | 名称 | 绑定形态 | 数量 | 必需 | 缺失时的临时设施 |
| --- | --- | --- | --- | --- | --- |
| `assembly` | 集结区 | 区域 | ≥1 | 是 | 无（发布时强制） |
| `courtyard` | 怪物庭院 | 区域 | ≥1 | 是 | 无（发布时强制） |
| `altar_pad` | 祭坛踏板 | 区域 | ≥1 | 是 | 无（发布时强制） |
| `altar_light` | 祭坛光柱 | 方块，限 `tinted_glass` | 0–4 | 否 | — |
| `landing_central` | 中央落点 | 点 | 1–16 | 是 | 无（发布时强制） |
| `landing_monster` | 庭院落点 | 点 | 1–16 | 是 | 无（发布时强制） |
| `landing_altar` | 祭坛落点 | 点 | 0–16 | 否 | 用庭院落点 |
| `display_slot` | 追猎目标展位 | 点 | 1–60 | 是 | 无（发布时强制） |
| `rules` | 规则 | 点击 | ≥1 | 是 | 讲台 |
| `history` | 战绩 | 点击 | ≥1 | 是 | 讲台 |
| `role_zombie`／`role_skeleton`／`role_creeper` | 角色展位 | 模型 或 点击 | ≥1 | 是 | 模型 |

| `vault`／`ominous_vault` | 试炼宝库／不祥宝库 | 方块，限 `vault` 且 `ominous` 属性匹配 | ≥1 | 是 | 宝库方块 |
| `page_prev`／`page_next` | 展位翻页 | 点击 | ≥1 | 是 | 告示牌 |
| `status` | 状态牌 | 文字 | 0–8 | 否 | — |
| `credits` | 署名牌 | 文字 | 0–8 | 否 | — |

绑定形态：

- **点**：一个位置加朝向。
- **模型**：一个位置加朝向，运行时模组在这里发数据包模型（僵尸、骷髅、苦力怕、女巫），沿用 `LobbyRoleModels`。
- **点击**：右键触发。可以是方块（任意方块），也可以是实体（任意带标签的实体，见 4.3）。
- **方块**：特定类型的方块。
- **区域**：玩家站进去生效，见第 5 节。
- **文字**：告示牌方块或 `text_display` 实体，内容由模组写入。

规则：

- 以后新增必需功能时，必须同时在枚举里声明临时设施形态。加一个单元测试遍历枚举，断言“必需且非发布时强制”的功能都有临时设施，并断言 jar 内默认大厅包包含全部必需功能。
- `WAIT_OUTSIDE` 落点删除，原用途（`HumanEntry` 恢复准备落点不安全时的退路）改用中央落点。
- `RESTORE_READY` 落点不再单独标记：取集结区内离区域中心最近的安全站立格。
- 追猎目标展位的顺序按 `(y, z, x)` 升序，容量等于标记数量，替代 `LobbyLayout.DISPLAY_CAPACITY`。少于 10 个时验收给警告。
- 原来随阶段改写的展位告示牌（`LobbyWorld.huntLabels`）删除。“极限挑战时开放”改为显示在角色模型的名牌上；翻页和其他说明牌由建设者自己写成普通告示牌。靠近设施时的动作栏提示（`PlayerFeedback.facilityTip`）保留，改为按 `LobbyFunction` 取文案。

实现偏差（M1）：

- 落点用途不是 `LobbyFunction`，而是核心里独立的小枚举 `dev.hardrush.core.lobby.plan.Landing`（`CENTRAL`、`MONSTER`、`ALTAR`、`RESTORE_READY`），`placeInLobby`／`endObservation` 收它。原因：“恢复准备”没有自己的标记，是从集结区推出来的，不是一个可绑定的功能。候选落点与散布规则在 `LandingRules`：`ALTAR` 没有祭坛落点时退回庭院落点；`RESTORE_READY` 取每块集结区地板里离区域中心最近的 9 格的站立点。方框集结区同样产生候选（评审修正）：方框内每列、脚在 `min.y..max.y` 的每一层都是站立点，取离方框中心（底面中心）最近的 9 个；不枚举整个方框，而是从中心向外扩一个立方体，直到里面有 9 个不超过其半宽的点，大方框也只算几十个点。原实现跳过方框，只用方框做集结区的大厅倒计时重启后找不到恢复落点。同一用途有多个候选时，每次放置轮流换一个，跳过不安全的。
- 散布规则改为对 plan 的通用几何判断，与旧的手写常量略有差别：中央落点离集结区每一格地板的水平距离都要大于 2（旧规则是离圆心大于 8.5）；庭院落点可以落在庭院区域的边缘格上；所有比较只看与站立格高度差不超过 2 的东西，适应多层大厅。
- 集结区判定改为 `Zone.Floor`：进入看身体中心是否在某格地板上方，停留看碰撞箱任一角。旧实现是“离圆心 6.85／7.35 格以内且脚下站得住”，现在以羊毛格为准，不再单独检查脚下方块。
- `LobbyRoleModels.view` 改为返回“功能 → 模型实体 ID 列表”，因为同一功能可以有多个模型。
- 过渡期内置营地的说明牌改成固定文字（例如僵尸展位“右键模型选角／挑战时右键目标追猎”，翻页“右键翻页／只对自己生效”）；已有存档里的旧告示牌不会自动改写。

## 4. 标记

功能绑定存在工坊世界里的**标记盔甲架**上，随建筑一起保存、一起被结构方块或 WorldEdit 复制。选盔甲架是因为它是地图作者用了很多年的习惯做法：有名牌能看见，创造模式打一下就删，朝向就是放下时面对玩家的方向。

### 4.1 标记盔甲架

属性：`Small:1b`、`NoGravity:1b`、`NoBasePlate:1b`、`CustomNameVisible:1b`，`CustomName` 为“【集结区】”这类中文名，头上戴一个代表该功能的物品（如僵尸头、书）。

数据全部放在实体的记分板标签（`Entity.entityTags()`／`addTag`）里，纯字符串，OP 用 `/tag` 也能查看和修改：

| 标签 | 含义 |
| --- | --- |
| `hardrush.marker` | 这是标记盔甲架。安装到正式大厅时会被剔除 |
| `hardrush.fn.<id>` | 功能，`<id>` 为第 3 节的 id。有且只有一个 |
| `hardrush.as.point`／`.model`／`.block`／`.zone`／`.text` | 绑定形态。有且只有一个 |
| `hardrush.shape.flood`／`hardrush.shape.box` | 区域形状，仅区域标记 |
| `hardrush.mat.<命名空间>+<路径>` | 连片区域的材质，如 `hardrush.mat.minecraft+lime_wool`。可多个。用 `+` 代替冒号，因为 `/tag` 的参数不接受冒号 |
| `hardrush.box.<x>.<y>.<z>` | 方框区域的尺寸，整数 0–64 |

解析与格式化写成核心里的纯函数 `MarkerTags.parse(Set<String>) → MarkerSpec | 错误`，单元测试覆盖。

实现偏差（`MarkerStands`）：
- 生成标记（`spawn`）和工具箱的标记物品（`item`，`minecraft:entity_data` 组件）共用同一份实体数据，并都走原版 `TypedEntityData.loadInto`（`ArmorStandItem` 放置时也走它），gametest 断言两种来源的标签和各项属性一致。
- 另加 `DisabledSlots`（全部槽位），头上的功能图标不能被取下或替换；盔甲架本身原版就不可被推动（`ArmorStand.isPushable` 恒为 false）。
- 头戴图标：集结区绿色羊毛（lime）、怪物庭院腐肉、祭坛踏板哭泣的黑曜石、祭坛光柱遮光玻璃、中央落点指南针、庭院落点追溯指针、祭坛落点磁石、展位盔甲架、规则书、战绩书与笔、三种角色对应头颅、商人药水、宝库试炼钥匙、不祥宝库不祥试炼钥匙、上一页箭、下一页光灵箭、状态牌橡木告示牌、署名牌命名牌。

### 4.2 位置规则

- **点、模型**：位置取盔甲架脚底坐标，朝向取盔甲架 yaw。
- **方块、文字、方块点击**：目标方块 = 盔甲架所在格的方块；如果那一格是空气，则取正下方一格。所以把标记放在讲台顶上就是绑定这个讲台。
- **区域**：见第 5 节。

实现偏差（`MarkerScan`）：方块类绑定的提示位置（`Trigger.anchor`、告示牌 `TextSlot.anchor`）取目标方块顶面中心，朝向取标记 yaw；文字功能的实体触发器只认 `text_display`，绑在其他实体上报标记错误。

### 4.3 实体触发器

任何**非标记**实体只要带 `hardrush.fn.<id>` 标签（且该功能支持“点击”），在正式大厅里右键它就触发该功能。安装时这类实体保留。

文字类功能（`status`、`credits`）同理：给一个 `text_display` 实体打上标签，模组就把内容写进它。

典型用法：建设者用展示实体拼了一个雕像，再在外面放一个 `interaction` 实体当点击范围，给它打标签。盔甲架雕像、物品展示框也可以直接打标签。

实现说明（M4）：右键实体是 `ServerboundInteractPacket`（`interaction` 实体 `isPickable` 为真，原版客户端会发），左键是另一个包 `ServerboundAttackPacket`，不触发、由保护拦截。只认主手；距离按玩家眼睛到实体碰撞箱最近点算，仍是 5 格。触发时不查 plan 里有没有这条实体触发器，只看实体标签，宝库（方块绑定）不能用实体触发。`text_display` 的文字每秒按标签比对一次，有差异才写，新加载的实体也会被补写。署名牌内容由核心 `LobbyCredits` 生成：告示牌四行是“大厅：名字”“v版本”“建设者：A、B”“续行”，宽度按每行 90 像素估算（中日韩字 9、其他 6），名字放不下以“…”截断，建设者放不下以“等”结尾；`text_display` 是“大厅：名字 v版本\n建设者：全部”。状态牌的 `text_display` 显示与告示牌相同的四行。

### 4.4 工具

进入工坊时发放，全部是原版物品加自定义数据：

1. **工具箱**（放在快捷栏第 9 格的箱子物品）：右键打开箱子菜单，分类列出所有标记物品，点击领取。菜单里还有验收清单、步行预览开关、离开工坊。
2. **标记物品**：预置了 `minecraft:entity_data` 组件的盔甲架物品。直接用原版方式放置，不需要模组写放置逻辑。
3. **绑定杖**（带自定义数据的木棍）：
   - 右键方块：菜单选择“把这个方块绑定为…”，模组在目标格上方生成标记；上方放不下时生成在目标格内。也可选“在这里创建点击范围”，生成一个 `interaction` 实体（提供 1×1、1×2、2×2、3×3 几种尺寸）。
   - 右键非标记实体：菜单选择功能，给实体加 `hardrush.fn.<id>` 标签；再次右键可移除。
4. **右键标记盔甲架**（拦截原版的“给盔甲架穿装备”）：
   - 连片区域标记：手持方块物品右键 = 添加或移除一种材质。
   - 方框区域标记：空手右键打开菜单，调整宽、高、深。
   - 其他标记：显示这个标记的说明。
5. 删除标记：创造模式打掉盔甲架。打掉被绑定的方块时，模组顺带移除它上面的标记。

### 4.5 让建设者看见

每 10 tick，对每个建设者 32 格内的标记：

- 区域标记：在解析出的地板格顶面或方框边线上发粒子。连片区域每 20 tick 重新解析一次。
- 方块标记：在目标方块外轮廓发粒子。
- 验收有问题的标记换一种颜色的粒子。

粒子只发给工坊里的玩家（`ServerLevel.sendParticles(player, ...)`）。

实现偏差（M3b，工具与显示）：
- 代码：`lobby/workshop/Toolkit`（物品、网络入口、标记编辑、绑定后生成）、`ToolboxMenu`（工具箱箱子）、`WandMenus`（绑定杖与方框尺寸菜单）、`MarkerView`（粒子）；网络拦截是 `player/mixin/WorkshopToolMixin`（`handleUseItem`／`handleUseItemOn`／`handleInteract` 的 HEAD，优先级 900，只对站在自己草稿里的建设者生效）。主手拿着工具时，紧随其后的副手包也一并吞掉，避免副手物品被放下；对标记盔甲架的任何交互都被吞掉，所以原版的装备交换不会发生。
- 进入工坊时快捷栏第 9 格是工具箱、第 8 格是绑定杖；工具箱菜单另有“领取绑定杖”。工具箱丢失 10 tick 后补回第 9 格（不是下一 tick：创造背包里挪动物品时服务端会短暂看不到它）；建设者 16 格内带工具数据的掉落物每 tick 清除；打开的其他容器里的工具箱被取回；多余的工具箱删掉。
- 绑定杖生成的标记朝向建设者（按 45° 取整，与原版放盔甲架一致）；`interaction` 点击范围带 `response:1b`。绑定杖点到标记盔甲架时按“右键标记”处理。“方框区域”菜单调整的是标签里的三个数（宽、深向两边各延伸，高从脚下往上），按钮标签显示换算后的实际宽 2n+1、高 n+1、深 2n+1。
- 空讲台会自己消费右键，要把标记物品放到空讲台上需要潜行右键（原版行为）；用绑定杖点讲台更直接。
- 工具箱菜单的辅助功能（范围中心、±16 直径、底部高度、清除生物、贴入建筑文件）都在主页；范围直径下限 16。
- 粒子：区域绿色、方块类蓝色（目标方块轮廓，0.25 格一点）、点／模型黄色（脚下一点）、验收有问题的标记红色；每人每次最多 400 个，先近的标记、标记内先近的点。连片区域的格子按标记缓存 20 tick，只在已加载区块里搜索。
- 标记被打掉的方块带走：监听 Fabric `PlayerBlockBreakEvents.AFTER`，只移除点击／方块／文字类标记（站在被打掉的格里，或站在它上方一格且那格是空气）。

## 5. 区域

两种形状，同一功能可以放多个，取并集。

**连片区域（`flood`）**：把标记放在地板上。从标记正下方的方块出发，在同一 Y 层按四邻接向外扩，凡是材质属于该标记材质集合的方块都算区域地板。材质集合 = 起点方块的类型 + `hardrush.mat.*` 标签。上限 4096 格，超出报验收错误。直觉是“这片绿羊毛就是集结区”。

**方框区域（`box`）**：以标记所在格为底面中心，水平方向各延伸 `x`、`z` 格，向上 `y` 格。用于地板材质与周围相同的地方，例如默认大厅的怪物庭院。

判定（写成核心纯函数 `Zone.contains(x, y, z, staying)`，替代 `LobbyLayout.Circle`／`Box` 和 `LobbyWorld.inAssembly`／`onAltar` 里的几何部分）：

- 连片区域：玩家脚下 `(floor(x), floor(z))` 列存在地板格 `cy`，且 `cy ≤ y ≤ cy + 2.5`（兼容半砖、地毯和跳跃）。
- 方框区域：玩家坐标在方框内。
- 滞回：`staying = false`（进入）用玩家中心点判定；`staying = true`（保持）时玩家碰撞箱四角（±0.3）任一满足即可。替代现在 `+0.35／-0.15` 的半径滞回。

发布时把连片区域解析成具体格子写进大厅包，运行时不再做搜索。

祭坛的粒子、音效、指引光柱位置取玩家所在祭坛区域的几何中心。

实现偏差：`Zone.Floor` 写成 final class 而不是 record，因为它要持有按列的地板索引（`contains` 每 tick 会被每个玩家调用多次），record 不能有额外实例字段；相等性仍只看地板格集合。

重叠判定与上面的命中范围一致（评审修正）：连片区域与方框重叠，当且仅当方框水平覆盖某个地板格所在列，且方框的竖直区间 `[min.y, max.y + 1)` 与该格的 `[cy, cy + 2.5]` 相交；例如地板在 Y64 时，从 Y66 开始的方框算重叠，从 Y67 开始的不算。两块连片区域在同一列 `|Δy| ≤ 2` 即重叠，这正是 `[a, a + 2.5]` 与 `[b, b + 2.5]` 相交的整数形式。原实现只取地板上方一格的点，漏掉了玩家跳起时同时命中两区的情况。

## 6. LobbyPlan

核心新增不可变记录 `LobbyPlan`，是运行时唯一的布局来源，取代 `LobbyLayout` 的全部静态成员。核心模块不依赖 Minecraft，自带 `Cell(int x, y, z)`、`Point(double x, y, z, float yaw)`、`Box(Cell min, Cell max)`。

```java
record LobbyPlan(
    Box bounds,
    List<Trigger> triggers,          // 点击与方块类：function、目标方块 Cell（实体触发器为 null）、方块 id、提示用位置 Point
    List<Model> models,              // function、Point
    Map<LobbyFunction, List<Point>> points,   // 各类落点、display_slot
    Map<LobbyFunction, List<Region>> zones,   // Region = 地板格集合 或 Box
    List<Cell> altarLights,
    List<TextSlot> texts)            // function、告示牌 Cell 或 null（text_display 实体靠标签在运行时查找）
```

配套：

- `LobbyPlanValidator`（核心，纯函数）：检查数量规则，返回 `List<Problem>`，每个问题带级别（错误／警告）、功能、位置、中文说明。
- `LobbyPlanJson`（平台模块，用 Minecraft 自带的 Gson；核心没有 JSON 库）：与 `pack.json` 的 `plan` 字段互转。
- `LobbyWorld` 持有当前 `LobbyPlan`，对外提供按功能查询的方法（落点、区域判定、最近设施）。所有调用方从这里取，不再引用静态常量。

## 7. 大厅包格式

单个 zip 文件，扩展名 `.hrlobby`：

```
pack.json
tiles/<tx>_<ty>_<tz>.nbt      每块 48×48×48 的原版结构模板（gzip NBT）
```

- 瓦片索引 = `floorDiv(世界坐标, 48)`，全空的瓦片不写。48 是原版结构方块的单轴上限，所以每块瓦片也能用原版结构方块加载。
- 用原版 `StructureTemplate` 是为了白拿三样东西：方块实体和实体的存取、跨版本升级（DataFixer）、久经验证的放置代码。分块是为了控制内存和分摊到多个 tick。

`pack.json`：

```json
{
  "format": 1,
  "id": "default",
  "name": "默认营地",
  "authors": ["LeifWebber"],
  "version": 3,
  "created": "2026-11-13T08:00:00Z",
  "mod_version": "…",
  "data_version": 0,
  "bounds": {"min": [-24, 63, -16], "max": [39, 70, 31]},
  "plan": { }
}
```

- `id`：`[a-z0-9_-]{1,32}`，等于草稿 id。`version`：每次发布加一。文件名 `<id>-v<version>.hrlobby`。
- `authors`：进入过该草稿的建设者（记在 `draft.json` 的参与者里），4 级 OP 发布时可在菜单里确认或删减。
- `data_version`：发布时的游戏数据版本。

`plan` 字段（`LobbyPlanJson`，平台模块 `lobby/pack`）。范围只写在顶层 `bounds`，`plan` 里不重复；功能写 `LobbyFunction.id()`，坐标 `[x, y, z]`，点 `[x, y, z, 朝向]`：

```json
"plan": {
  "triggers": [
    {"function": "rules", "block": [1, 64, 2], "block_id": "minecraft:lectern", "anchor": [1.5, 65.0, 2.5, 0.0]},
    {"function": "history", "anchor": [-3.25, 64.0, 7.75, -90.5]}
  ],
  "models": [{"function": "role_zombie", "point": [10.5, 64.0, -3.5, 45.0]}],
  "points": {"landing_central": [[0.5, 64.0, 0.5, 0.0]], "display_slot": [[1.0, 65.0, 3.0, 0.0]]},
  "zones": {
    "assembly": [{"type": "floor", "cells": [[0, 63, -1], [0, 63, 0], [1, 63, 0]]}],
    "courtyard": [{"type": "box", "min": [25, 64, 5], "max": [35, 68, 15]}]
  },
  "altar_lights": [[-6, 64, -5]],
  "texts": [{"function": "status", "sign": [2, 65, 2], "anchor": [2.5, 65.0, 2.5, 0.0]},
            {"function": "credits", "anchor": [-1.0, 66.0, -1.0, 270.0]}]
}
```

- 没有 `block`／`block_id` 的触发器是实体触发器；没有 `sign` 的文字位是 `text_display`。两者都靠标签在运行时查找。
- `points`、`zones` 的键按功能目录顺序写出，`display_slot` 按 (y, z, x) 排序，连片区域的格子按 (y, z, x) 排序；缩进两格，纯数字数组写在一行。同样的 plan 产出逐字相同的文本。
- 读取时未知功能 id、未知区域类型、绑定形态与功能不符都拒绝；单个连片区域格子 ≤ 16384，其他每个数组 ≤ 4096。

实现偏差：
- zip 条目时间戳固定为 DOS 纪元 1980-01-01 而不是 0（Java 对 1980 年前的时间会额外写扩展时间戳字段），效果同样是同内容同字节。
- 瓦片条目用 STORED 存放（瓦片本身已经是 gzip，避免二次压缩），`pack.json` 用 DEFLATED。
- 读取时还拒绝：同一瓦片的非规范写法（`-0`、前导零、`+`）、不与 `bounds` 相交的瓦片、缺少或重复的 `pack.json`、非 UTF-8 的 `pack.json`。
- `PackCapture` 捕获时删除实体的 `UUID`（放置时原版本来就会删），否则每次发布同一建筑都会因随机 UUID 得到不同的字节。
- `bounds` 必须整个落在世界范围内：水平 |x|、|z| ≤ 30,000,000（`Level.MAX_LEVEL_SIZE`），竖直 −2032..2031（26.3 的 `DimensionType.MIN_Y..MAX_Y`，不是 −2048..2047）。`Box` 的尺寸按 `long` 计算：评审发现 `min.x = Integer.MIN_VALUE, max.x = Integer.MAX_VALUE` 时 `int` 尺寸溢出为 0，能通过水平上限。瓦片与 `bounds` 相交改为比较瓦片索引，不再构造可能溢出的瓦片方框。`ChunkWarmup` 另有兜底：一次最多 33×33 个区块（按可配置的最大大厅 512 计算），超过就抛异常，即使上游漏检也不会在主线程建出巨大的加载队列。

读取限制（防恶意文件）：条目名只接受 `pack.json` 和 `tiles/-?\d+_-?\d+_-?\d+\.nbt`；条目数 ≤ 4096；`pack.json` ≤ 1 MB；单个瓦片解压后 ≤ 16 MB（`NbtAccounter`；一块填满的瓦片约 11 万个方块，带地形的存档导入后会出现这种瓦片）；总解压量 ≤ 1 GB；`bounds` 水平跨度 ≤ `hardrush.lobby.maxSize`；`data_version` 高于服务端时拒绝；`format` 不认识时拒绝。全程在内存里按条目读，不按条目名落盘。

## 8. 清洗

所有从大厅包进入世界的路径（安装到正式大厅、导入为草稿）都经过同一个 `TileSanitizer`，在 DataFixer 升级之后、`StructureTemplate.load` 之前对 NBT 操作。

1. **方块黑名单**，替换为空气：命令方块三种、结构方块、拼图方块、测试方块、刷怪笼、试炼刷怪笼、末地传送门、末地折跃门、幽匿尖啸体、`moving_piston`。
2. **方块实体**：清空所有容器的物品（`Items`、`item`、`RecordItem`、`Book` 等）；告示牌的八行文字剔除 `click_event`、`hover_event`、`insertion`，并把 `selector`／`score`／`nbt` 类文本组件替换为空文本。告示牌点击命令是以 2 级权限执行的，这是最主要的风险。
3. **实体白名单**：`armor_stand`、`item_frame`、`glow_item_frame`、`painting`、`block_display`、`item_display`、`text_display`、`interaction`。其余丢弃。保留的实体同样清洗文本组件，并清掉 `Passengers`。
4. **数量上限**：方块实体 ≤ 4096，实体 ≤ 1024。超出则拒绝整个包。
5. 安装到正式大厅时额外剔除带 `hardrush.marker` 的实体；导入为草稿时保留。

发布时不清洗输出，但验收会列出“安装时将被移除”的内容作为警告。

实现偏差（`TileSanitizer`，按架构师补充决定）：
- 黑名单另加 `nether_portal`、`barrier`；黑名单方块从 `blocks` 删除（新维度里即空气），`palette` 与 `palettes` 两种形态都处理。
- 方块实体还删除 `LootTable`、`LootTableSeed`、`bees`、`flower_pos`；宝库删除 `config`、`server_data`、`shared_data`（奖励由 `MonsterVaults` 发）；方块实体的 `components` 按与实体物品相同的组件白名单裁剪。
- 26.3 的告示牌有 `allow_op_features` 标志，为真时点击事件才会以 OP 权限执行、选择器才会被解析；旧存档的告示牌被 DataFixer（`SignsOpFlagFix`）升级时会带上它。清洗时一律删除。
- 保留实体的物品（盔甲架 `equipment` 各槽、物品展示框 `Item`、`item_display` 的 `item`）只留 `id`、`count` 和外观类组件白名单。
- 额外的几何检查：`size` 每轴夹到 0–48；`pos` 不在瓦片内的方块、`blockPos` 不在瓦片内或 `pos` 偏出瓦片 1 格以上的实体直接删除，防止恶意瓦片把内容放到范围之外。
- 实体 `UUID` 不删：`StructureTemplate` 放置实体时会自己删掉 `UUID`。
- `removedIds` 只列因不安全被删的方块和实体；安装时剔除的标记盔甲架计入 `removedEntities`，不列名。

## 9. 验收

发布前和安装前各做一次，规则相同，输出 `List<Problem>`。有错误不能发布；安装时除“缺少必需功能”走临时设施外，其余错误拒绝安装并保留当前大厅。

- 数量：第 3 节表格的上下限。
- 标记：每个标记的标签能解析；绑定形态是该功能允许的；没有无法识别的 `hardrush.*` 标签。
- 方块：目标方块非空气；`vault`／`ominous_vault` 的方块类型和 `ominous` 属性匹配；`altar_light` 是 `tinted_glass`；`status`／`credits` 的方块是告示牌。
- 点和模型：脚下有实心方块，身体两格不被阻挡（复用 `RoundWorldBundle.safeStanding`）。
- 区域：非空；至少有一格能站人；`assembly` 与 `altar_pad`、`courtyard` 互不重叠；落点不在 `assembly` 和 `altar_pad` 内。
- 范围：全部内容在世界边界内。
- 警告：`display_slot` 少于 10 个；存在将被清洗的内容。

工坊里每 40 tick 对当前草稿做一次轻量验收（只看已加载的标记），结果显示在工具箱菜单的清单里，并用 Boss 栏（走现有 `notice.StatusBars`）提示“还缺 N 项”。

实现偏差（M3b，轻量验收）：`MarkerScan.preview` 与发布用同一套解析和 `LobbyPlanValidator`，但不扫方块：只取已加载的标记与触发器，连片区域遇到未加载区块就停，不替它加载任何区块；没有方块就没有真实的内容范围，所以范围类问题（`BOUNDS`）留给发布时的完整扫描。选这个方案而不是按区块增量扫描方块：256×256 的草稿不会整片加载，建设者附近本来就加载着，轻量验收不该再加载别处。代价是远处角落里绑定的功能在没人过去时会显示为缺失，菜单里写明“只统计附近已加载区域”。代码在 `lobby/workshop/WorkshopChecks`，Boss 栏用新增的 `StatusBars.Slot.WORKSHOP`（在 `PACT` 之后、`LOBBY_INSTALL` 之前），“还缺 N 项”的 N 是错误条数。验收清单每条问题一个按钮（功能图标、说明、位置），点击传送到问题位置上方 2 格。轻量验收看到的第一个中央落点写进 `draft.json` 的 `entry`，此后建设者从那里进入（11.2 的进入点）。

## 10. 安装、切换与存储

### 10.1 存储布局（世界根目录下）

```
hardrush/lobby/packs/*.hrlobby        大厅包库。服主把别人的包放这里，发布也写到这里
hardrush/lobby/installed/<seq>.hrlobby 当前与上一个已安装包的副本，用于回滚和“从当前大厅开始草稿”
hardrush/lobby/current.json           当前安装：seq、维度、包的 id／name／version／authors／sha256、生效 plan、状态
hardrush/workshop/<draftId>/draft.json 草稿元数据：id、name、来源包、参与者、已发布版本号
```

维度：正式大厅 `hardrush:lobby_<seq>`，草稿 `hardrush:workshop_<draftId>`。全部是 Fantasy 持久维度，`VoidChunkGenerator`（群系用平原），主世界维度类型，和平难度，保留 `setFlat(true)`（否则低处天空会变暗），不生成生物、不走天气、不推进时间、随机刻速度 0、禁止传送门。

写文件一律“临时文件 + 原子移动”，路径检查复用 `RoundWorldPaths.checkAncestors`。大厅文件不在 `FullCheckpoint` 的保存范围内（它只保存本轮世界），两者互不影响。

### 10.2 安装状态机（`LobbyInstall`，替代 `LobbyWorld` 现在的施工逻辑）

1. 读包、校验限制、DataFixer 升级、清洗。IO 线程。
2. 打开新维度 `hardrush:lobby_<seq+1>`，对 `bounds` 覆盖的区块加票据并等待加载完成。沿用现有 `LOAD_BUDGET`。
3. 每 tick 放置 1 块瓦片：`placeInWorld`，放置设置开 `setKnownShape(true)`、不忽略实体，更新标志只通知客户端并保持已知形状，避免跨瓦片的门、床被邻接更新弄坏。
4. 等所有区块的实体区段加载完（`ServerLevel.areEntitiesLoaded`），按第 9 节验收。
5. 缺少必需功能时放置临时设施（10.4），得到“生效 plan”。
6. 把包复制到 `installed/`，原子写 `current.json`（状态 `COMPLETE`）。
7. 切换：同一 tick 内把 `LobbyWorld` 指向新维度和新 plan，递增 plan 代数；把旧大厅里的每个玩家传送到新大厅中央落点（`PlayerProfiles.placeInLobby`）；然后删除旧维度（`RuntimeLevelHandle.delete()`）。

任何一步失败：删除新维度，保留当前大厅，把原因告诉发起安装的 OP。

启动时：

- 有 `current.json` 且状态 `COMPLETE`：打开对应维度，直接就绪。
- 没有：从 jar 内默认大厅包安装。失败时沿用现有的 `failure()` 机制。
- 清理：删除 `dimensions/hardrush/` 下所有不是当前大厅、也不属于现存草稿的 `lobby_*` 和 `workshop_*` 目录，以及旧版的 `dimensions/hardrush/lobby` 和 `hardrush/lobby-layout.txt`。当前没有真实用户，不做迁移。

切换条件：`session.state() == OPEN`、本轮处于 `PREPARING` 或 `WAITING`、没有正在保存的完整保存点。

回滚：菜单里选“回到上一个大厅”，就是用 `installed/` 里的上一个副本再走一遍安装。

实现偏差（M4a，菜单留给 M4b）：
- 服务端接口 `lobby/pack/LobbyAdmin`：`install(server, packs 里的文件, 发起者)`、`rollback`、`cancel`、`progress`、`library`（`Library(packs, loading)`，后台读 `pack.json`，按文件大小和修改时间缓存，2 秒内重复轮询直接返回上次结果）。不检查权限，由菜单负责 4 级 OP。`PackFile.readHeader` 只读第一个条目 `pack.json`；第一个条目不是它时退回完整读取，免得跳过前面的条目时无上限解压。
- 第 6、7 步之间加了“等待切换”：安装**任何时候都能开始**（文档 1 节写“只在 PREPARING／WAITING 时安装”，这里理解为“只在那时切换”），建好、验收、放好临时设施后进入 `READY`，等切换条件满足才复制 `installed/` 副本、写 `current.json`，提交完成的同一 tick 切换。这样 `current.json` 永远不会指向一个等待中被放弃的维度。等待超过 10 分钟或被取消就删除新维度；提交已经开始后不能取消，期间轮次若进入倒计时也照样切换（只有几 tick）。停服时只放掉区块票据：提交完成的下次启动直接打开新大厅，没完成的由启动清理删掉。
- 切换时：活着的非旁观玩家，本轮已准备（`LOBBY` 且 ready）的落到新集结区的 `RESTORE_READY`，其余落到中央落点，都走 `PlayerProfiles.placeInLobby`；旁观者（管理旁观、附身观战）直接传到中央落点并保持旁观；死亡的身体不搬（大厅里不会受伤）。实际上 `WAITING` 时有人准备就会进入倒计时、不允许切换，所以“保持准备”只在提交与倒计时相撞的那几 tick 起作用。附身观战只在 `RUNNING`／`RESCUE` 存在，切换时不会有；庆典访客在末地；建设者不在大厅维度。
- 序号：`LobbyWorld.nextSeq()` 从启动时扫到的最大序号往上递增；回滚安装的是上一个副本的拷贝，序号仍然递增，`installed/` 只保留新旧两份，所以再次回滚会回到刚才的大厅。
- 进度用 OP 状态栏（`StatusBars.Slot.LOBBY_INSTALL`，最低优先级，只给 4 级 OP）显示“正在安装 … 已放/总瓦片”或“已就绪 · 等待本轮回到准备阶段”；开始、就绪等待、切换、失败、取消、临时设施和验收警告用 `Notices.operators` 告知（发起者本身是 OP，不另发）。
- `MonsterShop`、`RevivalAltar`、`PlayerFeedback` 都是每次现查 plan，没有跨代数缓存；`MonsterVaults` 的逐玩家显示状态按 plan 代数清空。
- 暂存副本（评审修正）：安装开始时先把源包（包库文件、jar 内默认包或回滚用的旧副本）原子复制到 `installed/.staging-<seq>.hrlobby`，之后读包、清洗、放置和提交都只用这份；提交时把它原子移动为 `installed/<seq>.hrlobby`，sha256 也从它计算。原实现在提交时重新打开源文件复制，等待切换期间包库文件被替换的话，运行中的大厅与记录的副本会来自两个版本。安装失败、取消、超时都删除暂存（读包任务还在写时，等它结束再删）；停服打断的由启动清理删除。

实现偏差（M2）：
- 代码：`LobbyInstall`（状态机）、`LobbyStorage`（`hardrush/lobby` 下的文件与启动清理）、`LobbyInstallation`（`current.json`，由 `LobbyPlanJson` 读写）、`PlanWorldChecks`（第 9 节里需要世界的检查，从 `MarkerScan` 抽出，扫描与安装共用）、`world/LobbyDimension`（维度键、存储目录与 Fantasy 配置）。`LobbyWorld.KEY` 删除，改为实例方法 `key()`；`builtBlocks()`／`loadedChunks()`／`layoutVersion()` 换成 `placedTiles()`（本次启动放置的瓦片数，重开已有大厅时为 0）和 `installation()`。
- 维度配置另加 `RANDOM_TICK_SPEED = 0`（26.3 的规则名；否则营地柱子下的草方块会退化成泥土）和固定种子 0；传送门用 `ALLOW_ENTERING_NETHER_USING_PORTALS = false`。
- 第 6 步顺序：先复制 `installed/<seq>.hrlobby`，再原子写 `current.json`，最后删除多余副本；删副本失败只记日志，不让已提交的安装失败。写 `current.json` 之前先 `save(flush)` 新维度，保证记录指向的区块已经落盘。提交阶段不计超时，避免超时删掉维度后后台线程又写出指向它的记录。
- 启动重开不再做完整验收，只像旧营地一样检查中央、庭院落点站得住：崩溃发生在极限挑战中时祭坛玻璃是亮着的黄色玻璃，按 `altar_light` 规则会误判。落点不安全时报 `failure()`，保留维度等待修复。
- 没有 `current.json` 时新安装的序号取“已安装副本、维度目录、记录里出现过的最大序号 + 1”，不复用旧序号；`current.json` 读不出来时直接失败，不做清理（它可能指向我们会删掉的维度）。清理时还跳过任何已加载维度的目录。`workshop_*` 暂不清理，留 TODO 给 M3。
- 缺少必需功能时（M4 才有临时设施）一律安装失败。已有大厅时安装新包失败只记日志并保留当前大厅（M4 再把原因交给发起的 OP）。
- （M4 已改）缺少声明了临时设施的必需功能时放临时设施（10.4）；运行中安装失败通过 `Notices.operators` 告知。
- 默认大厅包：锚点 (0, 65, 0)，`created` 固定为 `2026-11-15T00:00:00Z`，作者 `HardRush`。`altar_pad` 的连片标记站在非中心金块上，连片会把信标下的中心金块也算进去（9 格而不是旧布局的 8 格）；信标上方压着祭坛光柱玻璃，没人能站在中心格上，所以不影响判定，几何中心也不变。方块触发器的 `anchor` 取方块顶面中心，比旧布局高 1 格。

### 10.3 plan 代数

`LobbyInteractions` 现在按轮次 id 清空注册（`synchronizeRound`）。新增 plan 代数，与轮次 id 一起作为失效条件。`HumanEntry.registeredRound` 同样要在 plan 代数变化时重新注册。数据包模型（`LobbyRoleModels`、`LobbyProjections`）在切换时全部清除重发。

实现偏差（M2）：`LobbyWorld.planGeneration(server)` 是不会顺带开启大厅服务的静态查询，`LobbyInteractions` 用它与轮次 id 一起判断失效（清空方块注册、派发记录、投影、角色模型和提示）。`HumanEntry` 在代数变化时除了重新注册触发器，还清掉上次写的状态牌文字，让新大厅的状态牌立刻写上。

### 10.4 临时设施

对每个缺失的、声明了临时设施的必需功能：以第一个中央落点为中心，在同一 Y 层由近到远（半径 2–8）找一格，要求本格和上一格是空气、下方是完整实心方块、不在任何区域内、离已有落点和设施至少 2 格。

- 点击类：放讲台；`page_prev`／`page_next` 放写好字的橡木告示牌。
- 模型类：只登记一个模型点，朝向中央落点。
- 宝库：放对应属性的宝库方块。

放置发生在切换之前，此时新维度还不是受保护的大厅，可以直接写方块。完成后用 `Notices.operators` 告知“大厅包缺少：X，已在中央落点旁放置临时设施”。找不到位置则安装失败。

实现说明（M4）：选址是核心纯函数 `FallbackSites`（单元测试覆盖），放置是 `lobby/pack/FallbackFacilities`，在 `LobbyInstall.verify` 里接入：先验收，扣掉“可用临时设施补上的缺失”之外的错误就失败；放好临时设施后用 `withAdditions` 得到生效 plan 再验收一次，生效 plan 写进 `current.json`。补充规则：候选格本身和上方一格都要在大厅范围内（否则生效 plan 过不了范围检查）；“至少 2 格”按三维欧氏距离；同距离先北后南、先西后东，结果确定。讲台、宝库朝向中央落点，告示牌正面朝中央落点，写“上一页／下一页”和“右键翻页”并上蜡。临时设施的提示通知在切换完成时发出（与“已切换到大厅 X”一起）。

### 10.5 掉出大厅

虚空世界里玩家可能走出建筑掉下去，而大厅里伤害被拦截，会一直下落。`LobbyWorld` 每 tick 检查：大厅里的玩家 `y < bounds.min.y - 8` 时传回中央落点。

实现偏差：旁观模式的玩家（管理旁观、附身观战）不处理，他们本来就能飞到任何地方。档案服务管理的身体走 `PlayerProfiles.placeInLobby`（会重新套用大厅模式）；不受管理的玩家直接传送到散布后的中央落点。

## 11. 工坊

### 11.1 草稿

- 一个草稿一个维度。同一草稿可多人同时建，多个草稿可同时打开。维度在没人时卸载（`RuntimeLevelHandle.unload()`）。草稿上限 8 个。
- 建造范围用原版世界边界表示：中心默认 `(0, 0)`，直径默认 `hardrush.lobby.maxSize`。中心和直径记在 `draft.json` 里，建设者可在工具箱里“把范围中心设到我这里”和缩小直径（导入的存档里建筑往往不在原点）。**实现时先核实** Fantasy 维度的世界边界是否独立于主世界；如果不独立，退回到坐标检查（放置和移动超出范围时拒绝并提示）。
- 新建方式：从当前大厅（导入 `installed/` 里的当前副本）、空白（在 `(0, 64, 0)` 放一块 5×5 石台）、从包库里的某个文件、从已有存档或建筑文件（第 19 节）。没有任何草稿时，第一次打开菜单自动“从当前大厅”建一份。
- 从包导入草稿与安装用同一套读包、清洗、逐瓦片放置的代码，同样分摊到多个 tick；导入完成前草稿不可进入，菜单里显示进度。
- 最后一名建设者离开时保存维度。

实现偏差（M3a）：
- 代码：`lobby/workshop/Workshop`（服务：草稿、维度开关、送回）、`Draft`／`WorkshopStorage`（`draft.json` 与启动清理）、`DraftImport`（分 tick 导入，`Content` 留给 M3b 加“包库文件／存档／建筑文件”）、`WorkshopMenu`。读包、升级、清洗抽成 `PreparedPack`，与 `LobbyInstall` 共用；放置直接复用 `ChunkWarmup` 与 `PackPlacer`。
- 维度空闲时先立即保存，100 tick 后再 `unload()`；Fantasy 的卸载是排队执行的，卸载完成前重新进入会被拒绝（“草稿正在保存，稍后再试”），避免排队中的卸载落到重新打开的维度上。同理，本次运行中删除过的草稿 id 不再分配。
- 启动时 `IMPORTING` 状态的草稿（导入被停服或崩溃打断）连同维度一起删除；`draft.json` 读不出来的目录保留，连同维度都不清理，也不占用其 id。
- 导入失败（含 2 分钟超时）时删除该草稿，并告诉发起人原因。
- 从包新建（“从当前大厅”“从包库文件”）时，包内坐标保持绝对坐标不变，所以范围中心取包 `bounds` 的水平中心，直径取 `max(默认直径, bounds 水平跨度 + 2×16)`，不超过 `hardrush.lobby.maxSize`（评审修正：原先中心留在默认的 (0, 0)，远离原点的大厅重新导入后验收和发布会漏掉建筑）。进入点仍取第一个中央落点。

### 11.2 建设者身份（接入 `PlayerProfiles`，本功能风险最高的部分）

背景：大厅里的玩家身体带着本轮的封存档案。`Entry.resume` 是这份档案的权威快照；入场时非新档案从 `resume` 恢复，**新档案直接用身体上现有的状态**。所以建设者的创造背包绝不能留在身体上。

仿照现有的管理旁观（`Entry.adminSpectating`）新增 `Entry.building`：

- **进入**条件：`administrativeBody` 成立、`verifiedLobbyBody` 成立、未在管理旁观或附身观战、`entry.resume != null`、不是已准备的参赛者（与 `RoundRuntime.administrativeSpectatingAllowed` 对参赛者的判断一致）、2 级 OP、阶段允许。已准备的玩家提示“先走出集结区”。
- **进入**动作：`closeSuspendedContainer`、清空背包、传送到草稿（有中央落点用中央落点，否则 `(0.5, 65, 0.5)`）、切创造并开启飞行、发工具。
- **离开**动作：`building = false`，然后把 `entry.resume` 重新装回身体。`prepare()` 的新档案分支里已经有这段代码（`player.load` → `clearLoadedProfile` → `restoreAdvancements` → `moveToLobby` → `resetSentInfo` → `onUpdateAbilities` → 同步背包），把它抽成私有方法 `reloadSuspendedBody(entry)` 两处共用。新档案和非新档案离开时都调用。
- **`tick()`** 里必须注意两点：
  1. 在“代数变化 → `onLogin`”检查**之前**先处理建设者：不再满足条件（阶段不对、失去 OP、代数将变、恢复暂停）就执行离开。否则 `onLogin` 会把创造模式的身体当作原始档案捕获并写入日志。
  2. 循环末尾的“大厅身体校正”（不在大厅就 `moveToLobby`，并强制冒险模式）对有效建设者要 `continue`，和 `adminSpectating` 的处理方式一样。
- **`allowVanillaSave`** 对建设者返回 `false`（与 `celebrationGuest` 相同）。这样断线或崩服时磁盘上保留的是封存的大厅状态，下次登录按现有流程从日志恢复。因此 `onDisconnect` 不需要做恢复，直接丢弃标记即可。
- **`isLocked` 语义不变**（建设者仍然不是比赛身体）。新增 `PlayerProfiles.building(player)`，并在这些闸门上放行建设者：
  - `PlayerIsolationNetworkMixin` 里所有基于 `isLocked` 的拦截（含命令拦截 `hardrush$allowedCommand`）；建议抽一个 `sealed(player) = isLocked(player) && !building(player)`。
  - `PlayerIsolationEntityMixin` 的两处。
  - `simulationFrozen`。
  - `administrativeGameMode`：建设者直接返回 `Optional.empty()` 交给原版，否则 `/gamemode spectator` 会被当成申请管理旁观。
  - `PlayerAdvancementIsolationMixin` 不放行，建设期间不记进度。
- **限制在草稿维度内**：`ProtectionRuntime.rejectMove` 增加一条，建设者的目的地不是自己的草稿维度就拒绝（生命周期的强制返回先执行离开再传送，不受此限）。
- **不会死**：`ProtectionRuntime.rejectDamage` 对工坊维度里的玩家一律拒绝伤害（包括 `/kill` 和虚空）；`y` 低于世界底部 16 格时传回进入点。死亡会进入复杂的重生流程，必须避免。
- 工坊维度**不是**受保护世界（`protectedLevel` 返回 `false`），方块才能改。

建设者拥有 2 级 OP 的全部原版命令（`/give`、`/fill`、`/clone`、`/gamemode` 等）。不额外防范 `/execute in` 影响其他维度：OP 在比赛世界里本来就能用命令，这是服主对 OP 的信任问题。

实现偏差（M3a）：
- **离开时装回的是进入前一刻的大厅身体，而不是 `entry.resume`**。进入时用 `capture` 把身体原样留存在 `Entry.buildingBody`（只在内存，不写日志），离开时先清空背包、装备、末影箱、效果、属性，再装回它。原因：新档案入场直接使用身体，而大厅身体可能比 `resume` 多出在营地里拿到的东西（战绩书等），装回 `resume` 会把它们丢掉；装回进入前的身体正好满足“离开后与进入前一致”。`reloadSuspendedBody(entry, snapshot)` 接收要装回的快照，`prepare()` 的新档案分支传 `resume`。崩服、断线时原版存档仍是进入前保存的大厅状态（建设期间 `allowVanillaSave=false`），登录走原流程。
- 离开时先 `setGameMode(ADVENTURE)` 再装回：装回后服务端已认为是冒险模式，`applyLobbyMode` 不会再发包，客户端会停在创造模式。
- `isLocked` 不变；`PlayerIsolationNetworkMixin`、`PlayerIsolationEntityMixin` 里所有基于 `isLocked` 的闸门统一改为 `PlayerProfiles.sealed(player) = isLocked && !building`（命令放行随之对建设者全部放开）。
- `rejectBuilderMove` 只在建设者正站在自己草稿里时生效（目的地不是本草稿就拒绝），进入时从大厅出发的那次传送不受影响；离开时先清标记再传送。被拒绝时用 T1 提示说明如何离开。
- `tick()` 里建设者的有效条件：代数未变、`building(player)`（`administrativeBody` 且站在自己草稿里）、`Workshop.leaveReason` 为空；否则先离开再继续后面的代数检查。`returnToLobby` 也会先结束建设，所以失败门、在线恢复、停服、轮换都不会读到创造身体。
- 完整保存点：入口是 `FullCheckpointRuntime.tick`，它在同一个 tick 内同步完成“检查 → 发起 → 原生保存”，检查项包括 `profiles.readyForFullCheckpoint(round)`；后者在存在任何建设者时返回 `false`。另外保存点只在 `RUNNING` 发起，而 `Workshop.tick`（排在 `RecoveryRuntime.tick`、`profiles.tick`、`FullCheckpointRuntime.tick` 之前）在阶段离开开放期的第一个 tick 就让建设者离开；`FullCheckpointRuntime.saving`（含在线恢复）也是离开条件。
- “已准备的参赛者”判断抽成 `RoundRuntime.rosterBound`，与管理旁观共用；`RoundRuntime.buildingRefusal(player)` 给出阶段、会话与准备状态的拒绝原因，进入和送回共用。

### 11.3 送回大厅

`Workshop.tick` 每 tick 检查，出现下列任一情况时让对应建设者离开，并用 `Notices.personal` 说明原因：本轮阶段不在 `PREPARING`／`WAITING`／`COUNTDOWN`、`session.state() != OPEN`、正在保存完整保存点、玩家不再是 2 级 OP、服务器停止、草稿被删除。

### 11.4 步行预览

工具箱里的开关：切到冒险模式并关闭飞行，再点一次切回创造。只用来检查走位、跳跃、门。标记照常可见，设施不响应。真正的功能测试在安装到正式大厅后进行，不满意可回滚。

实现说明（M3b）：开关不另存状态，以当前游戏模式为准（冒险 = 预览中），所以建设者自己敲 `/gamemode` 也不会让开关错位；离开工坊时身体装回冒险模式的大厅身体，预览自然结束。工具箱在冒险模式下照样可用（右键空气或方块都由模组处理）。

### 11.5 发布（`PublishJob`，4 级 OP，分摊到多个 tick，Boss 栏显示进度）

1. 对草稿范围内的区块加票据，等区块和实体区段都加载完。**实体区段是异步加载的，不等的话会漏掉标记和装饰实体。**
2. 收集标记盔甲架和实体触发器，逐区块扫描非空气方块，得到紧致的 `bounds`（方块范围与标记位置的并集）。为空则报错。草稿设了“底部高度”（19.1）时，低于它的方块不计入。
3. 把标记解析成 `LobbyPlan`（连片区域在这里做搜索），按第 9 节验收。有错误就中止并列出。
4. 每 tick 捕获 1 块瓦片：`StructureTemplate.fillFromWorld(level, 起点, 尺寸, true, [air, cave_air, void_air])`。
5. IO 线程写 zip 到 `hardrush/lobby/packs/<id>-v<version>.hrlobby`，更新 `draft.json` 的版本号。
6. 完成后提示，并在菜单里提供“现在安装”。

第 1–4 步的通用构件在平台包 `lobby/pack`：`ChunkWarmup`（区块与实体区段预热）、`MarkerScan`（标记 → plan，含需要世界的验收）、`PackCapture`（每次调用捕获一块瓦片）、`PackPlacer`（每次调用放置一块瓦片）。

实现偏差：
- `MarkerScan.scan(level, area, bottomY, maxHorizontalSize)` 多一个参数，用于调用 `LobbyPlanValidator`。只要找到内容就返回 plan（即使有错误），调用方以 `hasErrors()` 判断能否发布；什么都没有时 plan 与范围为 null 并报 BOUNDS 错误。
- `bounds` 除方块与标记、触发器位置外，还并入：会被安装保留的白名单实体（悬在空中的展示实体等不会被裁掉）、方框区域在扫描范围内的部分（庭院方框向上延伸进空气，否则会被误报为超出范围）。
- 连片区域搜索不出扫描范围（范围外视为空气），保证只读调用方已加载的区块。
- 捕获时按实体的 `blockPos` 归属瓦片：`fillFromWorld` 按碰撞箱收实体，跨瓦片边界的实体会被两边都收到，每块瓦片只保留 `blockPos` 在自己捕获范围内的实体。
- 放置时用 `StructurePlaceSettings.setBoundingBox(bounds)` 裁掉越界的方块和实体，不改瓦片 NBT。

实现偏差（M3b，`lobby/workshop/PublishJob`）：
- 扫描范围是草稿的世界边界正方形（`Draft.range`，直径为奇数时多出的一格在正方向），全部高度；底部高度只影响方块与捕获，不影响标记。一次 `MarkerScan.scan` 在一个 tick 内扫完（大范围带地形的存档会卡一下，只在发布时发生）。区块加载超时 5 分钟。
- 捕获完成后对瓦片的拷贝跑 `TileSanitizer(INSTALL)`：`removedIds` 生成“安装时将被移除：…”，另外清空容器、去掉文字点击事件也各给一条提醒；`checkTotals` 超限则失败。
- 作者确认：草稿页“发布”进入发布页，打包完成后列出参与者（点击切换署名），“确认发布”才写文件；等待确认超过 10 分钟自动放弃。失败时最多列 10 条问题加“还有 N 条”，聊天栏同时告知发布者。
- 版本号取 `published_version + 1`；包库里已经有同名文件（例如以前删掉的草稿用过同一个 id）时继续往上加，不覆盖别人的文件。
- 发布未结束（`DONE`／`FAILED` 之前）时，模组自己发起的批量改世界操作一律拒绝（评审修正）：贴入建筑文件、清除生物，提示“草稿正在发布，等发布完成再操作”。扫描与逐瓦片捕获跨多个 tick，期间贴入会让包里只有半栋建筑，或覆盖已验收的绑定方块。绑定杖放标记、切换标记材质、调整范围中心／直径都是建设者手动的单次操作，和原版手动改方块一样拦不住也不必拦：范围在发布开始时已经定下，之后的改动只影响下一次发布。
- 进度条走 `StatusBars.Slot.PERSONAL`，只给发布者。完成后发布页提供“现在安装”，调用 `LobbyAdmin.install`。草稿被删除或停服时作业取消并释放区块票据；发布进行中不能再贴入建筑，贴入进行中不能发布。

## 14. 保护系统

### 14.1 受控写入（先修，独立提交）

**疑似现有 bug**：`ProtectionWorldMixin` 在受保护世界里拦截所有 `Level.setBlock`，没有任何放行。`LobbyWorld.altarLit` 用 `setBlockAndUpdate` 切换祭坛玻璃，且只在 `ready` 之后执行，而 `ready` 之后大厅就是受保护世界。按代码推断，正式服上祭坛光柱永远点不亮。断言它能点亮的 `HumanEntryGameTest` 运行时保护是关闭的（`UnprotectedLobbyFixtures` 的保留名单里没有 `HUMAN_ENTRY`），所以测试没发现。此结论未经运行验证，实现第一步先写一个在正式保护绑定下的 gametest 复现。

修法：`ProtectionRuntime.ownedWrite(ServerLevel, Runnable)`，仅服务器线程，用深度计数在回调期间放行该世界的 `setBlock`。只有模组自己的写入使用（祭坛玻璃切换）。

### 14.2 互动装饰（最后做，可独立延期）

两处放行，都只针对一个固定名单 `LobbyInteractive`：

- 原版标签：`doors`、`trapdoors`、`fence_gates`、`buttons`、`pressure_plates`。
- 方块：`lever`、`note_block`、`bell`、`redstone_wire`、`repeater`、`comparator`、`redstone_lamp`、`redstone_torch`、`redstone_wall_torch`、`target`、`daylight_detector`、`tripwire`、`tripwire_hook`，以及铜灯系列。

1. **玩家输入**（`ProtectionNetworkMixin.handleUseItemOn`）：目标方块属于名单中可手动操作的部分（门、活板门、栅栏门、按钮、拉杆、音符盒、钟），且玩家没有潜行时，放行给原版。潜行时原版会跳过方块交互直接用手上物品，所以继续拦截。
2. **世界写入**（`ProtectionWorldMixin`）：新旧状态是同一种方块、且该方块在名单内时放行。这样门的开合、按钮回弹、红石线充能都能生效，而任何“变成另一种方块”的写入仍被拦截。

活塞（`ProtectionPistonMixin`）、破坏、流体、爆炸、容器保持现状。发射器和投掷器不在名单内，且容器已被清空。

实现偏差：（1）放行后原版在方块不消费点击时（铁门、钟的非敲击面、音符盒顶面放头颅）会回落到手上物品，所以新增 `ProtectionItemMixin`，受保护世界里 `ItemStack.useOn` 一律返回 PASS。（2）`PlayerIsolationNetworkMixin` 对“未入局的大厅玩家”（`isLocked`）也会取消 `handleUseItemOn`，同样需要放行，统一由 `ProtectionRuntime.interactiveClick` 判定；冻结（存档中、待确认参与）时仍拦截。（3）音符盒左键（攻击）走 `handlePlayerAction`，仍被拦截；右键调音同时会响，不影响使用。

## 17. 已核实的原版与依赖事实

用 `scripts/mc-knowledge.py` 对 26.3 服务端 JAR 查证（本机没有 Vineflower，以下均来自方法签名和字节码，不是反编译源码）：

- `StructureTemplate.fillFromWorld(Level, BlockPos, Vec3i, boolean, List<Block>)`：最后一个参数是要忽略的方块列表。
- `StructureTemplate.fillEntityList` 用 `getEntitiesOfClass(Entity.class, …)` 收集范围内实体，盔甲架、展示实体、`interaction` 都会被保存。
- `StructureTemplate.placeInWorld(ServerLevelAccessor, BlockPos, BlockPos, StructurePlaceSettings, RandomSource, int)`；`StructurePlaceSettings` 有 `setKnownShape`、`setIgnoreEntities`。
- `StructureTemplate.load(HolderGetter<Block>, CompoundTag)`／`save(CompoundTag)`；`DataFixTypes.STRUCTURE` 存在。
- `StructureBlockEntity.MAX_SIZE_PER_AXIS` 存在（原版为 48）。
- `ArmorStandItem.useOn`：通过 `EntityType.createDefaultStackConfig` 应用物品上的实体数据；朝向由玩家朝向加 180° 后取整；放置前要求目标格无碰撞且没有其他实体，点击方块底面会失败。
- `EntityType.updateCustomEntityTag`：只有 `onlyOpCanSetNbt` 的实体类型才要求 OP。
- `ArmorStand.hurtServer`：伤害来源是创造模式玩家时直接移除。
- `SignBlockEntity.executeClickCommandsIfPresent`：告示牌点击命令以 `LevelBasedPermissionSet.GAMEMASTER` 执行。

## 19. 导入已有存档与建筑文件

别的服主很可能已经有现成的大厅。社区里常见的分发形式，按常见程度：

1. **整个存档**（世界文件夹）：大厅、主城类地图最常见的形式。
2. **`.schem`**：WorldEdit／FAWE 的建筑文件（Sponge Schematic 格式），单体建筑最常见。
3. **`.litematic`**：Litematica 模组的投影文件。
4. **`.nbt`**：原版结构方块保存的文件。
5. **`.mcfunction`**：一串 `setblock`／`fill` 命令，多见于转换工具的导出选项，很少用来分发。

导入的结果都是一份普通草稿，之后照常放标记、验收、发布。导入不会带来任何功能绑定，功能需要建设者自己绑。

文件统一放在 `hardrush/workshop/import/` 下，由 4 级 OP 在 `/hardrush lobby` 菜单的“新建草稿”里选择。需要 4 级是因为这一步读取服主放到磁盘上的任意文件。

### 19.1 从存档导入（随 M3 做）

做法：草稿本来就是一个真实维度，所以直接把存档的区块文件复制进草稿维度的目录，再打开维度。区块由原版自己读取和升级，旧版本存档的升级也由原版完成，模组不解析区块。

- 接受两种目录形态：直接含 `region/` 的目录；或完整存档，此时取主世界（新版在 `dimensions/minecraft/overworld/`，旧版在存档根目录）。
- 复制 `region/`、`entities/`、`poi/` 三个目录到 `DimensionType.getStorageFolder(草稿维度, 世界根)`，**必须在该维度第一次打开之前完成**。在 IO 线程做，菜单里显示进度。总大小超过 4 GB 时拒绝。
- 范围中心：存档里有 `level.dat` 就取它的出生点，否则取第一个区块文件的中心。建设者进去后用工具箱“把范围中心设到我这里”调整。
- 这条路径不做清洗：文件是服主自己放到服务器磁盘上的，而且清洗会在发布后的安装环节照常进行。验收会用警告列出将被移除的内容。
- 存档带着地形和生物，工具箱为此提供三个辅助：
  - **底部高度**：把“我脚下这一层以下”排除在大厅之外，记在 `draft.json`，发布时不捕获。避免把整片地下石头打进包里。
  - **缩小范围**：调小世界边界直径。
  - **清除生物**：移除范围内不在实体白名单里的非玩家实体。
- 存档里的模组方块、数据包方块在本服不存在，会变成空气。极老版本存档的升级效果不保证。

实现偏差（M3b，`lobby/workshop/SaveImport`、`ImportFolder`）：
- 已核实第 17 节最后一条：把一个草稿维度保存后的 `region/`、`entities/`、`poi/` 复制成 import 目录里的“存档”，导入后原有方块（含讲台、地下与远处的方块）和标记盔甲架都在相同坐标（`WorkshopGameTest`）。复制在维度首次打开前、`DraftImport` 读取阶段的同一个后台任务里完成（先删目标目录再复制）；只复制普通文件，跳过符号链接。读取阶段（含复制）超时放宽到 30 分钟，之后的步骤仍是 2 分钟。
- 出生点：`level.dat` 的 `Data.spawn.pos`（1.21.9 起）或 `SpawnX/Y/Z`；都没有时取按文件名排序的第一个区域文件里的第一个区块中心（Y 64），并在完成通知里提示调整。出生点同时作为范围中心和进入点。
- `import/` 目录与草稿目录并列在 `hardrush/workshop/` 下，草稿列表跳过它。“新建草稿”页还列出包库里的 `.hrlobby`（2 级，与“从当前大厅”同一条导入路径），import 目录条目对非 4 级管理员置灰。
- 清除生物只处理已加载的实体：范围内不在实体白名单里的非玩家实体（含掉落物）。
- 底部高度的语义（评审修正）：记录的 Y 是保留的最低一层，低于它的方块不发布（`MarkerScan` 与 `PackCapture` 都按 `y ≥ bottomY` 取）。“设为脚下”取建设者实际站着的承重方块（`Entity.getOnPos()`；站在半砖、地毯上时就是半砖、地毯那格），不是双脚所在的那格，所以脚下的地板本身会被发布；按钮与提示写作“低于 Y N 的方块不会发布”，N 与按钮上显示的是同一个值。

### 19.2 从建筑文件导入（M6）

三种格式各写一个转换器，统一转成“带原始数据版本号的原版结构瓦片”，之后完全复用大厅包的管线：DataFixer 升级 → 清洗 → 逐瓦片放置。这样跨版本升级、清洗、放置都不用再写一遍。

| 格式 | 要点 |
| --- | --- |
| `.nbt` | 就是原版结构模板，按 48 格切成瓦片即可 |
| `.schem` | gzip NBT。v2 字段在根上，v3 包在 `Schematic` 下、方块在 `Blocks` 里。调色板是“方块状态字符串 → 编号”，方块数据是变长整数的字节数组，下标 `x + z×宽 + y×宽×长`。方块实体带 `Pos`、`Id`，其余数据在 v2 里平铺、v3 里在 `Data` 下 |
| `.litematic` | gzip NBT。`Regions` 下可有多个区域，每个有 `Position`、`Size`（可为负，负值表示向反方向延伸）、`BlockStatePalette`（已经是原版的 `{Name, Properties}`）、`BlockStates`（长整型数组，每个编号占 `max(2, ⌈log₂调色板大小⌉)` 位，紧密排列、可跨越两个长整型），下标 `x + z×宽 + y×宽×长`。`TileEntities` 为方块实体。数据版本在 `MinecraftDataVersion` |

- `.schem` 的方块状态字符串（如 `minecraft:oak_stairs[facing=north,half=bottom]`）要拆成 `{Name, Properties}`。写成核心里的纯函数并单测。
- 只导入方块和方块实体，**不导入实体**，不支持旋转和镜像。
- 文件视为不可信：同样的大小限制（水平 ≤ `hardrush.lobby.maxSize`，总方块数对应的瓦片限制同第 7 节），同样经过清洗。
- 两种用法：
  - **新建草稿**：建筑水平居中放在 `(0, 64, 0)`，底面在 Y=64。
  - **贴进当前草稿**（2 级 OP，在工坊里）：水平居中于建设者、底面在脚下，不覆盖空气。没有撤销，菜单里二次确认。
- 仓库里放三个很小的样例文件做测试，用真实工具导出。

实现偏差：开发机上没有 WorldEdit 和 Litematica，样例文件无法用真实工具导出。改为 `SampleFiles` 按公开规范在测试运行时生成（`.nbt`、`.schem` v2/v3、含负尺寸和跨 long 位读取的双区域 `.litematic`），单元测试断言转换结果；“用真实工具导出的文件导入”列入人工客户端测试。另外，`.litematic` 的 `BlockStates` 只在数组比需要的短时拒绝（长了不拒绝，兼容各版本写入方式）；区域重叠时后一区域的非空气方块覆盖前一区域，并在转换结果的 `notes` 里提示。

实现说明（M3b）：新建草稿与贴入共用 `DraftImport.structure`（读取 → `placedAt` → `PackTiles.upgrade` → `TileSanitizer(DRAFT)` → 每 tick 一块 `PackPlacer`），`notes` 在完成时发给发起人。贴入的目标是已有维度，不删除目录；转换出的瓦片本来就不含空气和结构空位（`StateEntry` 过滤），`placeInWorld` 只写模板里列出的方块，所以不会覆盖成空气。`SampleFiles` 挪到 `development` 源码集，单元测试与 gametest 共用。

### 19.3 不专门支持的形式

- **`.mcfunction`**：不需要专门支持。建设者在工坊里有 2 级 OP 的全部命令，把文件放进数据包后在工坊里执行 `/function` 即可。注意两点：命令里是绝对坐标时会建在那个坐标上；大建筑可能超过单次函数的命令数上限。模组不替服主执行这类文件，因为它可以包含任意命令。
- **旧版 `.schematic`**（1.13 之前的数字 id 格式）：先用 WorldEdit 载入再另存为 `.schem`。
- 服主自己装了 WorldEdit 的话，也可以直接在工坊里用它的命令粘贴，与本功能互不影响。
