# 大厅包与工坊

2026-11-13 与需求方讨论定稿。状态：待实现。

实现时如与本文不一致，在对应小节末尾用“实现偏差：”写明原因，不要悄悄改方案。

## 背景

粉丝愿意帮忙建设准备大厅，但现在大厅的建筑和功能都写在代码里：

- `core/.../lobby/LobbyLayout.java`：设施、落点、集结圈、怪物庭院全是相对出生点的 2D 常量，没有 Y，做不了多层。
- `platforms/mc263/.../world/CampBlueprint.java`：逐块生成建筑。
- `platforms/mc263/.../world/LobbyWorld.java`：超平坦维度 + “只认自己铺的方块”的清单校验 + 旧版迁移。
- `ProtectionRuntime` 把大厅维度整体封死，没有“建设者”身份。
- `LobbyInteractions.registerBlock` 只接受讲台、告示牌、宝库三种方块。

目标：把“建设 → 绑定功能 → 打包 → 分发 → 安装”做成 HardRush 正式提供的服务端能力，其他服主装上模组就能用，全程原版客户端。

参考过的同类做法：

- 起床战争插件（Screaming BedWars、BedWars1058）：管理员站到位置上敲命令设点，坐标存配置，地图另存。学它“人在哪设在哪”和“保存时检查最低要求”；不学它“配置和地图分离”。
- Nucleoid Creator Tools（与本项目使用的 Fantasy 同一团队）：独立工作区维度里建，导出为单个文件，方块和区域都在里面。本方案结构与它一致。

## 1. 需求定稿

| 项 | 结论 |

## 2. 总体模型

三个概念，一条单向流：

```
草稿（工坊维度，可编辑） ──发布──▶ 大厅包（文件，唯一真相） ──安装──▶ 正式大厅（维度，只读的一次性实例）
        ▲                                   │
        └──────────── 导入为草稿 ◀───────────┘
```

- **大厅包是唯一真相**。正式大厅不允许就地修改，所有改动都走“草稿 → 发布 → 安装”。因此不再需要“方块所有权清单”这类机制。
- **所有坐标都是世界绝对坐标**，工坊、大厅包、正式大厅三者一一对应，没有任何平移或旋转。
- 模组自带的默认大厅是 jar 里的一个大厅包，与服主自己的包走同一条安装路径。

## 3. 功能目录

核心新增枚举 `core/.../lobby/LobbyFunction`，取代 `LobbyLayout.Facility`、`Landing` 和各区域常量。

| id | 名称 | 绑定形态 | 数量 | 必需 | 缺失时的临时设施 |
| --- | --- | --- | --- | --- | --- |
| `assembly` | 集结区 | 区域 | ≥1 | 是 | 无（发布时强制） |
| `courtyard` | 怪物庭院 | 区域 | ≥1 | 是 | 无（发布时强制） |
| `altar_pad` | 祭坛踏板 | 区域 | ≥1 | 是 | 无（发布时强制） |
| `altar_light` | 祭坛光柱 | 方块，限 `tinted_glass` | 0–4 | 否 | — |
| `landing_central` | 中央落点 | 点 | 1–16 | 是 | 无（发布时强制） |
| `landing_monster` | 庭院落点 | 点 | 1–16 | 是 | 无（发布时强制） |
| `landing_altar` | 祭坛落点 | 点 | 0–16 | 否 | 用庭院落点 |
| `display_slot` | 追猎目标展位 | 点 | 1–60 | 是 | 无（发布时强制） |
| `rules` | 规则 | 点击 | ≥1 | 是 | 讲台 |
| `history` | 战绩 | 点击 | ≥1 | 是 | 讲台 |
| `role_zombie`／`role_skeleton`／`role_creeper` | 角色展位 | 模型 或 点击 | ≥1 | 是 | 模型 |
| `merchant` | 女巫商人 | 模型 或 点击 | ≥1 | 是 | 模型 |
| `vault`／`ominous_vault` | 试炼宝库／不祥宝库 | 方块，限 `vault` 且 `ominous` 属性匹配 | ≥1 | 是 | 宝库方块 |
| `page_prev`／`page_next` | 展位翻页 | 点击 | ≥1 | 是 | 告示牌 |
| `status` | 状态牌 | 文字 | 0–8 | 否 | — |
| `credits` | 署名牌 | 文字 | 0–8 | 否 | — |

绑定形态：

- **点**：一个位置加朝向。
- **模型**：一个位置加朝向，运行时模组在这里发数据包模型（僵尸、骷髅、苦力怕、女巫），沿用 `LobbyRoleModels`。
- **点击**：右键触发。可以是方块（任意方块），也可以是实体（任意带标签的实体，见 4.3）。
- **方块**：特定类型的方块。
- **区域**：玩家站进去生效，见第 5 节。
- **文字**：告示牌方块或 `text_display` 实体，内容由模组写入。

规则：

- 以后新增必需功能时，必须同时在枚举里声明临时设施形态。加一个单元测试遍历枚举，断言“必需且非发布时强制”的功能都有临时设施，并断言 jar 内默认大厅包包含全部必需功能。
- `WAIT_OUTSIDE` 落点删除，原用途（`HumanEntry` 恢复准备落点不安全时的退路）改用中央落点。
- `RESTORE_READY` 落点不再单独标记：取集结区内离区域中心最近的安全站立格。
- 追猎目标展位的顺序按 `(y, z, x)` 升序，容量等于标记数量，替代 `LobbyLayout.DISPLAY_CAPACITY`。少于 10 个时验收给警告。
- 原来随阶段改写的展位告示牌（`LobbyWorld.huntLabels`）删除。“极限挑战时开放”改为显示在角色模型的名牌上；翻页和其他说明牌由建设者自己写成普通告示牌。靠近设施时的动作栏提示（`PlayerFeedback.facilityTip`）保留，改为按 `LobbyFunction` 取文案。

## 4. 标记

功能绑定存在工坊世界里的**标记盔甲架**上，随建筑一起保存、一起被结构方块或 WorldEdit 复制。选盔甲架是因为它是地图作者用了很多年的习惯做法：有名牌能看见，创造模式打一下就删，朝向就是放下时面对玩家的方向。

### 4.1 标记盔甲架

属性：`Small:1b`、`NoGravity:1b`、`NoBasePlate:1b`、`CustomNameVisible:1b`，`CustomName` 为“【集结区】”这类中文名，头上戴一个代表该功能的物品（如僵尸头、书）。

数据全部放在实体的记分板标签（`Entity.entityTags()`／`addTag`）里，纯字符串，OP 用 `/tag` 也能查看和修改：

| 标签 | 含义 |
| --- | --- |
| `hardrush.marker` | 这是标记盔甲架。安装到正式大厅时会被剔除 |
| `hardrush.fn.<id>` | 功能，`<id>` 为第 3 节的 id。有且只有一个 |
| `hardrush.as.point`／`.model`／`.block`／`.zone`／`.text` | 绑定形态。有且只有一个 |
| `hardrush.shape.flood`／`hardrush.shape.box` | 区域形状，仅区域标记 |
| `hardrush.mat.<命名空间>+<路径>` | 连片区域的材质，如 `hardrush.mat.minecraft+lime_wool`。可多个。用 `+` 代替冒号，因为 `/tag` 的参数不接受冒号 |
| `hardrush.box.<x>.<y>.<z>` | 方框区域的尺寸，整数 0–64 |

解析与格式化写成核心里的纯函数 `MarkerTags.parse(Set<String>) → MarkerSpec | 错误`，单元测试覆盖。

### 4.2 位置规则

- **点、模型**：位置取盔甲架脚底坐标，朝向取盔甲架 yaw。
- **方块、文字、方块点击**：目标方块 = 盔甲架所在格的方块；如果那一格是空气，则取正下方一格。所以把标记放在讲台顶上就是绑定这个讲台。
- **区域**：见第 5 节。

### 4.3 实体触发器

任何**非标记**实体只要带 `hardrush.fn.<id>` 标签（且该功能支持“点击”），在正式大厅里右键它就触发该功能。安装时这类实体保留。

文字类功能（`status`、`credits`）同理：给一个 `text_display` 实体打上标签，模组就把内容写进它。

典型用法：建设者用展示实体拼了一个雕像，再在外面放一个 `interaction` 实体当点击范围，给它打标签。盔甲架雕像、物品展示框也可以直接打标签。

### 4.4 工具

进入工坊时发放，全部是原版物品加自定义数据：

1. **工具箱**（放在快捷栏第 9 格的箱子物品）：右键打开箱子菜单，分类列出所有标记物品，点击领取。菜单里还有验收清单、步行预览开关、离开工坊。
2. **标记物品**：预置了 `minecraft:entity_data` 组件的盔甲架物品。直接用原版方式放置，不需要模组写放置逻辑。
3. **绑定杖**（带自定义数据的木棍）：
   - 右键方块：菜单选择“把这个方块绑定为…”，模组在目标格上方生成标记；上方放不下时生成在目标格内。也可选“在这里创建点击范围”，生成一个 `interaction` 实体（提供 1×1、1×2、2×2、3×3 几种尺寸）。
   - 右键非标记实体：菜单选择功能，给实体加 `hardrush.fn.<id>` 标签；再次右键可移除。
4. **右键标记盔甲架**（拦截原版的“给盔甲架穿装备”）：
   - 连片区域标记：手持方块物品右键 = 添加或移除一种材质。
   - 方框区域标记：空手右键打开菜单，调整宽、高、深。
   - 其他标记：显示这个标记的说明。
5. 删除标记：创造模式打掉盔甲架。打掉被绑定的方块时，模组顺带移除它上面的标记。

### 4.5 让建设者看见

每 10 tick，对每个建设者 32 格内的标记：

- 区域标记：在解析出的地板格顶面或方框边线上发粒子。连片区域每 20 tick 重新解析一次。
- 方块标记：在目标方块外轮廓发粒子。
- 验收有问题的标记换一种颜色的粒子。

粒子只发给工坊里的玩家（`ServerLevel.sendParticles(player, ...)`）。

## 5. 区域

两种形状，同一功能可以放多个，取并集。

**连片区域（`flood`）**：把标记放在地板上。从标记正下方的方块出发，在同一 Y 层按四邻接向外扩，凡是材质属于该标记材质集合的方块都算区域地板。材质集合 = 起点方块的类型 + `hardrush.mat.*` 标签。上限 4096 格，超出报验收错误。直觉是“这片绿羊毛就是集结区”。

**方框区域（`box`）**：以标记所在格为底面中心，水平方向各延伸 `x`、`z` 格，向上 `y` 格。用于地板材质与周围相同的地方，例如默认大厅的怪物庭院。

判定（写成核心纯函数 `Zone.contains(x, y, z, staying)`，替代 `LobbyLayout.Circle`／`Box` 和 `LobbyWorld.inAssembly`／`onAltar` 里的几何部分）：

- 连片区域：玩家脚下 `(floor(x), floor(z))` 列存在地板格 `cy`，且 `cy ≤ y ≤ cy + 2.5`（兼容半砖、地毯和跳跃）。
- 方框区域：玩家坐标在方框内。
- 滞回：`staying = false`（进入）用玩家中心点判定；`staying = true`（保持）时玩家碰撞箱四角（±0.3）任一满足即可。替代现在 `+0.35／-0.15` 的半径滞回。

发布时把连片区域解析成具体格子写进大厅包，运行时不再做搜索。

祭坛的粒子、音效、指引光柱位置取玩家所在祭坛区域的几何中心。

## 6. LobbyPlan

核心新增不可变记录 `LobbyPlan`，是运行时唯一的布局来源，取代 `LobbyLayout` 的全部静态成员。核心模块不依赖 Minecraft，自带 `Cell(int x, y, z)`、`Point(double x, y, z, float yaw)`、`Box(Cell min, Cell max)`。

```java
record LobbyPlan(
    Box bounds,
    List<Trigger> triggers,          // 点击与方块类：function、目标方块 Cell（实体触发器为 null）、方块 id、提示用位置 Point
    List<Model> models,              // function、Point
    Map<LobbyFunction, List<Point>> points,   // 各类落点、display_slot
    Map<LobbyFunction, List<Region>> zones,   // Region = 地板格集合 或 Box
    List<Cell> altarLights,
    List<TextSlot> texts)            // function、告示牌 Cell 或 null（text_display 实体靠标签在运行时查找）
```

配套：

- `LobbyPlanValidator`（核心，纯函数）：检查数量规则，返回 `List<Problem>`，每个问题带级别（错误／警告）、功能、位置、中文说明。
- `LobbyPlanJson`（平台模块，用 Minecraft 自带的 Gson；核心没有 JSON 库）：与 `pack.json` 的 `plan` 字段互转。
- `LobbyWorld` 持有当前 `LobbyPlan`，对外提供按功能查询的方法（落点、区域判定、最近设施）。所有调用方从这里取，不再引用静态常量。

## 7. 大厅包格式

单个 zip 文件，扩展名 `.hrlobby`：

```
pack.json
tiles/<tx>_<ty>_<tz>.nbt      每块 48×48×48 的原版结构模板（gzip NBT）
```

- 瓦片索引 = `floorDiv(世界坐标, 48)`，全空的瓦片不写。48 是原版结构方块的单轴上限，所以每块瓦片也能用原版结构方块加载。
- 用原版 `StructureTemplate` 是为了白拿三样东西：方块实体和实体的存取、跨版本升级（DataFixer）、久经验证的放置代码。分块是为了控制内存和分摊到多个 tick。

`pack.json`：

```json
{
  "format": 1,
  "id": "default",
  "name": "默认营地",
  "authors": ["LeifWebber"],
  "version": 3,
  "created": "2026-11-13T08:00:00Z",
  "mod_version": "…",
  "data_version": 0,
  "bounds": {"min": [-24, 63, -16], "max": [39, 70, 31]},
  "plan": { }
}
```

- `id`：`[a-z0-9_-]{1,32}`，等于草稿 id。`version`：每次发布加一。文件名 `<id>-v<version>.hrlobby`。
- `authors`：进入过该草稿的建设者（记在 `draft.json` 的参与者里），4 级 OP 发布时可在菜单里确认或删减。
- `data_version`：发布时的游戏数据版本。

读取限制（防恶意文件）：条目名只接受 `pack.json` 和 `tiles/-?\d+_-?\d+_-?\d+\.nbt`；条目数 ≤ 4096；`pack.json` ≤ 1 MB；单个瓦片解压后 ≤ 16 MB（`NbtAccounter`；一块填满的瓦片约 11 万个方块，带地形的存档导入后会出现这种瓦片）；总解压量 ≤ 1 GB；`bounds` 水平跨度 ≤ `hardrush.lobby.maxSize`；`data_version` 高于服务端时拒绝；`format` 不认识时拒绝。全程在内存里按条目读，不按条目名落盘。

## 8. 清洗

所有从大厅包进入世界的路径（安装到正式大厅、导入为草稿）都经过同一个 `TileSanitizer`，在 DataFixer 升级之后、`StructureTemplate.load` 之前对 NBT 操作。

1. **方块黑名单**，替换为空气：命令方块三种、结构方块、拼图方块、测试方块、刷怪笼、试炼刷怪笼、末地传送门、末地折跃门、幽匿尖啸体、`moving_piston`。
2. **方块实体**：清空所有容器的物品（`Items`、`item`、`RecordItem`、`Book` 等）；告示牌的八行文字剔除 `click_event`、`hover_event`、`insertion`，并把 `selector`／`score`／`nbt` 类文本组件替换为空文本。告示牌点击命令是以 2 级权限执行的，这是最主要的风险。
3. **实体白名单**：`armor_stand`、`item_frame`、`glow_item_frame`、`painting`、`block_display`、`item_display`、`text_display`、`interaction`。其余丢弃。保留的实体同样清洗文本组件，并清掉 `Passengers`。
4. **数量上限**：方块实体 ≤ 4096，实体 ≤ 1024。超出则拒绝整个包。
5. 安装到正式大厅时额外剔除带 `hardrush.marker` 的实体；导入为草稿时保留。

发布时不清洗输出，但验收会列出“安装时将被移除”的内容作为警告。

## 9. 验收

发布前和安装前各做一次，规则相同，输出 `List<Problem>`。有错误不能发布；安装时除“缺少必需功能”走临时设施外，其余错误拒绝安装并保留当前大厅。

- 数量：第 3 节表格的上下限。
- 标记：每个标记的标签能解析；绑定形态是该功能允许的；没有无法识别的 `hardrush.*` 标签。
- 方块：目标方块非空气；`vault`／`ominous_vault` 的方块类型和 `ominous` 属性匹配；`altar_light` 是 `tinted_glass`；`status`／`credits` 的方块是告示牌。
- 点和模型：脚下有实心方块，身体两格不被阻挡（复用 `RoundWorldBundle.safeStanding`）。
- 区域：非空；至少有一格能站人；`assembly` 与 `altar_pad`、`courtyard` 互不重叠；落点不在 `assembly` 和 `altar_pad` 内。
- 范围：全部内容在世界边界内。
- 警告：`display_slot` 少于 10 个；存在将被清洗的内容。

工坊里每 40 tick 对当前草稿做一次轻量验收（只看已加载的标记），结果显示在工具箱菜单的清单里，并用 Boss 栏（走现有 `notice.StatusBars`）提示“还缺 N 项”。

## 10. 安装、切换与存储

### 10.1 存储布局（世界根目录下）

```
hardrush/lobby/packs/*.hrlobby        大厅包库。服主把别人的包放这里，发布也写到这里
hardrush/lobby/installed/<seq>.hrlobby 当前与上一个已安装包的副本，用于回滚和“从当前大厅开始草稿”
hardrush/lobby/current.json           当前安装：seq、维度、包的 id／name／version／authors／sha256、生效 plan、状态
hardrush/workshop/<draftId>/draft.json 草稿元数据：id、name、来源包、参与者、已发布版本号
```

维度：正式大厅 `hardrush:lobby_<seq>`，草稿 `hardrush:workshop_<draftId>`。全部是 Fantasy 持久维度，`VoidChunkGenerator`（群系用平原），主世界维度类型，和平难度，保留 `setFlat(true)`（否则低处天空会变暗），不生成生物、不走天气、不推进时间、随机刻速度 0、禁止传送门。

写文件一律“临时文件 + 原子移动”，路径检查复用 `RoundWorldPaths.checkAncestors`。大厅文件不在 `FullCheckpoint` 的保存范围内（它只保存本轮世界），两者互不影响。

### 10.2 安装状态机（`LobbyInstall`，替代 `LobbyWorld` 现在的施工逻辑）

1. 读包、校验限制、DataFixer 升级、清洗。IO 线程。
2. 打开新维度 `hardrush:lobby_<seq+1>`，对 `bounds` 覆盖的区块加票据并等待加载完成。沿用现有 `LOAD_BUDGET`。
3. 每 tick 放置 1 块瓦片：`placeInWorld`，放置设置开 `setKnownShape(true)`、不忽略实体，更新标志只通知客户端并保持已知形状，避免跨瓦片的门、床被邻接更新弄坏。
4. 等所有区块的实体区段加载完（`ServerLevel.areEntitiesLoaded`），按第 9 节验收。
5. 缺少必需功能时放置临时设施（10.4），得到“生效 plan”。
6. 把包复制到 `installed/`，原子写 `current.json`（状态 `COMPLETE`）。
7. 切换：同一 tick 内把 `LobbyWorld` 指向新维度和新 plan，递增 plan 代数；把旧大厅里的每个玩家传送到新大厅中央落点（`PlayerProfiles.placeInLobby`）；然后删除旧维度（`RuntimeLevelHandle.delete()`）。

任何一步失败：删除新维度，保留当前大厅，把原因告诉发起安装的 OP。

启动时：

- 有 `current.json` 且状态 `COMPLETE`：打开对应维度，直接就绪。
- 没有：从 jar 内默认大厅包安装。失败时沿用现有的 `failure()` 机制。
- 清理：删除 `dimensions/hardrush/` 下所有不是当前大厅、也不属于现存草稿的 `lobby_*` 和 `workshop_*` 目录，以及旧版的 `dimensions/hardrush/lobby` 和 `hardrush/lobby-layout.txt`。当前没有真实用户，不做迁移。

切换条件：`session.state() == OPEN`、本轮处于 `PREPARING` 或 `WAITING`、没有正在保存的完整保存点。

回滚：菜单里选“回到上一个大厅”，就是用 `installed/` 里的上一个副本再走一遍安装。

### 10.3 plan 代数

`LobbyInteractions` 现在按轮次 id 清空注册（`synchronizeRound`）。新增 plan 代数，与轮次 id 一起作为失效条件。`HumanEntry.registeredRound` 同样要在 plan 代数变化时重新注册。数据包模型（`LobbyRoleModels`、`LobbyProjections`）在切换时全部清除重发。

### 10.4 临时设施

对每个缺失的、声明了临时设施的必需功能：以第一个中央落点为中心，在同一 Y 层由近到远（半径 2–8）找一格，要求本格和上一格是空气、下方是完整实心方块、不在任何区域内、离已有落点和设施至少 2 格。

- 点击类：放讲台；`page_prev`／`page_next` 放写好字的橡木告示牌。
- 模型类：只登记一个模型点，朝向中央落点。
- 宝库：放对应属性的宝库方块。

放置发生在切换之前，此时新维度还不是受保护的大厅，可以直接写方块。完成后用 `Notices.operators` 告知“大厅包缺少：X，已在中央落点旁放置临时设施”。找不到位置则安装失败。

### 10.5 掉出大厅

虚空世界里玩家可能走出建筑掉下去，而大厅里伤害被拦截，会一直下落。`LobbyWorld` 每 tick 检查：大厅里的玩家 `y < bounds.min.y - 8` 时传回中央落点。

## 11. 工坊

### 11.1 草稿

- 一个草稿一个维度。同一草稿可多人同时建，多个草稿可同时打开。维度在没人时卸载（`RuntimeLevelHandle.unload()`）。草稿上限 8 个。
- 建造范围用原版世界边界表示：中心默认 `(0, 0)`，直径默认 `hardrush.lobby.maxSize`。中心和直径记在 `draft.json` 里，建设者可在工具箱里“把范围中心设到我这里”和缩小直径（导入的存档里建筑往往不在原点）。**实现时先核实** Fantasy 维度的世界边界是否独立于主世界；如果不独立，退回到坐标检查（放置和移动超出范围时拒绝并提示）。
- 新建方式：从当前大厅（导入 `installed/` 里的当前副本）、空白（在 `(0, 64, 0)` 放一块 5×5 石台）、从包库里的某个文件、从已有存档或建筑文件（第 19 节）。没有任何草稿时，第一次打开菜单自动“从当前大厅”建一份。
- 从包导入草稿与安装用同一套读包、清洗、逐瓦片放置的代码，同样分摊到多个 tick；导入完成前草稿不可进入，菜单里显示进度。
- 最后一名建设者离开时保存维度。

### 11.2 建设者身份（接入 `PlayerProfiles`，本功能风险最高的部分）

背景：大厅里的玩家身体带着本轮的封存档案。`Entry.resume` 是这份档案的权威快照；入场时非新档案从 `resume` 恢复，**新档案直接用身体上现有的状态**。所以建设者的创造背包绝不能留在身体上。

仿照现有的管理旁观（`Entry.adminSpectating`）新增 `Entry.building`：

- **进入**条件：`administrativeBody` 成立、`verifiedLobbyBody` 成立、未在管理旁观或附身观战、`entry.resume != null`、不是已准备的参赛者（与 `RoundRuntime.administrativeSpectatingAllowed` 对参赛者的判断一致）、2 级 OP、阶段允许。已准备的玩家提示“先走出集结区”。
- **进入**动作：`closeSuspendedContainer`、清空背包、传送到草稿（有中央落点用中央落点，否则 `(0.5, 65, 0.5)`）、切创造并开启飞行、发工具。
- **离开**动作：`building = false`，然后把 `entry.resume` 重新装回身体。`prepare()` 的新档案分支里已经有这段代码（`player.load` → `clearLoadedProfile` → `restoreAdvancements` → `moveToLobby` → `resetSentInfo` → `onUpdateAbilities` → 同步背包），把它抽成私有方法 `reloadSuspendedBody(entry)` 两处共用。新档案和非新档案离开时都调用。
- **`tick()`** 里必须注意两点：
  1. 在“代数变化 → `onLogin`”检查**之前**先处理建设者：不再满足条件（阶段不对、失去 OP、代数将变、恢复暂停）就执行离开。否则 `onLogin` 会把创造模式的身体当作原始档案捕获并写入日志。
  2. 循环末尾的“大厅身体校正”（不在大厅就 `moveToLobby`，并强制冒险模式）对有效建设者要 `continue`，和 `adminSpectating` 的处理方式一样。
- **`allowVanillaSave`** 对建设者返回 `false`（与 `celebrationGuest` 相同）。这样断线或崩服时磁盘上保留的是封存的大厅状态，下次登录按现有流程从日志恢复。因此 `onDisconnect` 不需要做恢复，直接丢弃标记即可。
- **`isLocked` 语义不变**（建设者仍然不是比赛身体）。新增 `PlayerProfiles.building(player)`，并在这些闸门上放行建设者：
  - `PlayerIsolationNetworkMixin` 里所有基于 `isLocked` 的拦截（含命令拦截 `hardrush$allowedCommand`）；建议抽一个 `sealed(player) = isLocked(player) && !building(player)`。
  - `PlayerIsolationEntityMixin` 的两处。
  - `simulationFrozen`。
  - `administrativeGameMode`：建设者直接返回 `Optional.empty()` 交给原版，否则 `/gamemode spectator` 会被当成申请管理旁观。
  - `PlayerAdvancementIsolationMixin` 不放行，建设期间不记进度。
- **限制在草稿维度内**：`ProtectionRuntime.rejectMove` 增加一条，建设者的目的地不是自己的草稿维度就拒绝（生命周期的强制返回先执行离开再传送，不受此限）。
- **不会死**：`ProtectionRuntime.rejectDamage` 对工坊维度里的玩家一律拒绝伤害（包括 `/kill` 和虚空）；`y` 低于世界底部 16 格时传回进入点。死亡会进入复杂的重生流程，必须避免。
- 工坊维度**不是**受保护世界（`protectedLevel` 返回 `false`），方块才能改。

建设者拥有 2 级 OP 的全部原版命令（`/give`、`/fill`、`/clone`、`/gamemode` 等）。不额外防范 `/execute in` 影响其他维度：OP 在比赛世界里本来就能用命令，这是服主对 OP 的信任问题。

### 11.3 送回大厅

`Workshop.tick` 每 tick 检查，出现下列任一情况时让对应建设者离开，并用 `Notices.personal` 说明原因：本轮阶段不在 `PREPARING`／`WAITING`／`COUNTDOWN`、`session.state() != OPEN`、正在保存完整保存点、玩家不再是 2 级 OP、服务器停止、草稿被删除。

### 11.4 步行预览

工具箱里的开关：切到冒险模式并关闭飞行，再点一次切回创造。只用来检查走位、跳跃、门。标记照常可见，设施不响应。真正的功能测试在安装到正式大厅后进行，不满意可回滚。

### 11.5 发布（`PublishJob`，4 级 OP，分摊到多个 tick，Boss 栏显示进度）

1. 对草稿范围内的区块加票据，等区块和实体区段都加载完。**实体区段是异步加载的，不等的话会漏掉标记和装饰实体。**
2. 收集标记盔甲架和实体触发器，逐区块扫描非空气方块，得到紧致的 `bounds`（方块范围与标记位置的并集）。为空则报错。草稿设了“底部高度”（19.1）时，低于它的方块不计入。
3. 把标记解析成 `LobbyPlan`（连片区域在这里做搜索），按第 9 节验收。有错误就中止并列出。
4. 每 tick 捕获 1 块瓦片：`StructureTemplate.fillFromWorld(level, 起点, 尺寸, true, [air, cave_air, void_air])`。
5. IO 线程写 zip 到 `hardrush/lobby/packs/<id>-v<version>.hrlobby`，更新 `draft.json` 的版本号。
6. 完成后提示，并在菜单里提供“现在安装”。

## 14. 保护系统

### 14.1 受控写入（先修，独立提交）

**疑似现有 bug**：`ProtectionWorldMixin` 在受保护世界里拦截所有 `Level.setBlock`，没有任何放行。`LobbyWorld.altarLit` 用 `setBlockAndUpdate` 切换祭坛玻璃，且只在 `ready` 之后执行，而 `ready` 之后大厅就是受保护世界。按代码推断，正式服上祭坛光柱永远点不亮。断言它能点亮的 `HumanEntryGameTest` 运行时保护是关闭的（`UnprotectedLobbyFixtures` 的保留名单里没有 `HUMAN_ENTRY`），所以测试没发现。此结论未经运行验证，实现第一步先写一个在正式保护绑定下的 gametest 复现。

修法：`ProtectionRuntime.ownedWrite(ServerLevel, Runnable)`，仅服务器线程，用深度计数在回调期间放行该世界的 `setBlock`。只有模组自己的写入使用（祭坛玻璃切换）。

### 14.2 互动装饰（最后做，可独立延期）

两处放行，都只针对一个固定名单 `LobbyInteractive`：

- 原版标签：`doors`、`trapdoors`、`fence_gates`、`buttons`、`pressure_plates`。
- 方块：`lever`、`note_block`、`bell`、`redstone_wire`、`repeater`、`comparator`、`redstone_lamp`、`redstone_torch`、`redstone_wall_torch`、`target`、`daylight_detector`、`tripwire`、`tripwire_hook`，以及铜灯系列。

1. **玩家输入**（`ProtectionNetworkMixin.handleUseItemOn`）：目标方块属于名单中可手动操作的部分（门、活板门、栅栏门、按钮、拉杆、音符盒、钟），且玩家没有潜行时，放行给原版。潜行时原版会跳过方块交互直接用手上物品，所以继续拦截。
2. **世界写入**（`ProtectionWorldMixin`）：新旧状态是同一种方块、且该方块在名单内时放行。这样门的开合、按钮回弹、红石线充能都能生效，而任何“变成另一种方块”的写入仍被拦截。

活塞（`ProtectionPistonMixin`）、破坏、流体、爆炸、容器保持现状。发射器和投掷器不在名单内，且容器已被清空。

- `SignBlockEntity.executeClickCommandsIfPresent`：告示牌点击命令以 `LevelBasedPermissionSet.GAMEMASTER` 执行。

## 19. 导入已有存档与建筑文件

别的服主很可能已经有现成的大厅。社区里常见的分发形式，按常见程度：

1. **整个存档**（世界文件夹）：大厅、主城类地图最常见的形式。
2. **`.schem`**：WorldEdit／FAWE 的建筑文件（Sponge Schematic 格式），单体建筑最常见。
3. **`.litematic`**：Litematica 模组的投影文件。
4. **`.nbt`**：原版结构方块保存的文件。
5. **`.mcfunction`**：一串 `setblock`／`fill` 命令，多见于转换工具的导出选项，很少用来分发。

导入的结果都是一份普通草稿，之后照常放标记、验收、发布。导入不会带来任何功能绑定，功能需要建设者自己绑。

文件统一放在 `hardrush/workshop/import/` 下，由 4 级 OP 在 `/hardrush lobby` 菜单的“新建草稿”里选择。需要 4 级是因为这一步读取服主放到磁盘上的任意文件。

### 19.1 从存档导入（随 M3 做）

做法：草稿本来就是一个真实维度，所以直接把存档的区块文件复制进草稿维度的目录，再打开维度。区块由原版自己读取和升级，旧版本存档的升级也由原版完成，模组不解析区块。

- 接受两种目录形态：直接含 `region/` 的目录；或完整存档，此时取主世界（新版在 `dimensions/minecraft/overworld/`，旧版在存档根目录）。
- 复制 `region/`、`entities/`、`poi/` 三个目录到 `DimensionType.getStorageFolder(草稿维度, 世界根)`，**必须在该维度第一次打开之前完成**。在 IO 线程做，菜单里显示进度。总大小超过 4 GB 时拒绝。
- 范围中心：存档里有 `level.dat` 就取它的出生点，否则取第一个区块文件的中心。建设者进去后用工具箱“把范围中心设到我这里”调整。
- 这条路径不做清洗：文件是服主自己放到服务器磁盘上的，而且清洗会在发布后的安装环节照常进行。验收会用警告列出将被移除的内容。
- 存档带着地形和生物，工具箱为此提供三个辅助：
  - **底部高度**：把“我脚下这一层以下”排除在大厅之外，记在 `draft.json`，发布时不捕获。避免把整片地下石头打进包里。
  - **缩小范围**：调小世界边界直径。
  - **清除生物**：移除范围内不在实体白名单里的非玩家实体。
- 存档里的模组方块、数据包方块在本服不存在，会变成空气。极老版本存档的升级效果不保证。

### 19.2 从建筑文件导入（M6）

三种格式各写一个转换器，统一转成“带原始数据版本号的原版结构瓦片”，之后完全复用大厅包的管线：DataFixer 升级 → 清洗 → 逐瓦片放置。这样跨版本升级、清洗、放置都不用再写一遍。

| 格式 | 要点 |
| --- | --- |
| `.nbt` | 就是原版结构模板，按 48 格切成瓦片即可 |
| `.schem` | gzip NBT。v2 字段在根上，v3 包在 `Schematic` 下、方块在 `Blocks` 里。调色板是“方块状态字符串 → 编号”，方块数据是变长整数的字节数组，下标 `x + z×宽 + y×宽×长`。方块实体带 `Pos`、`Id`，其余数据在 v2 里平铺、v3 里在 `Data` 下 |
| `.litematic` | gzip NBT。`Regions` 下可有多个区域，每个有 `Position`、`Size`（可为负，负值表示向反方向延伸）、`BlockStatePalette`（已经是原版的 `{Name, Properties}`）、`BlockStates`（长整型数组，每个编号占 `max(2, ⌈log₂调色板大小⌉)` 位，紧密排列、可跨越两个长整型），下标 `x + z×宽 + y×宽×长`。`TileEntities` 为方块实体。数据版本在 `MinecraftDataVersion` |

- `.schem` 的方块状态字符串（如 `minecraft:oak_stairs[facing=north,half=bottom]`）要拆成 `{Name, Properties}`。写成核心里的纯函数并单测。
- 只导入方块和方块实体，**不导入实体**，不支持旋转和镜像。
- 文件视为不可信：同样的大小限制（水平 ≤ `hardrush.lobby.maxSize`，总方块数对应的瓦片限制同第 7 节），同样经过清洗。
- 两种用法：
  - **新建草稿**：建筑水平居中放在 `(0, 64, 0)`，底面在 Y=64。
  - **贴进当前草稿**（2 级 OP，在工坊里）：水平居中于建设者、底面在脚下，不覆盖空气。没有撤销，菜单里二次确认。
- 仓库里放三个很小的样例文件做测试，用真实工具导出。

### 19.3 不专门支持的形式

- **`.mcfunction`**：不需要专门支持。建设者在工坊里有 2 级 OP 的全部命令，把文件放进数据包后在工坊里执行 `/function` 即可。注意两点：命令里是绝对坐标时会建在那个坐标上；大建筑可能超过单次函数的命令数上限。模组不替服主执行这类文件，因为它可以包含任意命令。
- **旧版 `.schematic`**（1.13 之前的数字 id 格式）：先用 WorldEdit 载入再另存为 `.schem`。
- 服主自己装了 WorldEdit 的话，也可以直接在工坊里用它的命令粘贴，与本功能互不影响。
