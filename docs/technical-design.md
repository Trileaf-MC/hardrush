# HardRush 技术设计

推荐采用 Fabric 服务端模组、独立于 Minecraft API 的 Java 规则核心、SQLite 持久化，以及按 Minecraft 版本隔离的适配层。大厅长期加载，每轮创建并管理三个持久维度。纯原版客户端、旁人完整怪物外观与本人正常操作、模组内部轮换是设计约束；本人普通外观已于 2026-10-14 获得用户明确允许。

本设计定义目标架构。当前已有 26.3 P0 外观、单轮三维度及真实角色原型；用户双原版操作验收已通过并接受轻微尺寸差异，完整 P0 验收仍未放行。2026-10-14 按用户指示提前交付 P1 第一批独立规则、不可变配置、SQLite 幂等基础和轮次／计时核心，见 [实现与验证](p1-foundations.md)。随后交付 [P1 第二批](p1-world-profiles-combat.md) 的实际世界准备、登录／跨轮档案隔离、普通模式加入与死亡计时、攻击因果证据；[第三批](p1-terminal-rotation.md) 已实现普通／开发适配的首龙唯一终局、schema 3 原子记录、庆祝与自动轮换，139 项 JUnit 与 52 项必需无图形服务端 GameTest 通过。第四批已接通统计／分榜／TAB／历史书，第五批已完成[基础管理确认、审计与成绩修订](p1-admin-controls.md)，209 项 JUnit 和 62 项必需无图形服务端 GameTest通过。极限完整玩法、连续 10 轮与其他版本最终适配仍待开发／验收，实验 JAR 不作为正式发布包。依赖证据见 [版本与依赖核查](compatibility.md)，产品规则见 [产品需求](requirements.md)，阶段与任务状态见 [开发任务清单](implementation-plan.md)。

## 工程结构与版本适配

当前 P0 使用 Java 25、Gradle Wrapper 9.6.0 和 Fabric Loom 1.17.21。26.1 已切换到非混淆发布及新的 Loom 插件方式，不能照搬旧版本 `modImplementation` 和 remap 插件配置；另外两个目标版本仍须单独验证构建配置。[Fabric 26.1 迁移说明](https://fabricmc.net/2026/03/14/261.html)、[Fabric 26.3 开发说明](https://fabricmc.net/2026/09/15/263.html)。

目标目录及当前状态如下；已有目录不代表其中的完整职责已经实现：

```text
core/                  已实现轮次／身份／计时核心、配置与纯 Java 接口、攻击因果及首龙尾刀裁决
persistence/           已实现 SQLite schema 3、事件／版本、操作三阶段、有界证据与原子终局；统计／分榜索引待扩展
integration-contracts/ 当前接口在 core/api；26.3 已有世界／档案／攻击与录制停止门槛；真实录制器／GUI 待接通
platforms/mc2612/       待建；26.1.2 Fabric 适配
platforms/mc262/        待建；26.2 Fabric 适配
platforms/mc263/        已有 P0 主代码、JUnit、GameTest 和隔离 debugTools
probes/p0b/             已有三版基础依赖／SQLite／原版容器探针，非完整平台适配
test-support/          当前假时钟、重放、故障注入和契约测试在各模块 JUnit 测试源码中
```

核心代码不得引用 Minecraft 实体、网络包或 NBT 类。共享接口包括 `RoundWorldManager`、`PlayerStateGateway`、`DamageAttributionGateway`、`DisguiseGateway`、`BookGateway`、`ReplayGateway` 和 `ProtectionGateway`。接口方法名是设计契约，不是已存在的库 API。

每个适配器使用目标版本对应的依赖、映射和必要 Mixin。优先 Fabric 公共事件；不可替代的龙伤害、传送门、伪装和保存钩子局限在适配器。构建产物命名为 `hardrush-<modVersion>+mc<version>.jar`，元数据精确声明支持范围。社区安装指南给出对应依赖清单、校验值和许可证；只有许可证及加载方式允许的公共库才内嵌，不打包 Minecraft 代码。

## 状态与线程模型

轮次状态建议为 `PREPARING → WAITING → COUNTDOWN → RUNNING → SETTLING → CELEBRATING → ROTATING`；运行中可进入 `RESCUE`，再回 `RUNNING` 或失败结算。异常统一进入 `RECOVERY_REQUIRED`。失败结果使用大厅展示阶段，不套用通关最多 180 秒庆祝。

计时是否活跃与轮次生命周期分开：`RUNNING` 且在线人类数大于零时运行计时器。普通模式还需要 `HUMAN_RESPAWNING` 状态，死亡画面中的玩家暂不推进“活人在线”计时，但仍保留可重生资格，绝不触发极限团灭。

身份建议为 `LOBBY`、`HUMAN_ACTIVE`、`HUMAN_RESPAWNING`、`MONSTER_LOBBY`、`MONSTER_DEPLOYED`、`TRANSITION_PENDING`。在线状态、怪物类型、复生资格、生命序号、出场序号与身份分开保存。`gameMode` 和客户端外观都不是身份的可信来源。

所有游戏状态变更在服务端主线程串行仲裁，Minecraft 实体、区块、传送和容器操作只能在该版本允许的线程执行。独立线程承担 SQLite、压缩归档和不可变快照计算，完成后携带轮次 ID、操作 ID 与状态版本回到主线程；过期回调不能改变新轮次。

关键操作先锁定相应对象为待提交状态，暂停冲突操作，再异步持久化，成功后开放结果；不在主线程等待大文件 IO。数据库写入失败不能让复生、发奖或换局“看起来成功”，应隔离受影响玩家并进入恢复状态。

## 时间实现

运行进程内使用单调时钟累计经过量；需要落盘的量使用累计毫秒和服务器运行倒计时剩余毫秒。UTC 墙钟只作审计日期及允许离线流逝的技能冷却期限，不用它直接减出比赛成绩。

每次在线人类数从 0 变为正数、从正数变为 0、身份改变、停服和结算都关闭当前计时间隔并落盘。救场、开局和庆祝有独立的服务器运行时间计数。暂停竞速计时不能直接取消整个世界 tick，否则会改变怪物、传送门和回放行为。

建议每秒写入轻量计时检查点，正常停止时完成最后保存并关闭世界。崩溃恢复以最近成功持久化的累计量为准，不计停服时间、不用墙钟猜测丢失区间。保存延迟会扩大不确定范围，因此记录 `lastDurableCheckpoint` 和恢复标记；有未确认时间区间的成绩进入待核验。启动时系统墙钟倒退会影响冷却，应保留日志并限于该冷却处理，不能改变竞速计时。

26.3 P1 将首龙不可逆致死事件的 `observedNanoTime` 作为停表与庆祝的起点；2026-10-16 起庆祝上限改为 180 秒。捕获后立即冻结新竞技行为，等待同批原生调用结束及 SQLite 终局提交；提交延迟消耗庆祝剩余量，不增加挑战成绩，也不在回调时重新起算 180 秒。正常停止先调用 `prepareStop()` 捕获边界并收齐已受理终局，再等待档案／回放／世界 IO 和数据库队列；排空耗时不计挑战或庆祝。正常重开只消耗已保存的剩余服务器运行时间，停服时长不扣倒计时；脏标记仍进入 `RECOVERY_REQUIRED`，没有用墙钟补猜。

26.3 P1 的正常 `COUNTDOWN` 恢复在 Session 中单独暂挂：启动把已保存连接标记为离线，不代表玩家主动下线。原三维度 READY 后仍保留已保存的剩余量与 ready 标记，每秒只写检查点；等待停服前已 ready 的同一 UUID 完成档案核验并上线，才从原剩余量继续。其他 UUID 的连接不能替代该恢复门槛，暂挂期间加入／就绪请求会说明等待原因；原 ready 玩家先完成档案核验时，其上线状态保留到世界门槛通过后应用。暂挂期间再次正常 stop／新进程恢复仍保留剩余量；dirty 恢复仍走 `RECOVERY_REQUIRED`。恢复放行后继续按原规则处理：最后 ready 玩家取消就绪或断线即取消倒计时，下一次 ready 重新从规则的完整 30 秒开始。此修复不冻结世界模拟，不替代后续人类实际入场的档案与在线计时门槛。本批整服自动覆盖与结果以最终回归记录为准。

正常停止时，原版服务端先设置 stopped 再执行停止监听器，`server.execute()` 此时可能直接在提交它的 IO 线程执行。P1 轮次及默认档案回调在实际执行处检查服务端主线程；停服期间只排空已受理的 SQLite／journal IO，不在 worker 应用玩家、容器、TAB 或引擎副作用。状态由主线程 `close()` 接收并保存，未完成的档案转换保留持久化步骤供下进程核验恢复。真实整服停止夹具同时断言两类回调未越过主线程边界。

## 世界创建与轮换

使用 Fantasy 持久世界作为候选，禁止将需要重启恢复的正式轮次建成临时世界。Fantasy 的持久世界需要应用在重启时用同一标识和配置重新打开，不能假设库自动恢复所有世界。[Fantasy 文档](https://github.com/NucleoidMC/fantasy)。

每轮先持久化 `roundId`、种子、三维度注册键、生成器配置、维度类型、难度、规则快照及拥有路径，再创建世界。三个维度共享本轮种子，并沿用对应维度的原版生成规则。大厅不归任何一轮所有，不参与旧轮清理。

主世界、下界和末地组成一个明确的 `RoundWorldBundle`。需要显式验证和适配：

1. 主世界与下界 8∶1 传送关系、传送门查找和新建必须落在本轮配对维度，不能落回大厅基础世界或上一轮。
2. 末地传送、到达平台、末影龙战斗管理器、龙 UUID、出口传送门及龙重生状态均绑定本轮末地并持久化。
3. 返回传送门、死亡重生、床、重生锚、末影珍珠、载具和断线恢复都经过身份与轮次路由。
4. 不能只用 `dimension == minecraft:the_end` 判断末地。统计和本轮原版进度条件需要受控映射自定义维度到语义维度；Mixin 必须仅影响 HardRush 拥有的世界。
5. 默认世界全局存储的比分板、地图、玩家进度、配方和 bossbar 不能意外跨轮复用。保存恢复必须对玩家档案与世界全局数据分别处理。

新种子可以在通关庆祝期间准备。只预算化加载自然出生点附近及必要到达区域，不承诺庆祝结束前生成完所有世界。2026-10-16 起不修改主世界出生地形，不生成石台、台阶、护栏或出口；只读选择安全站位，保留原版末地到达平台。正式轮次不注册出生保护区，大厅仍全区保护；旧清单的出口和快照的离区字段仅兼容保留，不参与正式出生准入。使用受控任务队列及已支持的区块生成机制，不把任意 Minecraft 世界操作丢到异步线程。世界准备失败时记录阶段和错误，玩家等待大厅，保留可重试任务。

轮换顺序：捕获终局时刻并冻结逻辑结果及新竞技交互 → 持久化结算 → 公布结果并庆祝 → 在线全员回大厅或庆祝到期 → 全体转大厅并关闭容器／载具 → 停止旧轮录制并等待结果 → 保存并关闭旧世界 → 开启下一轮就绪流程 → 按策略归档与清理旧文件。通关停表与庆祝倒计时以捕获的通关时点为基准，数据库提交延迟不能增加成绩或重新开始三分钟。归档可以晚于新轮次开放，但原世界必须已关闭，录像保存任务不能仍持有待清理文件。

当前普通／开发实现进一步等待所有在线受管玩家的旧代数档案核验，再释放世界。`P1RoundWorldBundle.saveAndClose()` 在异步任务上重读清单及检查路径，主线程验证玩家撤离、维度实际注册对象／持久属性／轮次种子与存储路径；等待 Fantasy 三维度注销，随后显式关闭 native `ServerLevel`／region IO，完成结果才允许创建下轮。`CLOSING`／`CLOSE_FAILED` 保留轮次持有权，不能靠重开同 ID 取消卸载；失败保留文件，修复后可重试关闭 API。正常停服另用 `shutdown()` 保存，仍注册的世界由原版关闭循环释放。当前没有自动递归删除或归档，完整保留策略仍属于 P3。

文件操作仅作用于清单中明确归 HardRush 所有、且规范化后仍位于允许根目录内的路径。拒绝根存档、大厅、未登记世界、符号链接逃逸及当前活动轮次；先记录待归档任务，再移动／压缩，核验后标记完成，最后才允许按已配置策略删除源。不能在世界已加载时递归删除目录。

26.3 P3 的整服强杀回归使用仅测试模组的 SQLite trigger／function 和提交回调屏障，由父进程对自己的专用服务端子进程发送 SIGKILL。资格发放、消费及终局分别覆盖快照写入、索引写入和提交后回调前；恢复时保留原始脏检查点，只在内存建立 RECOVERY_REQUIRED，重复正常停止不能借此清除隔离。世界／档案文件保留且旧维度不重新模拟；详见 [整服强杀记录](p3-server-crash.md)。档案 journal 的整服各写盘窗口、不确定状态修复及继续原活动轮仍未覆盖，不能把隔离等同于恢复可玩。

第四批随后用外部 JDI 方法返回事件补充首次入轮的 PREPARED／目标快照已落盘／APPLIED／VERIFIED 四窗口，核对 VM PID、档案 worker 和玩家 UUID 后冻结全部线程，再由父 runner SIGKILL。测试专用的原生旧玩家基线、双新 JVM 重连、journal 阶段／封存／目标标记与原生 `players/data` 摘要均核验；不在正式 journal 加测试开关。详见 [档案强杀记录](p3-profile-crash.md)。跨轮整服档案转换、不确定资料处置和继续比赛仍未完成。

## 登录隔离与玩家档案

采用“轮次代数 + 玩家本轮档案 + 待执行转换”恢复玩家。网络登录完成到开放移动、容器和攻击之间设置隔离门；登录时必须先确认该 UUID 对应的本轮和转换状态。

- 同轮普通重连：恢复该身份和档案；外出怪物按需求返回大厅。
- 离线跨轮：将旧档案封存，执行新轮次重置，然后才允许加入；不能让旧背包先进入世界一刻。
- 人类死亡转怪物：先记录死亡，再发放受控角色装备，不能保留活人物资。
- 怪物复生：资格锁定并提交，保存新的生命序号，执行空装、状态清理和安全传送，完成后开放人类行为。

跨轮完整重置覆盖背包、装备、副手、末影箱、光标物品、已打开容器、经验、生命、饥饿、药效、属性修饰、飞行权限、床／锚、重生点、维度坐标、乘坐状态及必要的进度和配方缓存。原版累计统计与本轮统计分开；需要重置的原版展示项先按版本验明边界，不能随意删除整个玩家目录。

本轮死亡／复生使用独立转换，不能调用跨轮完整重置。普通重生保留有效床／锚、本轮末影箱及进度；极限死亡先按原版处理随身物品掉落，怪物期间隔离人类储存和物品交互，复生清除角色装备并恢复人类生命、饥饿、效果及权限，固定回本轮出生点而忽略旧床／锚。两种模式都保留本轮末影箱内容、进度、末地首次进入、参赛历史及应继续保留的技能冷却。复生不恢复死亡掉落物；全局原版档案字段的隔离范围需逐项实现，不能因方便而全删。

档案转换与世界文件不具有数据库级原子性。用 `PREPARED → APPLIED → VERIFIED` 的转换任务加玩家代数标签恢复；重启遇到待转换玩家先送大厅，根据已提交转换重新应用确定的目标状态。不能因为看到背包为空就认定资格已经消费，也不能因看不到实体就补发一份资格。

2026-10-15 第六批修复已连接玩家悬停顺序：捕获原档案后仍保留源 `ServerLevel`，通过原版传送同步迁移实体和玩家登记；不能先修改世界字段，否则后续同世界传送会残留旧维度玩家引用。登录前尚无连接的玩家继续直接设为安全大厅。原生列表撤离、同轮重连、跨三轮隔离与十轮实际世界关闭的自动证据见 [第六批回归](p1-ten-round-regression.md)；整服世界＋档案新进程恢复仍待验证。

## 伪装与战斗实体

保持服务端受控玩家作为移动和操作主体，仅向其他观察者发送所选怪物的原版实体包。本人的实体元数据、玩家模型、相机和 F5 切换保持原版路径，不生成本人怪物替身，不通过伪装额外设置本人隐身或私有隐藏队伍；玩家本身的正常状态仍由权威数据同步。现有 P0 的旁人实体替换路径可作为实现基础，DisguiseLib 或 Polymer 仅作为候选工具。只使用原版僵尸、骷髅、苦力怕及原版技能物品，不注册客户端必须认识的新实体类型。

当前 P0 实际使用自有数据包原型，没有将上述伪装候选库作为已采用方案。旧完整尺寸本人替身在第一人称遮挡并参与选取；手动 `selfview hidden|visible` 仅用于诊断，hidden 仍隐藏本人玩家模型。新实现已移除本人替身／额外隐身／私有队伍路径及相机实验，保留旁人外观替换，取消空装备限制；重连和原版死亡重生按 UUID 重新绑定权威玩家，换维度不恢复旧 self-view。本人使用固定 Steve 皮肤资料，仅改发给本人的外观包，不修改服务端认证 profile；解除恢复原皮肤。26.3 的本人皮肤缓存通过同维度原版客户端 respawn 包刷新，随后同步位置、能力、生命／饥饿、经验、效果和背包；不进行服务端死亡或重生。乘坐、睡眠、使用物品、相机不在本人或打开容器时延迟到安全点刷新。实现与验证见 [新外观记录](p0-observer-appearance.md)，旧实验见 [自身外观记录](p0-self-view-evidence.md)。

原型必须同时验证旁人完整怪物外观、本人普通玩家的前后 F5 与第一人称可操作性，以及影子、手持物、动画、重连、传送、复生和伪装解除。本人普通外观是显示规则，不改变怪物身份、属性、技能或攻击白名单。不能要求玩家执行会安装客户端内容的操作。

2026-10-14 用户随后要求真正接近原版怪物行为，已提前增加独立角色服务：原版属性／近战／怪物箭／普通苦力怕爆炸、2 只幼年僵尸和三连射。用户撤销装备总禁令后，本轮加入僵尸／骷髅的原版自动拾取／装备比较，实际装备独立于技能栏；世界拾取物按来源返还，系统弓／控制物不产出物资。网络与实体入口继续限制人工背包换装、普通物品使用和容器，不能借穿戴装备获得人类能力；外观诊断与真实角色分开。实现、数值来源、会话恢复以及尚未接入的赛制／大厅／资格边界见 [真实角色记录](p0-monster-roles.md)。

玩家本体、旁人可见怪物实体与攻击命中盒需要一个明确映射，不增加本人替身。外观不得有第二套生命、独立掉落或重复受伤。来自客户端的实体交互按可见 ID 映射到唯一受伤目标，同时检查攻击距离、视线、轮次与身份。禁止不可见残留实体受击、打中模型无反馈及通过伪装绕过服务器距离检查。

原版客户端本地移动预测不会因服务端把外观换成怪物自动采用该怪物碰撞体。2026-10-14 用户在双原版人工检查后明确接受小尺寸差异：原版玩家站立／蹲下／游泳碰撞分别为 0.6×1.8、0.6×1.5、0.6×0.6，旁人按所选原版怪物进行本地选取。保留单一真实玩家的移动和受击判定，原版实体 ID 直接对应该玩家，不增加攻击代理实体；三种站立模型的 1.95／1.99／1.7 高度差异被接受。移动、门洞、台阶、游泳及近战／弓箭的人工结果为“全部符合预期”；具体尺寸、回归和截图归档边界见 [新外观人工验收](p0-appearance-manual.md)。正式战斗的身份、攻击白名单及距离检查仍由后续规则控制器实现。

技能用服务端身份和不可伪造的技能槽映射授权，原版物品只是操作入口。一次施法分配唯一 ID，在提交冷却后创建带有归属标签的实体；重复包、重连和恢复不能重复召唤。召唤物保留原版自然消失，所有实体查询和寻路调度只优化计算成本，不引入人数、时长或召唤数量限制。

## 伤害与归因

伤害进入统一规则入口，按攻击来源快照和当前目标校验。建议事件字段为：`eventId`、`roundId`、服务端序号、来源种类、主人 UUID、创建时身份、生命／出场序号、直接实体 ID、受害者 UUID、当前身份、原始伤害源和因果父事件。

攻击白名单必须在实际伤害、击退、点燃和负面效果应用之前生效；只取消最终扣血会留下非法击退或状态影响。怪物来源永远不能伤龙、水晶、其他怪物或不合法玩家；主人后来复生也不能将旧怪物箭矢洗成人类攻击。人类原先射出的箭，也不能因为射手后来死亡而变成赚取复生资格的怪物箭。

苦力怕使用目标版本真实普通苦力怕爆炸路径，或者经对照验证完全等价的适配路径；复生归属用旁路事件字段保存，不篡改原版伤害类型。过滤爆炸受害者及方块破坏时，需要同步检查传给客户端的爆炸击退、音效和粒子。

床、锚、TNT 及水晶引爆在动作入口保存因果信息，链式爆炸只有可可靠追踪时才继承。末影龙分部命中合并到同一龙死亡事件。不要以 `getKillCredit` 一类可能使用历史仇恨／最近攻击的结果直接替代实际致死来源。

一次可能连带多个死亡的事件批次执行：

1. 固定轮次与来源身份快照，收集实际死亡。发现龙不可逆死亡时立即捕获单调时钟和成绩快照，锁定终局候选，完成当前伤害批次后阻止新的竞技动作。
2. 对每个死亡分配唯一事件并计算复生奖励；主人致死时仍属怪物才可奖励，离线不影响。计算人类死亡、自爆回大厅和资格发放后的目标状态。
3. 在目标状态上先判断龙通关；同一批次内同归于尽时通关优先，按真实人类攻击保存胜者。没有通关才检查人类及复生资格，确定继续、暂停、救场或团灭；此时捕获相应状态改变时间。
4. 将计算结果置于待提交状态，以唯一约束和版本提交死亡、非叠加资格、身份转换计划、终局及审计；事务不成功就不公开为已完成结果。
5. 提交成功后幂等应用大厅安置等转换、公布结果和推进阶段。沿用事件发生时捕获的时间，不在数据库回调时重新停表；提交失败进入恢复状态。

救场到期前已受理的复生请求进入 `TRANSITION_PENDING` 并阻止竞态团灭；事务成功后恢复人类，失败则进入恢复处理，不能默默吞掉资格。已结束轮次拒绝所有迟到伤害、奖励、技能和异步回调。

当前 P1 首龙判定由平台先核对本轮 END 中的实际 `EnderDragon`、原生 fight 的龙 UUID 和 `hasPreviouslyKilledDragon=false`，核心再按攻击创建时封存的人类身份／生命序号裁决尾刀。捕获候选后只放行同 `batchId` 已开始的伤害链；最外层原生攻击／爆炸结束触发 `batchClosed`，统一提交同批人类／怪物死亡与资格；首龙完成使用唯一终局事务。因此人类已创建的箭或爆炸不会因本人同批死亡／下线而失去尾刀归属。未知、旧轮、怪物或未参赛来源不指定胜者，实际首龙死亡仍形成通关与待核验原因；后续复召和重复回调不能改已有结果。2026-10-15 P2 已接通极限资格发放、主动消费与救场／团灭；原生死亡批次使用 `DEATH_BATCH`，终局持久化同时接受既有 `FINISH` 与该批次标签并保持原始首龙证据检查。复生先提交资格与生命，安全安置且档案写盘成功后才解锁身体与在线计时；完整实现与证据见 [P2 复生与救场记录](p2-revival-rescue.md)。真实客户端仍需单独验收。

## SQLite 与事件幂等

数据库放在独立于单轮世界的 HardRush 数据目录中，启用外键、迁移版本和适合单写者的 WAL 模式。具体驱动和文件锁行为由三平台构建验证。建议模型如下：

| 表或集合 | 关键字段与约束 |
| --- | --- |
| `rounds` | 轮次 ID、顺序号、状态、结果、模式、种子、配置指纹、累计时间、版本、结束事件；结束事件唯一 |
| `participants` | 轮次与 UUID 联合唯一、名字快照、当前身份、生命序号、在线会话、人类资格、复生布尔值、状态版本 |
| `participant_progress` | 轮次、UUID、进度 ID 唯一，取得时间；末地首次进入另存唯一事件 |
| `life_events` | 死亡／复生事件、来源及前后生命序号；事件 ID 唯一 |
| `combat_events` | 需要持久化的致死因果、关键龙伤害、异常归因；不记录每个游戏刻全部战斗细节 |
| `cooldowns` | 轮次、UUID、技能 ID 唯一，到期时间、最后施法事件 |
| `world_manifests` | 三维度键、所有权、路径、配置、世界代数、保存及关闭阶段 |
| `operations` | 发奖、复生、重置、轮换、归档及恢复任务，操作 ID、阶段、重试次数、前置状态版本 |
| `recordings` | 轮次、玩家或区域、录制器标识、片段路径、格式、保存结果及错误 |
| `book_deliveries` | UUID、源轮次、书版、卷号和自动发放键，待领／已领状态 |
| `admin_audit` | 操作者、操作、对象轮次、原因、前后值、发生时间 |

投票是可丢失的临时会话状态，重启后重新投票，不必每次点选强制写盘。关键死亡、奖励、消费、结束和世界所有权必须持久化。召唤物实体标签是恢复归属的入口，数据库事件是资格发放依据，两者不得互相替代。

数据库中的多表状态可以在单事务提交；Minecraft 世界文件、客户端包和录像文件不在同一事务中。系统只承诺通过幂等操作与恢复取得一致结果，不声称跨这些系统天然“恰好一次”。

当前落地的表名与上述目标模型分别记录：P1 使用 `round_snapshots`、`store_events`、`operations`、`pending_rules` 等基础表，schema 2 增加 `evidence_events`，schema 3 增加 `round_terminals`。`commitTerminal` 将实际致死证据、原始 SETTLING 快照、全局 FINISH 事件及每轮唯一终局行放进同一版本 CAS 事务；任一写入失败全部回滚。原终局快照和因果 payload 保留摘要，后续庆祝／停服检查点只能推进阶段／版本，不能修改胜者、已停止成绩、规则、种子或轮次身份；相同操作可重放，冲突内容拒绝。schema 2→3 的 DDL 与迁移版本一起提交，历史已有结果保留，不为旧数据伪造首龙因果。2026-10-14 第四批已接通 schema 4 的 `history_rounds`、`participant_records`、`progress_events`、`round_advancements`、`advancement_sets` 和 `book_deliveries`：快照事务投影参与者，进度按 UUID／ID 去重并记录集合指纹，首次终局冻结历史；只按完整规则指纹纳入可信、计时确定的通关记录。TAB 和原版成书经独立适配器展示；库存原版保存回读核验后才 ACK 自动书册，满包保留待领。详见 [P1 第四批记录](p1-records-books.md)，第五批schema 5增加原子管理审计、原历史副本和按书版CAS追加修订；原始终局／因果保留，CORRECT先转待核验，VERIFY仍要求原始可信胜者。详见[P1第五批](p1-admin-controls.md)；跨系统强制终止窗口仍待P3。

## 防作弊与回放

防矿透使用 AntiXray 候选。它的默认配置并不自动保护任意动态维度；新轮次的每个维度必须在第一份区块数据发送之前得到对应规则。优先使用经核查可用的加载期配置／适配入口，无法热注册时设计显式适配，不能边发送真实矿物数据边补配置。[AntiXray 自定义维度配置](https://github.com/DrexHD/AntiXray#custom-dimensions)。

Grim 作为移动、攻击距离等检测的候选，不能把安装它等同于杜绝 KillAura。版本发布元数据和 README 对 26.3 支持存在差异，须选择明确构建并验证。角色速度使用服务端正式属性更新，传送和伪装通过兼容接口同步，不全局豁免玩家怪物来掩盖误报。默认记录和通知管理员，不因单次启发式告警永久封禁；具体自动处罚规则在检测验证后单独配置。

HardRush 自身仍执行权限、阶段、攻击目标、技能冷却、交互距离及物品转移校验。集成配置为 `off / optional / required`，状态在管理员界面明确显示；`required` 不满足时禁止开局，`optional` 失败时提示并把保护状态写入本轮记录。发布包的推荐防护组合必须三版本分别验收。

ServerReplay 通过可选适配器管理轮次录制片段，保留原本由管理员管理的录像文件。当前版本的格式与 API 以实际发行源码为准，不能仅照 README 假定一定生成 `.mcpr`。玩家断线可能结束录制，重连需建新片段并关联同一轮；角色变换、跨维度及虚拟外观都须回放验收。[ServerReplay 文档](https://github.com/senseiwells/ServerReplay)。

P1 第三批目前提供 `ReplayPort` 的停止／保存门槛，没有安装真实录制器。未安装时明确记录 disabled，不声称产生或保存了录像。已安装时要求 `stopAndFlush` 返回同轮、同操作标签的 `VERIFIED` 结果，结果缺失、不可信、失败或旧轮回调均不能触发世界释放。正常停止等待独立 IO 保存屏障，避免等待需要主线程执行的释放回调而死锁。真实片段建立／重连、文件播放验证、失败重试及管理员确认跳过仍待 P0b／P3。

默认自动管理的录制在开局／加入时启动，轮次冻结后持续到庆祝结束或按明确配置截止。停止后等待写入完成，再释放旧世界。保存失败时保留旧世界和现有片段，允许重试；默认停留大厅。管理员可明确确认跳过失败录像后开启下一轮，但旧文件仍保留，轮次标记录像不完整。未启用回放集成时不得假装已有录像。

## 恢复与运维

| 故障点 | 恢复行为 |
| --- | --- |
| 只保存了种子／清单，世界未创建完整 | 在大厅重试同一轮次任务，不另换种子冒充同一轮 |
| 正常重启活动轮次 | 登录先在安全大厅隔离；重开并核验同一三维度后恢复累计时间与身份。COUNTDOWN 另等待原 ready UUID 档案上线，从保存剩余量继续 |
| 崩溃后世界／玩家档案与事件不一致 | 保持大厅隔离，根据操作阶段核对；无法判定则人工恢复 |
| 资格已提交但尚未显示或传送 | 重放同一操作，不能再次消费资格 |
| 世界已经关闭、归档尚未完成 | 继续归档任务；不重新打开给玩家游玩 |
| 录像停止／保存失败 | 留存文件，禁止自动清理，按已说明的重试或管理员跳过流程 |
| SQLite 不可写、磁盘不足 | 暂停受影响状态转换和新开局，保留诊断，不删除资料腾空间 |

备份使用 SQLite 一致性备份机制并配合已关闭世界的清单，不能只复制正在使用的主数据库文件而忽略 WAL。备份记录模组、MC、依赖版本和文件校验；恢复演练验证 UUID、资格、成绩和录像索引。配置升级先检查 schema，迁移失败保留原文件并停止开局。

2026-10-15 P3 第一批补充了真实 SQLite READONLY／FULL／事务中途失败及独立 JVM 强终止矩阵，恢复仍停在大厅隔离。跨轮档案的既存 PREPARED／APPLIED／VERIFIED 仅重用带匹配轮次／代数／悬停标记的持久目标快照，不重复执行新轮重置；缺快照或身份不确定时报错留厅。世界准备在 IO 线程检查实际写入／fsync 和默认 512 MiB 可用储备（`hardrush.p1.minimumFreeBytes`），准备期间异步复检，存储失败保留半完成世界并按原轮重试。停服排空还核对异步任务结果，不能把 worker 失败误作正常结束。完整恢复决策、失败 Session 重新核验、整服联合强杀、归档／回放和备份闭环仍未完成，边界与操作流程见 [P3 第一批记录](p3-crash-storage.md)。

2026-10-15 P3 第二批补充了已有轮次 FAILED 会话的显式存储重核：排空 IO／回调、重开原库并检查完整性／外键／身份／历史，恢复快照与审计同事务提交；成功只进入 RECOVERY_REQUIRED。OP 4 可确认结束恢复轮，保留已有终局或将未结算轮记待核验中止，资格／生命不重放，再经过档案／回放／世界原有安全门槛轮换。上一进程已关闭的故障世界只读核验清单和路径，不重新模拟、生成或删除。重核中停服排空事务并保持隔离。具体命令、故障边界与证据见 [P3 第二批记录](p3-recovery-controls.md)；继续原活动轮、档案不确定状态修复、整服联合强杀、归档／回放和备份仍未完成。

默认正版身份认证，历史按 UUID 追踪；代理服的可信转发和离线账号模式是另行验证的部署配置，不自动相信客户端传来的 UUID。原始日志、存档和录像只在服主文件系统内保存，不为本期额外开放 Web 后台或下载端口。

## 性能设计

在线人类及可追猎候选维护索引；TAB 增量更新，投票每 15 秒计算，安全点搜索分摊执行，实体归属查询按 UUID／实体 ID 索引，历史书按需分页。世界生成、录像压缩和备份分别度量，避免将它们混入日常战斗平均值掩盖峰值。

以选定并记录的部署硬件、视距、模拟距离和集成配置建立约 20 在线玩家基线。召唤物无玩法数量上限，但硬件容量有限，必须测试 50、200、500 个活跃召唤物等明确负载并记录结果；不能承诺无限实体保持恒定 TPS。性能不达标时先优化寻路与扫描、IO 和世界生成预算，不能偷偷添加怪物人数或存活时间限制。

## 2026-10-16 庆祝与返回大厅

成功庆祝由 `P1CelebrationRuntime` 在终局持久化后建立固定末地在线名单；名单、原档案、临时装备检查点和 returned 标记通过档案单线程 worker 写入校验摘要和原子替换文件。先保存原档案，再应用装备，临时装备检查点落盘后才解锁；重连恢复剩余物资，returned 玩家保持大厅。原档案另用于跨轮归档，临时装备不替代旧轮原物资。怪物庆祝暂时撤销表现层且不掉落装备；结算身份不改变。

原生末地出口在查找床／锚前拦截，返回操作先落盘再进入 `hardrush:lobby`。只放行标记庆祝烟花、滑翔及个人临时背包整理；烟花对方块的使用直接调用物品逻辑，避免顺带操作容器。竞技伤害、建造、外部容器及丢弃／拾取仍锁定。

默认成功时长与运行上限均为 180000 ms。RoundSnapshot 编码 v5 标记已封顶计时语义，v1～4 成功 SETTLING／CELEBRATING 快照扣除原配置超出三分钟的部分，保留已耗时；原规则和成绩不改写。在线全员完成返回后，Session 通过版本校验提交 CELEBRATION_COMPLETE；时间到则统一撤离，仍等待档案、回放和旧世界 native IO 关闭后才创建唯一下一轮。正常 stop 保存临时状态并排空档案队列，不把停服墙钟计入余量；无在线玩家也可以提前结束庆祝。
