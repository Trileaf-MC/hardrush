# HardRush 26.3 无指令大厅五轮交付计划

日期：2026-10-16。状态：规划已落库，五轮开发均未开始。

按五个 Codex 会话串行完成“交互底座 → 人类入场 → 定向追猎 → 完整闭环 → 稳定化交付”。每轮交付实现、自动验证和可供下一会话直接使用的交接记录。第五轮负责集成与修复，不首次实现人偶系统、重启恢复或书屋。

本次只创建计划、初始状态和启动提示词，不执行开发或产品测试。用户在新会话粘贴某轮启动词后，该会话才执行相应开发任务；[产品设计](lobby-interaction-design.md)中的“本轮不实现代码”描述设计编写阶段，不禁止用户随后明确授权的实施。

## 固定产品约束

1. 集结区站入即准备，离开取消；首位准备者触发 30 秒，人数归零后取消，再次集结从完整 30 秒开始。普通断线取消准备。
2. 正常停服保存开局余量；世界就绪且任一原准备 UUID 核验、上线并恢复圈内站位后续计，不等待所有原准备者，无关 UUID 不能放行。
3. 怪物右键本轮活人皮肤模型直接发起个人追猎，系统处理目标当前维度。取消投票、15 秒共同目标结算、手动维度和失效目标随机替换。
4. 请求绑定目标轮次、UUID 与生命序号。搜索跨维度共享原来的 2 秒／64 候选预算；失败后的 3 秒重试间隔按发起怪物 UUID 计算，换人不绕过。
5. 保留现有安全落点、提交后应用、传送前复核与内部补偿。真实档案、世界或存储故障进入隔离，不伪装成普通重试。
6. 人偶不计作真实玩家，不泄露坐标、方向、距离、装备、背包或血量。独立分页不改变其他观察者看到的目标，迟到点击不得绑定到新目标。
7. 首次变怪物、败退和成功主动返厅沿用 30 秒出场冷却；归返引导为 5 秒，复生不等待出场冷却。技能及出场冷却的跨离线、停服处理沿用本轮既有规则。
8. 资格、致死归属及救场按既有死亡批次处理，离线人类仍保留资格，不能误判团灭。救场 60 秒，祭坛复生空装回自然出生点，无出生保护。
9. 庆祝最多 180 秒，末地固定在线名单获得临时装备，龙池直回独立大厅；在线全员回厅可提前结束，档案、录制和世界释放门槛保留。
10. 正式世界维持自然出生地形；只在大厅建设营地。新追猎规则在新轮次启用，历史记录与指纹不被追改。

## 第 1 轮 交互底座与关键风险

### 实现范围

建立统一大厅布局定义、设施登记、落点用途、菜单上下文和提示优先级。布局定义供后续加载、建造、区域判定、设施右键和传送共同使用；只读规则／书屋与竞技动作分开，避免准备或异常期间全部菜单不可用。

打通 ProtectionNetworkMixin 和 PlayerIsolationNetworkMixin 两层保护，仅允许当前连接、合法身份、距离内且由服务端登记的专用交互。不能只新增 Fabric 回调，也不能依赖 Mixin 的偶然执行顺序。真正隔离态、普通容器、无登记实体和伪造远程交互继续受限。

实现可复用人偶展示基础，并用无图形协议场景验证原 profile、双观察者独立分页、每次展示代次与实体 ID 映射、旧包失效、断线与换轮清理。不能退化成公共翻页或纯头像菜单。人偶投影与怪物玩家伪装使用独立生命周期。

实现新旧追猎语义的规则版本边界，保留旧规则原样编码与指纹。旧维度字段如需保留只作兼容，不为删字段强行迁移历史。明确并实现加载旧活动轮时的安全门槛：在旧构建完成后升级，或按既有管理员中止／恢复处置结束；不静默切换语义，也不重启旧投票。新个人追猎业务由第 3 轮接通，期间保持未开放能力关闭。

## 第 2 轮 营地与人类入场

### 实现范围

按设计建设营地，完成布局实际覆盖的有界异步区块加载、布局版本、幂等施工、设施登记与安全站位。现有大厅仅加载出生附近 3 × 3 区块，不能假设已经覆盖 64 × 48 营地。旧大厅只在明确拥有与允许范围内升级，不每次启动覆盖地形。

实现中央、怪物、圈外等候及恢复圈内落点策略，保持已核验大厅玩家自由移动，不在每 tick 把人拉回出生点。未完成建造或世界未就绪时不开放入口。

贯通 RoundEngine、Session、Runtime 与 profiles，形成一次入圈意图的权威准备操作，处理离圈、普通断线、快速进出、迟到提交与归零位置终验。不能用前端先 join 后 ready 的两个无保护异步调用冒充完成。

实现中途门确认、确认前关闭放弃、受理后关闭不撤销或重复执行；极限死者拒绝、存活人类重连、普通死亡与床／锚重生继续正确。完成正常停服与普通断线的区别，并维护相关重启夹具。

修复前四轮缺口与已有人工反馈，审核发布 JAR 不含测试、MCPFabric、调试辅助代码，产出生产制品。提供新隔离演示实例与准确安装、升级、旧轮处理、备份和回退说明。回退旧编码前需使用对应一致性备份，不能承诺新旧存档任意互读。

## 验证执行规则

当前存在的基础入口为 scripts/p0-gradle.sh checkP3 -PhardrushP1=true --console=plain，但它只覆盖实际依赖任务，不能代替新增 GameTest 专场。现有 P2 大厅、庆祝、十轮、恢复和新 JVM 场景按各自参数在独立实例运行，先核对 build.gradle 中的过滤器及互斥条件。

新增测试入口只有在本轮已经实现后，才能在交接中写成可运行命令。每轮运行新增和受影响检查；无需在没有变化时机械重跑所有强杀矩阵。不得运行图形客户端、浏览器或 computer use 测试，除非用户另行明确要求。复杂画面、选取与游玩问题放入人工清单。

所有测试使用新建的独立目录，不清空日常存档、数据库或正在使用的服务器。测试专用辅助代码不能进入发布制品，预置数据与缩短时钟需在证据中说明。

## 会话交接与状态规则

每轮启动先读 AGENTS.md、设计、计划、交接和本轮验收依据，再核验源码。状态为未开始、进行中、开发与自动验证完成、受阻之一；人工验收与部署发布另记，不混入“完成”。后轮未开始只是等待前置，不写成技术阻塞。

任一必需前轮尚未开始，或该轮主能力尚未交付时，当前会话不得替代执行整轮前置，也不得开始当前轮；应指出应先使用的启动词。只有已交付前轮的局部直接缺陷允许在本轮修复并记录归属。证据不足先复核，不自动认定通过；不能安全补齐时给出实际失败、影响和解除条件，不跳过门槛、不虚报完成，也不默默扩成第六轮。技术故障应定位修复或更换满足原约束的路线，不能降低产品要求来赶进度。

前置核验通过后，在修改代码前将当前轮标为“进行中”，写入会话、日期、HEAD 和工作树基线；取得重要结果或遇阻时及时保存进度。若当前轮已有进行中记录，应先恢复已有工作再续作，不重新初始化。已完成轮次需先复核实际交付，不因重复粘贴启动词而清空记录或重新施工。

每次交接填写日期、会话标识、基线、改动、接口、验证命令与结果、证据路径、实际限制、人工待验和下一轮入口。已有验证由后轮按变更与风险复核，不把历史命令测试算成新交互证据。

各会话只执行用户指定的一轮，可自主处理必要实现与修复；未经另行授权不提交、推送、部署、操作日常实例或启动下一轮。当前文档准备会话不执行上述开发任务。
