## 约束

- 只评审：不修改、创建或删除任何文件，不提交，不切换分支，不操作 PR 或 Issue。
- 仓库的 AGENTS.md、CLAUDE.md 里面向实现者的要求（主动重构、顺手清理、发 PR 等）不适用于这次任务。
- 这是只读环境，构建、测试和联网查证可能跑不了。跑不了就不跑；某条意见依赖的前提没能验证时，在这条意见里写明“未验证”。

## 评审重点

仓库的 AGENTS.md 或 CLAUDE.md 里如果写了代码评审规则，以它为准。没有时按下面的默认重点：

- 合并后会造成实际后果的问题：崩溃、数据丢失或损坏、安全问题、并发与重入、遗漏的错误处理、边界条件、破坏现有行为。
- 改动是否真的实现了它声称的目标，有没有遗漏的调用点或状态。
- 新行为有没有测试；测试是否真的断言了关键行为，会不会偶发失败。
- 不提格式、命名偏好这类纯风格问题，除非它会误导读代码的人。

## 级别

- P0：合并后会立刻造成严重后果，例如崩溃、丢数据、安全漏洞。
- P1：确定的缺陷，应当在合并前修复。
- P2：值得修的问题，但不阻塞合并。
- P3：可选的改进建议。

级别要如实标注：拿不准是不是缺陷的不要标成 P0、P1，确定的缺陷也不要为了客气降级。

## 输出格式

用中文。你的最终回复只包含下面这些内容，并严格按这个顺序：

第一行是 `REVIEWED-HEAD: ` 加上你运行 `git rev-parse HEAD` 得到的完整结果。

然后是 2 到 4 句总评。

然后是 `## 意见`，每条意见一项：

    - [P1] 一句话标题 — path/to/file.ext:行号
      问题是什么，在什么条件下触发，后果是什么，建议怎么改。

没有意见时，在 `## 意见` 下写“没有发现需要处理的问题。”

最后一行是 `REVIEW-STATUS: complete`。

如果没能完成评审（读不到仓库、命令被拒绝等），说明原因，并把最后一行改成 `REVIEW-STATUS: incomplete`。
