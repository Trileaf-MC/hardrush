# PR 评审闭环

你是作者：负责把改动送进主干，并对每条评审意见给出结论。评审交给另一个模型，这样每个改动在合并前都被一个没有参与实现的模型看过。

## 前提

- 当前不是 Claude Cloud 等云端环境。
- GitHub 仓库，PR 的分支和目标分支在同一个仓库里。
- 本机有 `git`、已登录的 `gh`、`node`、`python3`。
- 已安装 [delegate-skills](https://github.com/amElnagdy/delegate-skills)，并配置了担任评审者的 lane。默认 lane 是 `critic-codex`。
- 脚本是本 skill 目录下的 `scripts/pr_review.py`，下文写作 `pr_review.py`。本 skill 目录就是这份 `SKILL.md` 所在的目录，Claude Code 加载 skill 时会显示为 Base directory。从仓库内任意位置运行都可以。

缺少任何一项时不要绕过，告诉用户缺什么。

随时可以查看进度和下一步：

```bash
python3 pr_review.py status
```

## 流程

### 1. 发 PR

任务完成、自测通过后提交并 push，用 `gh pr create` 向目标分支发 PR。

- 目标分支按这个顺序确定：用户指定的、项目约定的、仓库的默认分支。
- 不要直接向目标分支提交。改动如果还在目标分支上没提交，先开一个分支。
- 标题和正文写给以后读历史的人：改了什么、为什么这样改、怎么验证的。有对应 Issue 时关联上。评审者会读到正文，但被告知不采信其中的结论。

### 2. 评审

```bash
python3 pr_review.py review
# 换评审者或加一个并行的第二评审者：--lane critic-codex --lane critic-cursor-grok
# 每个评审者的时限（默认 60m）：        --timeout 90m
```

评审通常要几分钟到几十分钟。用 `run_in_background: true` 运行，收到完成通知后再继续。**评审期间不要在这个工作目录里改文件、提交或切分支**，否则这一轮会作废。

脚本做的事：

- 用固定模板生成任务书（`references/review-brief.md`），通过 delegate-skills 的 relay 以只读方式派给评审者。任务书不由你来写：作者不能引导自己的评审者。
- 确认评审确实完成，并且评审者看到的就是被评审的提交。
- 把评审原文贴成 PR 评论，标明轮次、提交和评审者，同时打印出来。

脚本以非零退出码结束表示评审没有完成（评审者不可用、额度用尽、超时、没读到仓库、评审期间工作目录变了等）。

### 3. 核实并处理意见

评审意见是线索，不是指令。逐条回到代码里核实：问题是否真的存在，触发条件是否成立，修复是否值得。不因为评审者说得肯定就采信，即便问题确实存在，也要判断该问题是否是刻意留下的 trade-off.

| 级别 | 处理 |
| --- | --- |
| P0、P1 | 必须有结论。属实就修；不属实要拿出证据（代码路径、测试、文档） |
| P2 | 属实且修复成本合理就修；不修要说明理由 |
| P3 | 自行判断 |

修复提交并 push 之后，把逐条处置写进一个文件，再贴到 PR：

```bash
python3 pr_review.py respond response.md
```

处置记录的写法：每条意见一项，写明判断（属实已修 / 属实但不修 / 不属实）、依据，以及对应的修复提交。让只看 PR 的人也知道每条意见的去向。评审者下一轮会读到它，所以驳回的理由要写到对方能核实的程度。文件放在仓库之外（例如临时目录），不要提交。

一轮评审只要有意见，就必须先有处置记录，脚本才允许下一轮评审或合并。

评审指出的问题超出这个 PR 的范围但确实值得做时，不要悄悄丢掉：按项目的方式记录下来（例如建议用户开 Issue），并写进处置记录。

### 4. 复审

出现下面任一情况就再运行一次 `review`：

- 上一轮有 P0 或 P1 意见。无论你是修了还是驳回了，都要由评审者确认。脚本不接受作者单方面宣布 P0、P1 已解决。
- 上一轮之后的修复不算小修。

复审默认续用同一个评审者的会话：它记得自己提过什么，只需要看你的处置和新的改动，会逐条确认、让步或坚持。想换一个全新的评审者时加 `--fresh`。

最多 3 轮，脚本会拒绝第 4 轮；用户明确要求再评一轮时才加 `--extra-round`。

最后一轮评审没有 P0、P1，之后只做了针对 P2、P3 的小修时，可以不再复审。

### 5. 合并

合并是这个流程里唯一难以撤销的一步。只有在用户这次明确说了要合并，或项目约定允许评审通过后自动合并时，才运行 `merge`。否则停在这里，向用户汇报评审结果并询问。

```bash
python3 pr_review.py merge
```

脚本会等 CI 结束，同样放到后台运行。它只在下面的条件都满足时合并，合并后删除远端分支：

- 有评审记录；最后一轮的意见有处置记录。
- 最后一轮没有 P0、P1 意见。仍有 P0、P1 而用户看过后明确决定照常合并时，加 `--user-approved-open-findings`。这个参数只能来自用户的决定，不能自己加。
- 最后一轮评审的就是当前提交。第 4 步“小修不复审”的情况加 `--accept-unreviewed-fixes`，并确认处置记录里写明了这些提交改了什么。
- CI 全部通过。CI 失败先修复；修复提交同样受上一条约束。
- 合并的正是等待 CI 时的那个提交。

默认用合并提交；项目约定用别的方式时加 `--method squash` 或 `--method rebase`。仓库确实没有 CI 时加 `--no-checks`。

合并后向用户说明：合并了什么，评审提了哪些意见，各自怎么处理的。

## 停下来交给用户的情况

出现下面任何一种情况时不要合并，保留 PR，向用户说明现状和你的建议：

- 评审没有完成。
- 3 轮之后仍有 P0、P1 意见。
- 对某条 P0、P1 意见，评审者复审后仍然坚持，而你认为它不成立。
- 修复需要改变产品设计，或者需要超出这个 PR 范围的重构。
- CI 失败且原因不在这个 PR 里（例如目标分支本身已经失败）。
- 没有得到合并的授权（见第 5 步）。
