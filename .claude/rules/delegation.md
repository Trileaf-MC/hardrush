# 委派规则（delegate-skills）

**在 claude cloud 环境，以及你当前没有 `codex-delegate` 这样的 skill 时直接忽略本文档。** 

本文档只用于指导担任编排者的 Claude 主会话如何委派任务给子代理。被委派的实现者（Codex、Cursor 等）不读这个文件，它们读的是 AGENTS.md 和你写的任务书。

目标：主线程的上下文只留给产品/架构判断、任务拆分、验收和提交。凡是会产生大量中间输出（读很多文件、长日志、反复试错），又能用一段摘要交回结论的工作，都派出去。委派省的是你的上下文，不是 token，所以不要为了"显得并行"而委派。

lane 定义在 `~/.config/delegate-skills/config.json`：`execute`、`research`、`critic-codex`（均为 codex-delegate），`critic-cursor-grok`（cursor-delegate）。

## 何时委派：按顺序问自己

1. 下一步是否立刻依赖这个结果，而且几次 Read/Grep 就能拿到？是 → 自己做。
2. 是否要读 10 个以上文件、会产生长日志，或者能拆成 3 个以上互不依赖的部分？是 → 委派。
3. 验收标准能否写成命令或可核对的清单？不能 → 先把标准想清楚；想不清楚就留在主线程。
4. 是否和正在进行的写任务改同一批文件？是 → 串行，或者并进同一份任务书。

## 分工

你自己做，不委派：

- 产品设计、架构判断、AGENTS.md 里 Level 2 的重构方案。
- mixin 和适配层的结构性决策。
- 任务拆分、写任务书、验收、提交。
- 根因判断：调研和排查可以外派，但"问题到底是什么、该改哪里"由你根据证据下结论。不要把理解本身委派出去。
- 很快就能内联做完的小改动；一两次 Read/Grep 就能回答的定位；验收标准说不清的任务；需要真实客户端或游玩才能判断的工作。
- 每一步都取决于上一步结果的紧耦合工作。

下面这些委派给 codex-delegate（个别条目用 cursor-delegate，已注明），不要自己做，也不要派 Claude 子代理。

实现：

- `--lane execute`：范围明确、有客观验收标准的实现。最合适的是 `core` 和 `persistence` 里有单元测试覆盖的改动、批量机械改动、补测试。
- 迁移、改名、删除 API 这类扇出改动：按模块拆成任务队列，默认串行（见"多任务队列"）。只有文件完全不相交时才并行。
- 多个互不相关的失败（3 个以上测试类、根因明显不同）：每个根因域派一个 `--lane execute`，各用独立 worktree，任务书写明只能动哪些文件。失败之间可能相关时不要并行，先做分诊。

调研：

- `--lane research`：大范围只读调研，例如定位代码、梳理调用链、盘点某类用法。
- 原版机制查证：minecraft-knowledge 要往 `.local/` 写缓存，在只读沙箱里会失败。用 `--lane research --sandbox workspace-write` 派发，任务书写明不得改动受版本控制的文件，回来后确认 `touchedFiles` 为空。
- 外部 API/文档查证（第三方库、加载器、映射等）：`--lane research --web-search`。要求给出来源链接和适用版本，并与仓库里实际依赖的版本核对。

诊断：

- 构建/测试失败分诊：不要把完整的 Gradle 输出拉进主线程。用 `--lane research --sandbox workspace-write --network-access` 派发，任务书写明只跑命令、读日志、定位问题，不改受版本控制的文件。要求返回：失败的测试或任务列表，每个失败的首个根因堆栈片段（只保留关键几行）及 file:line，初步归因，以及哪些失败可能同源。回来后确认 `touchedFiles` 为空。
- 失败复现与二分：只在专用 worktree 里做（`--cd` 指向它）。任务书写明只允许在该 worktree 内使用 `git bisect`/`git checkout`，不得碰其他工作区。返回首个坏提交、复现命令和最小复现步骤。涉及 Gradle 时同样加 `--network-access` 和 `--sandbox workspace-write`。
- 调试的第二意见：同一个问题你已经修过两次仍没解决，或者手上有两个以上互相竞争的假设时，用 `--lane critic-codex`（只读）派发。任务书写明现象、复现方式、已排除的假设及证据、你当前倾向的假设，要求对方对每个假设逐一给出支持和反对的证据（file:line），并提出你没考虑到的假设。第一次尝试修复之前不要用。

评审：

- 实现者 diff 的独立评审：diff 跨越多个模块、改了 `persistence` 的数据格式、动了 mixin 注入点，或者你一遍读不完时，在自己验收之前派一个不共享上下文的评审。用 `--lane review`；加入之前用 `--lane critic-codex`。评审者最好和实现者不是同一个 lane。任务书给出任务书原文、基准提交、验收命令；实现者的报告标明为"待核实的声明"。要求两个结论（是否符合任务书、代码质量是否合格），每条问题带 file:line 和严重程度，只报本次改动引入的、具体可修的问题。评审不能代替你自己的验收。

难题：

- best-of-N：只用于解法路径不确定、但验收命令客观的难题。在两个独立 worktree 里，用同一份任务书分别派 `--lane execute` 和 `--lane execute-cursor`。你比较两份 diff 和验收输出，选一份，或者综合思路后让其中一个返工。它会让你的审阅量翻倍，默认不用，用之前告诉用户。

## 派发参数

- `--cd` 指向你当前所在的工作区；在 worktree 里就用 worktree 路径。并行的写任务各用独立 worktree，同一工作区内串行。
- 凡是要跑 Gradle 的任务都加 `--network-access`：Gradle 需要本地 socket，否则在沙箱里无法启动。续聊时要重新传，并同时带上 `--sandbox workspace-write`。
- 实现类任务加 `--timeout`，例如 `--timeout 2h`。
- relay 一律用 Bash 的 `run_in_background: true` 运行。等待期间做不相关的事，或者结束本轮。不要轮询，不要读实现者的过程输出；只读结果里的 `status`、`exitCode`、`signal`、最终报告和 `touchedFiles`。
- 一波并行最多 2–4 个任务。你的审阅速度才是真正的上限。多个 worktree 同时跑 Gradle 会争抢内存；如果 `signal` 带 OOM 提示，就降低并行度。
- 所有只读派发（`critic-codex`、`critic-cursor-grok`、只读调研）回来都确认 `touchedFiles` 为空。cursor-delegate 的派发可以加 `--stall-timeout 10m`，防止它卡住不退出。

## 任务书必须写明

- 角色：你是实现者，范围以任务书为准。AGENTS.md 中"你的角色"和 Level 1、Level 2 重构不适用于本次任务；范围之外发现的问题只写进报告，不要动手。
- 不提交。不使用 `hardrush_server`、`hardrush_client` MCP 工具，不启动测试服或客户端。不执行影响整个工作区的 git 操作（bisect 任务除外，且只限于它的 worktree）。
- 现状、要改什么，以及明确的"不要动"清单。之前任务已经定下的接口、你对歧义的裁决，直接写进去。不要粘贴对话历史或整份计划。
- 并行时：写明它负责哪些文件或模块，告诉它仓库里还有别的代理在改其他部分，不要回退不属于它的改动。
- 验收命令：按改动涉及的模块列出，例如 `./gradlew :core:test --offline --console=plain`、`:persistence:test`、`:platforms:mc263:test`。要求实现者修复验收命令暴露的问题，而不只是报告。gametest 由你自己在验收时跑，不交给实现者。
- 涉及原版机制、数值或行为时：要求按 `.agents/skills/minecraft-knowledge/SKILL.md` 查证，并在报告里给出证据来源。
- 报告格式：改了什么、验收命令的实际输出、做出的设计取舍、范围之外的发现。保持精简；长清单写到 `.local/delegate/<任务名>.md`，报告里只给路径。调研类报告分三段写：事实（附 file:line 或来源）、推断、未决问题。

## 验收

- 不采信实现者的自述：自己重跑验收命令，对照任务书读 diff，检查有没有超出范围的改动。
- 实现者报告的设计取舍和范围外发现，按 AGENTS.md"决策准则"的分级处理并告诉用户，不要默默吸收或丢弃。
- 需要返工时，用 `--session <threadId>` 发增量任务书，只写差异。

## 异常处理

- `status` 不是成功、`exitCode` 非零或有 `signal` 时：先读报告和工作树，判断是超时、资源问题还是任务本身有问题，再决定是续聊还是重派。不要盲目重试。
- 前提在派发时就冻结了。中途发现任务书的前提错了，就停掉，修正任务书后重派，不要在错误前提上的结果里挑挑拣拣。
- 同一任务返工两次仍不达标：停下来，自己重新理解问题，或者先走"调试的第二意见"，不要继续派第三次。

## 多任务队列

- 默认串行，按依赖顺序执行，一个任务一次提交，每次派发前工作树是干净的。
- 前面任务已经定下的约束，要明确写进后面的任务书。
- 超过 3 个任务的队列，维护 `.local/delegate/progress.md`：状态表（附提交哈希）、每个任务的验收笔记、"需要用户看"一节。上下文压缩之后以这个文件和 `git log` 为准，不要凭记忆重派已经完成的任务。
- 队列结束后，在最终工作树上跑所有涉及模块的测试和你自己的 gametest，全仓 grep 这次队列的主题词。改动面大时，再派一次 `--lane review` 做整条分支的一致性评审。

## 方案的对抗性评审

当你制定方案/计划的时候，如果用户明确提及"方案要对抗性评审"，那么你的方案/计划在给用户看之前先评审

- 并行派发 `codex-delegate --lane critic-codex` 和 `cursor-delegate --lane critic-cursor-grok`，两者都是只读。
- 任务书包含方案全文、相关代码位置，以及 AGENTS.md"关于功能"一节作为评审标准。已经有共识的点列为"已同意"；有争议的点把两种立场都写出来，要求对方坚持或让步并给出理由。
- 每条反对意见必须指向具体的代码位置或 AGENTS.md 条款，并标注严重程度（阻断/重要/建议）。没有证据的泛泛担忧单独归为"疑虑"。
- Cursor 的只读靠 plan 模式，评审后确认 `touchedFiles` 为空。两个评审都回来之后再判定，不要先看一个就动手修订。
- 逐条判定采纳或驳回并写明理由，修订方案。向用户呈现方案时附上评审摘要：采纳了什么、驳回了什么、仍有分歧的点。
